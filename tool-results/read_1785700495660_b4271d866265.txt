    20→    20→## 1. High-Level Architecture
    21→    21→
    22→    22→### 1.1 Monorepo Structure
    23→    23→
    24→    24→HotHoosh is a **Turborepo + pnpm** monorepo containing three applications and two packages. Turborepo provides task orchestration with remote caching and parallel execution; pnpm provides strict, content-addressable dependency management that prevents phantom dependencies.
    25→    25→
    26→    26→```
    27→    27→hotHoosh/
    28→    28→├── apps/
    29→    29→│   ├── web/                    # Next.js 15 — User workspace (chat, agents, knowledge)
    30→    30→│   ├── admin/                  # Next.js 15 — Admin panel (management, analytics, settings)
    31→    31→│   └── api/                    # NestJS   — Single API server (modular monolith)
    32→    32→├── packages/
    33→    33→│   ├── shared/                 # Branded types, Zod validators, constants, pure utilities
    34→    34→│   ├── ui/                     # Shared React component library (shadcn/ui + custom)
    35→    35→│   └── eslint-config/          # Shared ESLint configuration
    36→    36→├── docs/                       # PRD, Database, Backend Architecture, Agent System, etc.
    37→    37→├── scripts/                    # Build, deploy, and utility scripts
    38→    38→├── turbo.json                  # Turborepo pipeline configuration
    39→    39→├── pnpm-workspace.yaml         # Workspace package references
    40→    40→├── tsconfig.base.json          # Shared TypeScript strict config
    41→    41→├── .eslintrc.cjs               # Root ESLint config
    42→    42→├── .prettierrc                 # Prettier configuration
    43→    43→└── package.json                # Root workspace scripts
    44→    44→```
    45→    45→
    46→    46→**Turborepo pipeline:** Build, lint, type-check, and test tasks are orchestrated with `turbo.json`. Tasks are cacheable by file hash, enabling instant re-runs on unchanged code. The `topo` dependency order ensures `packages/shared` builds before `apps/web`.

   315→   315→### 3.2 State Management Boundaries
   316→   316→
   317→   317→HotHoosh enforces a strict separation of state management concerns. Overlapping these boundaries is a violation of Engineering Rules §10.4.1.
   318→   318→
   319→   319→| State Type | Tool | Scope | Examples |
   320→   320→|-----------|------|-------|----------|
   321→   321→| **Server state** | TanStack Query | API data: users, agents, knowledge bases, usage stats | `useQuery`, `useMutation`, `useInfiniteQuery` |
   322→   322→| **Client state** | Zustand | UI-only: theme, sidebar open/closed, command palette, selection | `useThemeStore`, `useSidebarStore` |
   323→   323→| **Form state** | React Hook Form + Zod | Form inputs: login form, create agent, upload document | `useForm` with `zodResolver` |

   326→   326→**Key rules:**
   327→   327→- Zustand stores never hold server data. If it came from the API, it belongs in TanStack Query.
   328→   328→- Zustand store actions are synchronous. Async work (API calls) lives in TanStack Query mutations, which call Zustand actions on success.
   329→   329→- Components read Zustand via selectors (`useThemeStore(s => s.theme)`) to prevent unnecessary re-renders.
   330→   330→- TanStack Query keys use a factory pattern: `chatKeys.messages(sessionId)`, `adminKeys.agents.list(filters)`.

   442→   442→- Use `ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `inline-*`, `block-*` exclusively.

   460→   460→## 4. Backend Architecture
   461→   461→
   462→   462→### 4.1 Architectural Philosophy
   463→   463→
   464→   464→HotHoosh's backend is a **NestJS modular monolith** with hexagonal module boundaries (PRD Principle #15, Engineering Rules §10.4.2). The entire backend runs as a single deployable unit, but internal module boundaries are strictly enforced as if each module were a separate microservice. Modules communicate exclusively through well-defined public APIs (injected services and domain events), never through shared mutable state or direct internal imports across module boundaries.
   465→   465→
   466→   466→The modular monolith preserves the ability to extract modules into separate services in the future (v2.0+) because hexagonal boundaries ensure low coupling and high cohesion within each domain module.
   467→   467→
   468→   468→### 4.2 Technology Stack
   469→   469→
   470→   470→| Layer | Technology | Rationale |
   471→   471→|-------|-----------|----------|
   472→   472→| Runtime | Node.js 20+ LTS | Non-blocking I/O for SSE streaming and concurrent AI requests |
   473→   473→| Framework | NestJS 10+ | DI container, module system, guard/filter/interceptor pipeline |
   474→   474→| ORM | TypeORM | PostgreSQL-native, custom repository support, migration tooling |
   475→   475→| Database | PostgreSQL 16+ | pgvector, RLS, JSONB, partitioned tables, full-text search |
   476→   476→| Cache/Queue | Redis 7+ | BullMQ job queues, session store, rate limiting, caching |
   477→   477→| Validation | Zod | Shared schemas between frontend and backend (§10.1.3) |
   478→   478→| File Storage | S3-compatible (MinIO) | Document storage for knowledge bases |
   479→   479→| Email | Nodemailer (SMTP) | Transactional emails for invitations, password resets |
   480→   480→| Streaming | Server-Sent Events (SSE) | One-directional real-time AI response streaming |
   481→   481→
   482→   482→### 4.3 12 Domain Modules
   483→   483→
   484→   484→Each domain module follows hexagonal architecture: controllers define the HTTP API boundary, services encapsulate business logic, and repositories (TypeORM custom repositories) handle data access. Modules expose only their public service interface; internal implementations are private.
   485→   485→
   486→   486→| Module | Responsibility | Key Tables | Emits Events |
   487→   487→|--------|---------------|------------|-------------|
   488→   488→| **auth** | Authentication, token mgmt, invitation, 2FA, impersonation | `users`, `refresh_tokens`, `user_invitations` | `UserLoggedIn`, `UserRegistered`, `UserInvited`, `UserImpersonation` |
   489→   489→| **users** | User CRUD, profile, preferences, search | `users`, `workspace_users`, `roles` | `UserCreated`, `UserUpdated`, `UserDeleted` |
   490→   490→| **organizations** | Org lifecycle, settings, plan management | `organizations`, `subscriptions` | `OrganizationCreated`, `OrganizationSuspended` |
   491→   491→| **companies** | Company CRUD within organization scope | `companies` | `CompanyCreated`, `CompanyUpdated`, `CompanyDeleted` |
   492→   492→| **brands** | Brand CRUD with visual identity (colors, fonts, CSS) | `brands` | `BrandCreated`, `BrandUpdated` |
   493→   493→| **workspaces** | Workspace CRUD, members, model restrictions | `workspaces`, `workspace_users` | `WorkspaceCreated`, `WorkspaceMemberAdded` |
   494→   494→| **agents** | Agent lifecycle (draft → active → deprecated), bindings | `agents`, `agent_tools`, `agent_knowledge`, `agent_memory`, `tools`, `tool_parameters` | `AgentCreated`, `AgentDeployed`, `AgentDeprecated` |
   495→   495→| **chat** | Sessions, messages, branching, history | `chat_sessions`, `chat_messages` | `ChatSessionCreated`, `MessageSent`, `MessageReceived` |
   496→   496→| **knowledge** | Knowledge base CRUD, document upload, processing | `knowledge_bases`, `knowledge_documents`, `knowledge_chunks`, `knowledge_embeddings` | `KnowledgeBaseCreated`, `DocumentUploaded`, `DocumentProcessingComplete` |

   499→   499→| **audit** | Audit log recording, querying, retention | `audit_logs`, `system_logs` | None (audit is a sink, not a source) |
   500→   500→
   501→   501→### 4.4 6 Engine Modules
   502→   502→
   503→   503→Engine modules provide AI/ML infrastructure consumed by domain modules. They are stateless computational units (no owned database tables, except for caching/state).
   504→   504→
   505→   505→| Engine | Responsibility | Consumed By | Key Design |
   506→   506→|--------|---------------|-------------|------------|
   507→   507→| **llm-router** | Route AI requests to optimal provider/model, health monitoring, failover | `ChatModule`, `RAGEngine` | 5-step routing pipeline, circuit breakers, Redis health cache |
   508→   508→| **context-engine** | Token budget allocation, context window management, priority reduction | `ChatModule` | Priority: Knowledge (40%) → History (30%) → Memory (20%) → Tools (10%) |
   509→   509→| **rag-engine** | Document processing pipeline, hybrid retrieval, Persian NLP | `ChatModule`, `KnowledgeModule` | HNSW + BM25 with RRF, 4 chunking strategies, Persian normalizer |
   510→   510→| **memory-engine** | Memory pack resolution, hierarchical assembly, injection | `ChatModule`, `ContextEngine` | Workspace → Brand → Company → Org (accumulates upward) |
   511→   511→| **tool-engine** | Tool registry, validation, sandboxed execution, result formatting | `ChatModule` | JSON Schema input validation, timeout enforcement, audit logging |
   512→   512→| **streaming-engine** | SSE connection management, event emission, backpressure | `ChatModule`, `KnowledgeModule` | 8 event types, Redis connection tracking, 50ms batch window |
   513→   513→
   514→   514→### 4.5 Domain Event System
   515→   515→
   516→   516→Modules never import each other's services directly for cross-domain operations. Instead, they emit **domain events** through an in-memory event bus backed by Redis for reliability. A **transactional outbox** pattern ensures no events are lost: events are written to the database within the same transaction as the state change, then dispatched asynchronously by a BullMQ worker.
   517→   517→
   518→   518→```
   519→   519→Service performs write operation
   520→   520→  → Opens DB transaction
   521→   521→  → Writes domain state change
   522→   522→  → Inserts outbox_events record (same transaction)
   523→   523→  → Commits atomically
   524→   524→  → BullMQ worker polls outbox
   525→   525→  → Dispatches to event bus
   526→   526→  → Handlers react asynchronously
   527→   527→```
   528→   528→
   529→   529→### 4.6 Authentication: Dual-Token JWT
   530→   530→
   531→   531→| Token | Algorithm | Expiry | Storage | Purpose |
   532→   532→|-------|-----------|-------|---------|---------|
   533→   533→| **Access** | RS256 (asymmetric) | 15 minutes | In-memory only | API authentication. Validated via public key — no DB lookup. |
   534→   534→| **Refresh** | HS256 (symmetric) | 7 days | `HttpOnly`, `Secure`, `SameSite=Strict` cookie | Session persistence. Validated via DB lookup (revocation check). |
   535→   535→
   536→   536→**Token rotation on refresh:** Every refresh invalidates the old token and issues a new one with the same `family_id`. If a previously-revoked token is presented (theft detection), all tokens in that family are revoked.
   537→   537→
   538→   538→**Password hashing:** Argon2id (memory=64MB, time=3, parallelism=4). Account lockout after 10 failed attempts within 1 hour (30-minute lockout).
   539→   539→
   540→   540→### 4.7 Authorization: Three-Layer RBAC + RLS
   541→   541→
   542→   542→| Layer | Source | Scope | Example Roles |
   543→   543→|-------|--------|-------|--------------|
   544→   544→| **Organization Role** | `roles` table (`level = 'org'`) | Organization-wide | `super_admin`, `org_admin`, `org_member` |
   545→   545→| **Workspace Role** | `workspace_users.role_id` | Workspace-specific | `workspace_admin`, `workspace_member`, `workspace_viewer` |
   546→   546→| **Resource Permissions** | `roles.permissions` JSONB | Individual resource | `agents:create`, `knowledge:delete`, `billing:read` |
   547→   547→
   548→   548→Effective permissions are the **union** of all permissions from all roles the user holds. Authorization is enforced via NestJS guards (`JwtAuthGuard → TenantScopeGuard → RolesGuard → ImpersonationGuard`).
   549→   549→
   550→   550→**PostgreSQL RLS** provides database-level tenant isolation — even if application code has a bug, RLS prevents cross-tenant data access. Session variables (`app.current_user_id`, `app.current_org_id`) are set at connection checkout.
   551→   551→
   552→   552→### 4.8 API Design
   553→   553→
   554→   554→All endpoints follow REST conventions with URL-based versioning (`/v1/`), consistent response envelopes, and pagination on all list endpoints.
   555→   555→
   556→   556→**Response envelope (success):**
   557→   557→```json
   558→   558→{ "data": { ... }, "meta": { "page": 1, "limit": 20, "total": 142, "hasMore": true } }
   559→   559→```
   560→   560→
   561→   561→**Response envelope (error):**
   562→   562→```json
   563→   563→{ "error": { "code": "AGENT_NOT_FOUND", "message": "عامل هوش مصنوعی یافت نشد", "details": {} } }
   564→   564→```
   565→   565→
   566→   566→**SSE streaming** is used for all AI responses. The endpoint `GET /v1/chats/:sessionId/stream` emits 8 event types: `token`, `message_start`, `message_delta`, `message_complete`, `tool_call`, `tool_result`, `error`, `heartbeat`.
   567→   567→
   568→   568→### 4.9 Error Handling
   569→   569→
   570→   570→Each domain module defines typed exceptions extending `DomainException`. A global `DomainExceptionFilter` catches all unhandled exceptions and returns the standardized error envelope. Raw stack traces never reach the client. Circuit breakers protect against external service failures (AI providers, S3, SMTP, embedding APIs).

   913→   913→## 7. Infrastructure
   914→   914→
   915→   915→### 7.1 PostgreSQL 16+
   916→   916→
   917→   917→PostgreSQL is the sole data store, chosen for its rich feature set that eliminates the need for multiple specialized databases.
   918→   918→
   919→   919→| Feature | Implementation | Purpose |
   920→   920→|---------|---------------|---------|
   921→   921→| **pgvector** (0.7+) | HNSW index with cosine similarity | Vector embeddings for RAG — 10M+ vectors |
   922→   922→| **Row-Level Security** | Session variable-based policies | Tenant isolation at DB level |
   923→   923→| **JSONB** | GIN indexes via `btree_gin` | Flexible settings, permissions, tool schemas |
   924→   924→| **Full-Text Search** | `to_tsvector('persian', ...)` with GIN | BM25 retrieval for hybrid RAG search |
   925→   925→| **pg_trgm** | Trigram GIN indexes | Fuzzy text search |
   926→   926→| **Partitioning** | Monthly range on `usage_logs`, `audit_logs`, `chat_messages` | Query performance on high-volume tables |
   927→   927→| **UUID v7** | Custom `uuid_generate_v7()` function | Time-sortable globally unique PKs |
   928→   928→| **BIGINT PKs** | Auto-increment on append-only tables | Maximum insert throughput for logs/messages |
   929→   929→
   930→   930→**Connection pooling:** PgBouncer in transaction mode for high-concurrency scenarios. Pool size configurable (default: 20 connections). Connection initialization callback sets RLS session variables.
   931→   931→
   932→   932→### 7.2 Redis 7+
   933→   933→
   934→   934→Redis serves six distinct roles in the HotHoosh architecture:
   935→   935→
   936→   936→| Role | Data Type | TTL | Key Pattern Example |
   937→   937→|------|-----------|-----|-------------------|
   938→   938→| **BullMQ backing store** | Lists, hashes, sets | Job-dependent | `bull:document-processing:*` |
   939→   939→| **SSE connection tracking** | Hash | 30 min | `sse:connections:{sessionId}` |
   940→   940→| **Rate limiting** | String (sliding window) | Window-dependent | `ratelimit:{userId}:{endpoint}` |
   941→   941→| **Session lockout** | String (counter) | 1 hour | `lockout:{userId}:attempts` |
   942→   942→| **Event outbox pointer** | String | Persistent | `outbox:lastProcessedId` |
   943→   943→| **Provider health cache** | Hash | 30 seconds | `health:{providerId}` |
   944→   944→| **Config cache** | Hash | 5 minutes | `cache:config:{scope}:{key}` |
   945→   945→| **Token family tracking** | String (set) | 7 days | `family:{familyId}:tokens` |
   946→   946→| **Password reset tokens** | String | 1 hour | `reset:{email}` |
   947→   947→| **Idempotency keys** | String | 24 hours | `idempotency:{key}` |
   948→   948→
   949→   949→Configured with `maxmemory-policy: allkeys-lru`. Connection pooling enabled (max 20 connections).
   950→   950→
   951→   951→### 7.3 S3-Compatible Storage
   952→   952→
   953→   953→Used for all file storage. MinIO for self-hosted deployments; AWS S3 for cloud deployments. All uploads use server-side encryption (AES-256). Pre-signed URLs for client-side downloads (15-minute expiry).
   954→   954→
   955→   955→| Operation | Key Pattern | Max Size | Validation |
   956→   956→|-----------|-------------|----------|------------|
   957→   957→| Document upload | `knowledge/{wsId}/{kbId}/{uuid}/{filename}` | 50 MB | Magic bytes, content scan |
   958→   958→| Avatar upload | `avatars/{userId}/{uuid}.{ext}` | 5 MB | Image magic bytes |
   959→   959→| Logo upload | `logos/{entityType}/{entityId}/{uuid}.{ext}` | 5 MB | Image magic bytes |
   960→   960→| Exports/Backups | `backups/{type}/{date}/{filename}` | Variable | N/A |
   961→   961→
   962→   962→### 7.4 BullMQ Queue System
   963→   963→
   964→   964→11 queues handle all asynchronous processing. No long-running operations run in request handlers.
   965→   965→
   966→   966→| # | Queue | Purpose | Priority | Concurrency |
   967→   967→|---|-------|---------|----------|-------------|
   968→   968→| 1 | `document-processing` | Knowledge document pipeline (extract → chunk → embed → index) | Low | 5 |
   969→   969→| 2 | `embedding-generation` | Batch embedding for chunks | Low | 3 |
   970→   970→| 3 | `vector-indexing` | Bulk vector index updates | Low | 2 |
   971→   971→| 4 | `health-check` | AI provider health monitoring (every 30s) | Critical | 3 |
   972→   972→| 5 | `email-sending` | Transactional emails | Medium | 10 |

  1021→  1021→## 8. Key Design Decisions
  1022→  1022→
  1023→  1023→### DD-01: Modular Monolith, Not Microservices
  1024→  1024→
  1025→  1025→**Decision:** Build the backend as a single NestJS application with strict hexagonal module boundaries, not as a set of independent microservices.
  1026→  1026→
  1027→  1027→**Rationale:**
  1028→  1028→
  1029→  1029→| Factor | Modular Monolith | Microservices |
  1030→  1030→|--------|-----------------|---------------|
  1031→  1031→| Development velocity | Single codebase, single build, single deploy | Multiple codebases, independent builds |
  1032→  1032→| Data consistency | Single PostgreSQL transaction spans all modules | Distributed transactions (Saga) or eventual consistency |
  1033→  1033→| Team size fit | 3–8 developers (current phase) | Requires 10+ for independent service ownership |
  1034→  1034→| Latency | In-process communication (nanoseconds) | Network communication (milliseconds) |
  1035→  1035→| Operational cost | Single process to monitor and debug | Service mesh, load balancing, distributed tracing |
  1036→  1036→
  1037→  1037→Hexagonal boundaries ensure that any module can be extracted into a separate service in v2.0+ with minimal refactoring. The modular monolith gives us microservice-level discipline without microservice-level operational tax.
  1038→  1038→
  1039→  1039→### DD-02: PostgreSQL, Not MongoDB
  1040→  1040→
  1041→  1041→**Decision:** Use PostgreSQL 16+ as the sole data store.
  1042→  1042→
  1043→  1043→**Rationale:** HotHoosh requires ACID transactions (billing, token accounting), relational data (Org → Company → Brand → Workspace hierarchy), full-text search (BM25 for RAG), vector search (pgvector for embeddings), and row-level security (tenant isolation). PostgreSQL provides all of these in a single database, eliminating the operational complexity of maintaining MongoDB + a vector DB + a relational DB. JSONB columns provide schema flexibility where needed (settings, permissions, tool schemas).
  1044→  1044→
  1045→  1045→### DD-03: pgvector, Not Dedicated Vector DB (Initially)
  1046→  1046→
  1047→  1047→**Decision:** Use pgvector for vector storage and HNSW indexing. Do not introduce Pinecone, Qdrant, or Weaviate in v1.0.
  1048→  1048→
  1049→  1049→**Rationale:** pgvector with HNSW indexes achieves < 150ms P95 latency for 10M+ vectors, which meets our requirements. Adding a dedicated vector DB introduces operational complexity, data synchronization challenges, and cost. The PRD explicitly defers dedicated vector DB to v2.0 if scale demands it. PostgreSQL's advantage is that vector queries can join with relational data (e.g., filter by `knowledge_base_id` and `workspace_id` within the same query).
  1050→  1050→
  1051→  1051→### DD-04: Dual-Token JWT, Not Single Token or Session
  1052→  1052→
  1053→  1053→**Decision:** Use two separate JWTs: RS256 access token (15min, in-memory) + HS256 refresh token (7d, HttpOnly cookie).
  1054→  1054→
  1055→  1055→**Rationale:**
  1056→  1056→
  1057→  1057→| Approach | Security | Performance | Complexity |
  1058→  1058→|----------|----------|-------------|------------|
  1059→  1059→| Single long-lived JWT | Low — compromised token valid for days | High — no refresh needed | Low |
  1060→  1060→| Server-side sessions | High — instant revocation | Low — DB lookup on every request | Medium |
  1061→  1061→| **Dual-token JWT** | **High** — short-lived access, rotation detects theft | **High** — access token validated without DB | **Medium** |
  1062→  1062→
  1063→  1063→RS256 for access tokens means validation requires only the public key (no DB lookup). HS256 for refresh tokens means revocation requires the shared secret + DB check. The rotation mechanism provides theft detection: if a previously-revoked token is presented, all sessions are terminated.
  1064→  1064→
  1065→  1065→### DD-05: UUID v7, Not UUID v4
  1066→  1066→
  1067→  1067→**Decision:** Use UUID v7 (time-sortable) as the default primary key for all entities.
  1068→  1068→
  1069→  1069→**Rationale:** UUID v7 combines a Unix timestamp (millisecond precision) with random bytes. This produces IDs that are globally unique (no coordination) and time-sortable (recent entities have higher IDs), which benefits B-tree index performance on append-heavy tables. UUID v4 is random, causing index fragmentation on time-ordered data. For high-throughput append-only tables (audit_logs, chat_messages, usage_logs), BIGINT auto-increment is used instead to avoid UUID storage overhead.
  1070→  1070→
  1071→  1071→### DD-06: Immutable Chat Messages
  1072→  1072→
  1073→  1073→**Decision:** Chat messages are never updated in place. Edits create new messages. Branching uses `parent_message_id` + `branch_index`.
  1074→  1074→
  1075→  1075→**Rationale:** Immutability eliminates an entire class of bugs (concurrent edits, lost updates, audit trail corruption). Branching enables exploring different AI response directions without losing the original thread. The `parent_message_id` + `branch_index` model reconstructs conversation history by walking up the tree. This design also simplifies billing (each message has a definitive token count that never changes) and audit logging (a complete, tamper-proof record of every interaction).
  1076→  1076→
  1077→  1077→### DD-07: Zod, Not class-validator
  1078→  1078→
  1079→  1079→**Decision:** Use Zod schemas for all input validation on both frontend and backend.
  1080→  1080→
  1081→  1081→**Rationale:** Zod schemas can be shared between frontend and backend via `packages/shared`, guaranteeing that the same validation rules apply on both sides. `class-validator` uses decorators and classes, which cannot be shared with a React frontend. Zod also provides superior TypeScript inference (`z.infer<typeof schema>`) and composable schema building (`.pick()`, `.omit()`, `.partial()`, `.merge()`).
  1082→  1082→
  1083→  1083→### DD-08: NestJS, Not Express or Fastify
  1084→  1084→
  1085→  1085→**Decision:** Build the backend API with NestJS.
  1086→  1086→
  1087→  1087→**Rationale:** NestJS provides a built-in DI container, module system, and guard/filter/interceptor pipeline that directly map to our hexagonal architecture requirements. Express requires manual assembly of middleware chains and has no DI or module system. Fastify is performant but lacks NestJS's structured module system. NestJS's decorators (`@Controller`, `@Get`, `@UseGuards`) provide declarative API definitions that align with our engineering rules (thin controllers, guard-based authorization).
  1088→  1088→
  1089→  1089→### DD-09: App Router, Not Pages Router
  1090→  1090→
  1091→  1091→**Decision:** Use Next.js App Router (`app/` directory) exclusively.
  1092→  1092→
  1093→  1093→**Rationale:** The App Router supports React Server Components, which allow page-level data fetching via `async/await` without client-side JavaScript. This reduces the client-side JavaScript bundle and improves Core Web Vitals (especially LCP and FID). Server Components are the default; the `'use client'` directive is added only where needed. The Pages Router does not support Server Components and is considered legacy by Next.js.
  1094→  1094→
  1095→  1095→### DD-10: Zustand, Not Redux
  1096→  1096→
  1097→  1097→**Decision:** Use Zustand for client-side state management.
  1098→  1098→
  1099→  1099→**Rationale:**
  1100→  1100→
  1101→  1101→| Factor | Zustand | Redux Toolkit |
  1102→  1102→|--------|---------|---------------|
  1103→  1103→| Boilerplate | Minimal — no actions, reducers, providers | Significant — slice, asyncThunk, configureStore |
  1104→  1104→| Bundle size | ~1 KB | ~11 KB |
  1105→  1105→| Learning curve | Low — hooks-based API | Medium — requires understanding thunks, selectors |
  1106→  1106→| TypeScript | First-class, simple | Good but verbose |
  1107→  1107→
  1108→  1108→Zustand's minimal API reduces boilerplate while providing the same capabilities (selectors, middleware for persistence, devtools integration). Since TanStack Query handles all server state, Zustand only manages simple UI state (theme, sidebar, selection), where its simplicity is a perfect fit.
  1109→  1109→
  1110→  1110→### DD-11: Feature-Based Folders, Not Type-Based
  1111→  1111→
  1112→  1112→**Decision:** Organize frontend code by feature (`features/chat/`), not by type (`components/`, `hooks/`, `stores/`).
  1113→  1113→
  1114→  1114→**Rationale:** Feature-based organization ensures that all code related to a domain concept lives in one place. A feature is self-contained and deletable — removing the `features/chat/` directory removes chat without affecting agents or knowledge. Type-based organization scatters related code across multiple directories, making it harder to understand, modify, and delete features. The engineering rules enforce this with the principle: "A feature must be deletable without affecting other features."
  1115→  1115→
  1116→  1116→### DD-12: CSS Logical Properties, Not Physical Properties
  1117→  1117→
  1118→  1118→**Decision:** Use `ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*` exclusively. Never use `left`, `right`, `ml-*`, `mr-*`.
  1119→  1119→
  1120→  1120→**Rationale:** HotHoosh is Persian-first and RTL-native. CSS logical properties automatically adapt to the document's `dir` attribute. When `dir="rtl"`, `margin-inline-start` maps to `margin-right`; when `dir="ltr"`, it maps to `margin-left`. Physical properties (`margin-left`) require manual RTL/LTR conditionals in every component. Logical properties make bidirectional support automatic and eliminates an entire class of RTL bugs.
  1121→  1121→
  1122→  1122→### DD-13: Solar Hijri Calendar
  1123→  1123→
  1124→  1124→**Decision:** Use Solar Hijri (شمسی) as the default calendar. Gregorian available as secondary.
  1125→  1125→
  1126→  1126→**Rationale:** HotHoosh targets Iranian enterprises. The Solar Hijri calendar is the official calendar of Iran, used for business operations, financial reporting, and legal documents. Displaying Gregorian dates as the default would be a localization failure. Day.js with the `jalaali-js` plugin provides Solar Hijri support with the same API as standard date handling.
  1127→  1127→
  1128→  1128→### DD-14: SSE, Not WebSocket for AI Streaming
  1129→  1129→
  1130→  1130→**Decision:** Use Server-Sent Events (`text/event-stream`) for all AI response streaming.
  1131→  1131→
  1132→  1132→**Rationale:**
  1133→  1133→
  1134→  1134→| Factor | SSE | WebSocket |
  1135→  1135→|--------|-----|-----------|
  1136→  1136→| Direction | Server → Client (unidirectional) | Bidirectional |
  1137→  1137→| Complexity | Simple — built on HTTP | Complex — handshake, framing, ping/pong |
  1138→  1138→| Proxy compatibility | Works through all proxies, CDNs, load balancers | Requires special proxy configuration (Upgrade header) |
  1139→  1139→| Reconnection | Browser auto-reconnects | Manual reconnection logic |
  1140→  1140→| HotHoosh need | Server pushes AI tokens to client | Client only sends messages via POST |
  1141→  1141→
  1142→  1142→AI response streaming is inherently unidirectional: the server generates tokens and the client displays them. The client sends messages via standard `POST` requests. There is no need for bidirectional communication. SSE is simpler, more robust, and works through all network infrastructure without special configuration.
  1143→  1143→
  1144→  1144→### DD-15: TypeORM, Not Prisma
  1145→  1145→
  1146→  1146→**Decision:** Use TypeORM as the ORM for NestJS.
  1147→  1147→
  1148→  1148→**Rationale:** TypeORM provides native PostgreSQL support including custom repository classes (essential for the repository pattern mandated by Engineering Rules §10.4.2), direct access to migration tooling, and fine-grained query control needed for complex operations (recursive CTEs for branch traversal, JSONB queries, pgvector operations). While Prisma offers a cleaner query API, TypeORM's custom repository support better aligns with our hexagonal architecture where repositories are the data access boundary.
  1149→  1149→
  1150→  1150→### DD-16: Invitation-Only Registration
  1151→  1151→
  1152→  1152→**Decision:** Users cannot self-register. All access is via organization invitation.
  1153→  1153→
  1154→  1154→**Rationale:** HotHoosh is an enterprise product, not a consumer SaaS. Open registration creates security risks (unauthorized access, spam accounts) and administrative burden. Invitation-only registration ensures that every user is explicitly authorized by an organization admin, tied to a specific role and organizational scope. This aligns with enterprise security requirements and Iranian enterprise governance practices.
  1155→  1155→
  1156→  1156→### DD-17: Hybrid Search (Vector + BM25), Not Vector Only
  1157→  1157→
  1158→  1158→**Decision:** Combine pgvector HNSW cosine similarity with PostgreSQL BM25 full-text search using Reciprocal Rank Fusion.
  1159→  1159→
  1160→  1160→**Rationale:** Vector search excels at semantic similarity but misses exact keyword matches. BM25 excels at keyword matching but misses semantic relationships. Hybrid search with RRF (k=60) combines the strengths of both. For Persian text specifically, exact keyword matching is critical because Persian morphology (prefixes, suffixes, zero-width non-joiners) can cause vector embeddings to miss matches that a full-text search catches easily.
  1161→  1161→
  1162→  1162→### DD-18: Bigint Auto-Increment for High-Throughput Tables
  1163→  1163→
  1164→  1164→**Decision:** Use BIGINT auto-increment (not UUID v7) for `audit_logs`, `usage_logs`, `chat_messages`, and `system_logs`.
  1165→  1165→
  1166→  1166→**Rationale:** UUID v7 is 128 bits (16 bytes) vs BIGINT which is 64 bits (8 bytes). On append-only tables that receive millions of inserts per month, halving the primary key size significantly reduces storage and index size. BIGINT auto-increment also provides optimal B-tree insert performance (sequential, no page splits). UUID v7 is used for all other tables where the benefits of global uniqueness and time-sortability outweigh the storage cost.
