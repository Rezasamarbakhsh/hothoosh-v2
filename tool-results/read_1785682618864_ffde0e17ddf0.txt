    30→## 1. Overview
    31→
    32→### 1.1 Architectural Philosophy
    33→
    34→HotHoosh's backend is built as a **NestJS modular monolith** with hexagonal module boundaries, as mandated by PRD Principle #15 and Engineering Rules §10.4.2. This means the entire backend runs as a single deployable unit, but internal module boundaries are strictly enforced as if each module were a separate microservice. Modules communicate exclusively through well-defined public APIs (injected services and domain events), never through shared mutable state or direct internal imports across module boundaries.
    35→
    36→The choice of modular monolith over microservices is deliberate and rooted in the team's operational capacity and the product's current scale requirements. A microservices architecture introduces distributed system complexity—network partitions, eventual consistency, distributed tracing, service mesh overhead—that is unnecessary for HotHoosh's v1.0 deployment target of ~100 organizations and ~10,000 concurrent users. The modular monolith preserves the ability to extract modules into separate services in the future (v2.0+) because hexagonal boundaries ensure low coupling and high cohesion within each domain module.
    37→
    38→### 1.2 Why Not Microservices
    39→
    40→| Factor | Modular Monolith | Microservices |
    41→|--------|-----------------|---------------|
    42→| Development velocity | Single codebase, single build, single deploy | Multiple codebases, independent builds |
    43→| Operational complexity | Single process to monitor, scale, and debug | Multiple processes, service discovery, load balancing |
    44→| Data consistency | Single PostgreSQL transaction spans all modules | Distributed transactions (Saga) or eventual consistency |
    45→| Team size | 3–8 developers (current phase) | Requires 10+ developers for independent service ownership |
    46→| Latency | In-process communication (nanoseconds) | Network communication (milliseconds) |
    47→| Cost | Single instance to run | Multiple instances + infrastructure overhead |
    48→| Future extraction | Hexagonal boundaries allow clean extraction | Already extracted |
    49→
    50→Per Engineering Rules §10.4.2, the modular monolith enforces the same architectural discipline as microservices at the code level, without paying the operational tax. Each domain module has a clear boundary defined by its controller, service, and repository layers. Internal implementation details are never exported. If a module needs to be extracted into a separate service in the future, the hexagonal boundary makes this a mechanical process rather than a rewrite.
    51→
    52→### 1.3 Technology Stack
    53→
    54→| Layer | Technology | Rationale |
    55→|-------|-----------|-----------|
    56→| Runtime | Node.js 20+ LTS | Non-blocking I/O for SSE streaming and concurrent AI requests |
    57→| Framework | NestJS 10+ | DI container, module system, guard/filter/interceptor pipeline |
    58→| ORM | TypeORM | PostgreSQL-native, custom repository support, migration tooling |
    59→| Database | PostgreSQL 16+ | pgvector, RLS, JSONB, partitioned tables, full-text search |
    60→| Cache/Queue | Redis 7+ | BullMQ job queues, session store, rate limiting, caching |
    61→| Validation | Zod | Shared schemas between frontend and backend (§10.1.3) |
    62→| File Storage | S3-compatible (MinIO) | Document storage for knowledge bases |
    63→| Email | Nodemailer (SMTP) | Transactional emails for invitations, password resets |
    64→| Streaming | Server-Sent Events (SSE) | One-directional real-time AI response streaming |

   365→## 3. Domain Event System
   366→
   367→### 3.1 Architecture
   368→
   369→The domain event system is the backbone of inter-module communication in HotHoosh. Per Engineering Rules §10.4.2, modules never import each other's services directly for cross-domain operations. Instead, when a domain operation produces side effects that concern other modules, it emits a domain event. Interested modules register handlers that react to these events asynchronously.
   370→
   371→The event system is implemented as an **in-memory event bus** (`DomainEventBus`) backed by Redis for reliability. Events are published synchronously within the current transaction scope but dispatched to handlers asynchronously after the transaction commits (to avoid handlers operating on uncommitted data). A **transactional outbox** pattern ensures no events are lost if the application crashes between transaction commit and handler dispatch.
   372→
   373→### 3.2 Event Bus Implementation
   374→
   375→```typescript
   376→// Simplified interface — actual implementation uses NestJS CQRS EventBus
   377→interface DomainEventBus {
   378→  publish(event: DomainEvent): Promise<void>;
   379→  subscribe(eventType: string, handler: EventHandler): void;
   380→  unsubscribe(eventType: string, handler: EventHandler): void;
   381→}
   382→
   383→interface DomainEvent {
   384→  readonly eventId: string;       // UUID v7
   385→  readonly eventType: string;      // Discriminator for the event type
   386→  readonly timestamp: Date;       // Event creation time
   387→  readonly actorId: string;       // User who triggered the event
   388→  readonly payload: unknown;      // Event-specific data
   389→  readonly correlationId: string; // Request correlation ID
   390→}
   391→```
   392→

   451→### 3.5 Transactional Outbox Pattern
   452→
   453→To guarantee that every domain state change is accompanied by its corresponding event (no lost events), HotHoosh uses the **transactional outbox** pattern:
   454→
   455→1. When a service method performs a write operation (e.g., `UsersService.createUser`), it opens a database transaction.
   456→2. Within the same transaction, it writes the domain state change AND inserts an outbox record into an `outbox_events` table.
   457→3. The transaction commits atomically — both the state change and the event record are persisted together.
   458→4. A background worker (BullMQ processor) polls the `outbox_events` table for unprocessed events, dispatches them to the event bus, and marks them as processed.
   459→5. If the application crashes between steps 4 and 5, the outbox records remain unprocessed and are picked up on restart.
   460→
   461→The `outbox_events` table uses BIGINT auto-increment for throughput, with columns for `event_type`, `payload` (JSONB), `created_at`, `processed_at`, and `correlation_id`.

   465→## 4. Authentication Flow
   466→
   467→### 4.1 Overview
   468→
   469→HotHoosh uses a **dual-token JWT** authentication system as specified in PRD FR-AUTH-002 and Engineering Rules §10.6.1. Access tokens use RS256 asymmetric signing for short-lived authentication (15 minutes, stored in memory only). Refresh tokens use HS256 symmetric signing for longer-lived session persistence (7 days, stored in HttpOnly cookies). This separation ensures that access tokens can be validated without database lookups (RS256 public key), while refresh tokens require server-side validation (HS256 shared secret + database lookup for revocation).
   470→
   471→### 4.2 Registration Flow
   472→
   473→Users cannot self-register. Registration is invitation-only (PRD FR-AUTH-001). The flow is:
   474→
   475→1. **Invitation Creation**: An organization admin sends an invitation via `POST /v1/organizations/:orgId/invitations`. The `user_invitations` table records the target email, role, and optional company/brand/workspace scope. A SHA-256 hashed invitation token is stored. An email is dispatched with a secure link containing the raw token.
   476→
   477→2. **Invitation Acceptance**: The invitee clicks the link, which navigates to the registration page with the token. They provide display name, password (validated against policy: min 8 chars, uppercase, lowercase, number, special character), and phone number (optional).
   478→
   479→3. **Registration**: `POST /v1/auth/register` accepts the invitation token, user data. The service:
   480→   - Validates the token against `user_invitations.token_hash` and checks `status = pending` and `expires_at > NOW()`.
   481→   - Hashes the password with Argon2id (OWASP parameters: memory=64MB, time=3, parallelism=4).
   482→   - Creates the `users` record with `status = active`, `email_verified_at = NOW()`.
   483→   - Creates a `workspace_users` record if the invitation targets a specific workspace.
   484→   - Marks the invitation as `status = accepted`, `accepted_at = NOW()`.
   485→   - Emits `UserRegisteredEvent`.
   486→
   487→4. **Auto-Login**: After registration, the system automatically triggers the login flow (step 4.3) to issue tokens without requiring the user to separately authenticate.
   488→
   489→### 4.3 Login Flow

   541→
   542→### 4.4 Token Refresh Flow
   543→
   544→1. Client detects access token expiration (via 401 response or proactive check).
   545→2. Client sends `POST /v1/auth/refresh` with no body — the refresh token is read from the HttpOnly cookie.
   546→3. Server validates the refresh token signature (HS256), extracts `userId` and `familyId`.
   547→4. Server looks up the `refresh_tokens` record by `token_hash` and verifies:
   548→   - `expires_at > NOW()`
   549→   - `revoked_at IS NULL`
   550→5. **Token rotation**: Server invalidates the old refresh token (`revoked_at = NOW()`) and creates a new refresh token with a new hash but the same `family_id`. The new token is set as a new HttpOnly cookie.
   551→6. **Theft detection**: If a previously-revoked refresh token is presented (same `family_id`, different token hash, but the old token's `revoked_at IS NOT NULL`), the server revokes ALL tokens in that `family_id` (all sessions terminated). This detects token theft.
   552→7. Server generates a new RS256 access token and returns it.
   553→8. Emits `UserLoggedInEvent` (with `isRefresh: true`).
   554→
   555→### 4.5 Impersonation Flow
   556→
   557→Super admins can impersonate any user (PRD FR-AUTH-007). This flow is critical for support and debugging.
   558→
   559→1. Super admin sends `POST /v1/auth/impersonate` with `{ targetUserId }`.
   560→2. The `AuthService` verifies the actor has `super_admin` role.
   561→3. An audit log entry is created with both `actor_id` (admin) and target user ID. The `description` includes "Impersonation started" in Persian.
   562→4. An RS256 access token is generated for the target user, but with a custom claim `impersonatedBy: adminUserId`.
   563→5. The access token has a reduced expiry (30 minutes instead of 15 minutes) to limit impersonation window.
   564→6. All actions taken during the impersonated session are logged with both the impersonator and target user IDs.
   565→7. The `ImpersonationGuard` checks the custom claim on every request and adds audit metadata.
   566→
   567→### 4.6 Password Reset Flow
   568→
   569→1. User requests reset via `POST /v1/auth/forgot-password` with `{ email }`.
   570→2. Rate limit: 3 requests per hour per email.
   571→3. Server generates a reset token (128-bit random), stores its SHA-256 hash in a Redis key with 1-hour TTL.
   572→4. Email dispatched with reset link containing raw token.
   573→5. User submits `POST /v1/auth/reset-password` with `{ token, newPassword }`.
   574→6. Server validates token against Redis, validates new password against policy, hashes with Argon2id, updates `password_hash`.
   575→7. All existing refresh tokens for the user are revoked (all `family_id` entries).
   576→8. Emits `UserUpdatedEvent`.

   580→## 5. Authorization Architecture
   581→
   582→### 5.1 Three-Layer RBAC
   583→
   584→Per PRD FR-AUTH-003 and Engineering Rules §10.6.2, HotHoosh implements a three-layer role-based access control system:
   585→
   586→| Layer | Source | Scope | Example |
   587→|-------|--------|-------|---------|
   588→| **Layer 1: Organization Role** | `roles` table where `level = 'org'` or `level = 'system'` | Organization-wide | `super_admin`, `org_admin`, `org_member` |
   589→| **Layer 2: Workspace Role** | `workspace_users.role_id` → `roles` table where `level = 'workspace'` | Workspace-specific | `workspace_admin`, `workspace_member`, `workspace_viewer` |
   590→| **Layer 3: Resource Permissions** | `roles.permissions` JSONB array | Individual resource | `agents:create`, `knowledge:delete`, `billing:read` |
   591→
   592→All three layers are checked for every authenticated request via the guard chain (§5.3). The user's effective permissions are the **union** of all permissions from all roles they hold across the hierarchy (PRD FR-TENANT-003).
   593→
   594→### 5.2 Permission Resolution Algorithm
   595→
   596→The permission resolution process follows this sequence:
   597→
   598→1. **Identify the user's roles**: Query `workspace_users` for the user's role in the current workspace context. Query `roles` for the organization-level role (via user's organization membership).
   599→2. **Collect all permission arrays**: For each role, extract the `permissions` JSONB array from the `roles` table. System roles (like `super_admin`) may have `'*'` indicating all permissions.
   600→3. **Union permissions**: Merge all permission arrays, deduplicate.
   601→4. **Check against required permission**: The controller/endpoint defines the required permission (e.g., `agents:create`). If the union set includes this permission, access is granted.
   602→5. **Super admin bypass**: If the user holds a role with `'*'` in permissions, all checks pass immediately.
   603→
   604→```typescript
   605→// Simplified permission resolution
   606→async resolvePermissions(userId: UserId, workspaceId: WorkspaceId): Promise<Set<string>> {
   607→  const workspaceRole = await this.workspaceUsersRepo.findOne({
   608→    where: { userId, workspaceId },
   609→    relations: ['role'],
   610→  });
   611→  const orgRole = await this.getUserOrgRole(userId, workspaceId);
   612→
   613→  const permissions = new Set<string>();
   614→  if (workspaceRole?.role.permissions) {
   615→    workspaceRole.role.permissions.forEach(p => permissions.add(p));
   616→  }
   617→  if (orgRole?.permissions) {
   618→    orgRole.permissions.forEach(p => permissions.add(p));
   619→  }
   620→
   621→  // Super admin wildcard
   622→  if (permissions.has('*')) {
   623→    return ALL_PERMISSIONS;
   624→  }
   625→
   626→  return permissions;
   627→}
   628→```
   629→
   630→### 5.3 Guard Chain
   631→
   632→Authorization is enforced via NestJS guards (§10.1.3), not manual checks in controllers. The guard chain executes in this order:
   633→
   634→| Order | Guard | Purpose | Failure Response |
   635→|-------|-------|---------|-----------------|
   636→| 1 | `JwtAuthGuard` | Validates RS256 access token, extracts `userId` from claims | `401 Unauthorized` |
   637→| 2 | `TenantScopeGuard` | Validates that the user has access to the requested tenant (org/company/brand/workspace) | `403 Forbidden` |
   638→| 3 | `RolesGuard` | Checks if the user's resolved permissions include the endpoint's required permission | `403 Forbidden` |
   639→| 4 | `ImpersonationGuard` | Logs impersonation context and enforces impersonation limitations | `403 Forbidden` |
   640→
   641→Each guard uses decorators to declare its requirements:
   642→
   643→```typescript
   644→@Controller('agents')
   645→@UseGuards(JwtAuthGuard, TenantScopeGuard, RolesGuard)
   646→export class AgentsController {
   647→  @Post()
   648→  @RequirePermissions('agents:create')
   649→  async create(@CurrentUser() user: UserPayload, @Body() dto: CreateAgentDto) {
   650→    // ...
   651→  }
   652→}
   653→```
   654→
   655→### 5.4 PostgreSQL RLS Integration
   656→
   657→Per PRD FR-TENANT-004, data isolation is enforced at the database level via PostgreSQL Row-Level Security (RLS). Even if application code has a bug that bypasses permission checks, RLS prevents cross-tenant data access. RLS policies are defined on all tenant-scoped tables.
   658→
   659→RLS is implemented via **session variables** that NestJS sets at connection initialization. When a request arrives, the authentication middleware extracts the user's tenant context and sets PostgreSQL session variables:
   660→
   661→```sql
   662→-- Set at connection initialization
   663→SET LOCAL app.current_user_id = 'uuid';
   664→SET LOCAL app.current_org_id = 'uuid';
   665→SET LOCAL app.is_super_admin = false;
   666→
   667→-- RLS policy example on the agents table
   668→CREATE POLICY agents_workspace_isolation ON agents
   669→  USING (
   670→    workspace_id IN (
   671→      SELECT w.id FROM workspaces w
   672→      JOIN brands b ON b.id = w.brand_id
   673→      JOIN companies c ON c.id = b.company_id
   674→      JOIN organizations o ON o.id = c.organization_id
   675→      WHERE o.id = current_setting('app.current_org_id', true)::uuid
   676→      OR current_setting('app.is_super_admin', true)::boolean = true
   677→    )
   678→  );
   679→```
   680→
   681→The TypeORM connection pool is configured to run the `SET LOCAL` commands on each connection checkout (via a connection initialization callback). This ensures RLS context is always correct, even with connection pooling.
   682→
   683→### 5.5 Admin Panel Access Control
   684→
   685→Per Admin-Panel §9.1.3, the admin panel uses a dedicated permission namespace: `admin:*`. Access levels determine what a user can see and do:
   686→
   687→| Role | Scope | Permission Example |
   688→|------|-------|--------------------|
   689→| **Super Admin** | All organizations | `admin:*` (wildcard) |
   690→| **Org Admin** | Own org + descendants | `admin:users:create`, `admin:billing:read` |
   691→| **Company Admin** | Own company + descendants | `admin:users:read`, `admin:agents:create` |
   692→| **Brand Admin** | Own brand + workspaces | `admin:agents:read`, `admin:knowledge:manage` |
   693→| **Workspace Admin** | Own workspace | `admin:agents:manage`, `admin:knowledge:manage` |

   823→| 1 | `token` | server → client | `{ content: string, index: number }` | Single token or word chunk in the AI response stream. `index` is the cumulative token index. |
   824→| 2 | `message_start` | server → client | `{ messageId: bigint, modelId: string, sessionId: string }` | Emitted when the AI response begins. Contains the message ID allocated before streaming starts. |
   825→| 3 | `message_delta` | server → client | `{ content: string, role: 'assistant' }` | Cumulative message content delta. Superset of `token` — used for UI rendering. |
   826→| 4 | `message_complete` | server → client | `{ messageId: bigint, inputTokens: number, outputTokens: number, latencyMs: number, finishReason: string }` | Emitted when the full response is complete. Contains token usage and latency. |
   827→| 5 | `tool_call` | server → client | `{ id: string, name: string, arguments: object }` | Emitted when the AI requests a tool invocation. |
   828→| 6 | `tool_result` | server → client | `{ id: string, name: string, result: object, status: 'success' \| 'error' }` | Emitted after tool execution completes. |
   829→| 7 | `error` | server → client | `{ code: string, message: string }` | Emitted when an error occurs during streaming. Client should display error and allow retry. |
   830→| 8 | `heartbeat` | server → client | `{ timestamp: string }` | Keep-alive event sent every 15 seconds. Prevents connection timeout. |
   831→
   832→**SSE connection lifecycle:**
   833→1. Client opens SSE connection to `GET /v1/chats/:sessionId/stream`.
   834→2. Server sends `message_start` event with allocated message ID.
   835→3. Server streams `token` / `message_delta` events as AI generates response.
   836→4. If tool calls are needed, `tool_call` events are emitted, then `tool_result` after execution, then streaming resumes.
   837→5. When complete, `message_complete` is sent with usage metadata.
   838→6. On error, `error` event is sent and connection is closed.
   839→7. Heartbeat events prevent proxy/load-balancer timeout.

   843→## 7. LLM Router Engine
   844→
   845→### 7.1 Overview
   846→
   847→The LLM Router is the central intelligence for routing AI requests to the optimal provider and model. It implements the 5-step routing pipeline defined in PRD FR-PROVIDER-002 and handles provider health monitoring, automatic failover, and cost optimization. The router is a stateless service that reads provider and model configuration from the database (`api_providers`, `models`, `model_routing_rules`) and caches it in Redis for performance.
   848→
   849→### 7.2 Five-Step Routing Pipeline
   850→
   851→Each AI request passes through five sequential steps, each of which may narrow the candidate model pool:
   852→
   853→**Step 1: Model Requirement Filtering**
   854→- The agent or request specifies required capabilities (e.g., `supports_function_calling`, `supports_vision`, `supports_persian`).
   855→- The router filters all enabled models (`models.is_enabled = true`) to only those matching the requirement.
   856→- If the agent specifies a `model_id` directly, this step validates that the model is enabled and has the required capabilities.
   857→- Example: If the request requires function calling, only models with `supports_function_calling = true` are considered.
   858→
   859→**Step 2: User Tier Filtering**
   860→- The user's subscription plan (Free, Pro, Enterprise) defines which models are available.
   861→- Free plans may be restricted to lower-cost models. Enterprise plans have access to all models.
   862→- The router queries the `plans.limits` JSONB field for `custom_models: boolean` to determine if custom/premium models are accessible.
   863→- Models tagged with `supports_persian = true` are prioritized for Persian-language requests.
   864→
   865→**Step 3: Workspace Configuration**
   866→- The workspace's `allowed_model_ids` array (on the `workspaces` table) restricts available models if not null.
   867→- If the workspace has configured specific model restrictions, only those models are considered.
   868→- Workspace-level model preferences override plan-level defaults.
   869→
   870→**Step 4: Cost Optimization**
   871→- Among remaining candidates, the router applies cost optimization:
   872→  - Sorts candidates by total cost per request: `(input_tokens × input_cost_per_1m) + (output_tokens × output_cost_per_1m)`.
   873→  - For requests where quality is critical (high-stakes interactions), the router selects the best model regardless of cost.
   874→  - For routine requests, the router prefers the cheapest model that meets all requirements.
   875→  - Workspace-level `token_budget_monthly` is checked against current consumption.
   876→
   877→**Step 5: Health-Based Fallback**
   878→- The final step selects the optimal model based on provider health:
   879→  - Health statuses: `healthy`, `degraded`, `down`, `unknown` (from `api_providers.health_status`).
   880→  - Prefer `healthy` providers. Use `degraded` providers only if no `healthy` alternative exists. Never use `down` providers.
   881→  - If the primary model (from Step 4) is on a `degraded` provider, the router selects the next-best model on a `healthy` provider.
   882→  - If all candidates are `down`, the router throws `AllProvidersDownException`.
   883→
   884→### 7.3 Provider Health Monitoring
   885→
   886→Each AI provider has continuous health monitoring:
   887→
   888→| Metric | Source | Threshold | Status Impact |
   889→|--------|--------|-----------|---------------|
   890→| **Latency** | Measured per-request (P95) | < 2000ms = healthy, 2000–5000ms = degraded, > 5000ms = down | Direct |
   891→| **Error rate** | Tracked per minute (5xx + timeouts) | < 5% = healthy, 5–20% = degraded, > 20% = down | Direct |
   892→| **Uptime** | Tracked over 30-minute window | > 99% = healthy, 95–99% = degraded, < 95% = down | Direct |
   893→| **Last check** | Timestamp from `api_providers.last_health_check_at` | Stale (> 5 minutes) = unknown | Forces recheck |
   894→
   895→Health data is stored in Redis with 5-second resolution. A background BullMQ job (`health-check` queue) pings each active provider every 30 seconds by sending a minimal request (e.g., 1 token). The `api_providers` table is updated asynchronously with the latest health status.
   896→
   897→### 7.4 Failover Logic
   898→
   899→When a provider fails during an active request, the failover sequence is:
   900→
   901→1. **Retry with backoff**: If the error is retryable (HTTP 429, 500, 502, 503 — per `api_providers.retryable_status_codes`), retry with exponential backoff (base: `backoff_multiplier = 2.0`, max retries: `max_retries = 3`).
   902→2. **Switch provider**: If all retries fail, the router selects the next-best model from a different provider.
   903→3. **Circuit breaker**: If a provider's error rate exceeds 20%, a circuit breaker opens. All requests are immediately routed to alternative providers. The circuit breaker resets after 60 seconds of no errors (half-open state).
   904→4. **Notify admin**: If all providers for a model are down, emit `AllProvidersDownEvent` which triggers an admin notification.
   905→5. **Graceful degradation**: If no model can handle the request, return a degraded response: "این هوش مصنوعی در حال حاضر در دسترس نیست. لطفاً بعداً تلاش کنید." (This AI is currently unavailable. Please try again later.)
   906→
   907→### 7.5 Model Selection Algorithm
   908→
   909→```typescript
   910→async route(request: RoutingRequest): Promise<RoutingResult> {
   911→  // Step 1: Model requirement filtering
   912→  let candidates = await this.filterByRequirements(request.requirements);
   913→
   914→  // Step 2: User tier filtering
   915→  candidates = this.filterByUserTier(candidates, request.user.tier);
   916→
   917→  // Step 3: Workspace configuration
   918→  candidates = this.filterByWorkspace(candidates, request.workspace.allowedModelIds);
   919→
   920→  // Step 4: Cost optimization
   921→  candidates = this.optimizeByCost(candidates, request.estimatedTokens);
   922→
   923→  // Step 5: Health-based fallback
   924→  const result = this.selectByHealth(candidates);
   925→  if (!result) {
   926→    throw new AllProvidersDownException(request.requirements);
   927→  }
   928→
   929→  return result;
   930→}
   931→```

   935→## 8. Context Engine
   936→
   937→### 8.1 Overview
   938→
   939→The Context Engine is responsible for assembling the complete context window that is sent to the LLM for each AI request. It manages the token budget allocation across all context sources and implements the priority reduction algorithm defined in PRD FR-CHAT-004. The context engine ensures that the most important information is always included, and less critical content is progressively truncated to fit within the model's context window limit.
   940→
   941→### 8.2 Token Budget Allocation
   942→
   943→The total context budget is the model's `context_window` (from the `models` table) minus the `max_output_tokens` (from the agent's configuration). The remaining space is allocated to context sources by priority:
   944→
   945→| Priority | Source | Allocation | Description |
   946→|----------|--------|-----------|-------------|
   947→| **1 (Highest)** | Knowledge (RAG) | Up to 40% | Retrieved knowledge chunks from bound knowledge bases. Essential for accurate, grounded responses. |
   948→| **2** | Conversation History | Up to 30% | Previous messages in the current branch. Recent messages have higher priority than older ones. |
   949→| **3** | Memory Packs | Up to 20% | Resolved memory content from bound memory packs. Hierarchical assembly (workspace → brand → company → org). |
   950→| **4 (Lowest)** | Tool Definitions | Up to 10% | JSON Schema definitions for tools available to the agent. Only included if tools are bound. |
   951→
   952→### 8.3 Priority Reduction Algorithm
   953→
   954→When the total context exceeds the available budget, the engine applies reduction in reverse priority order:
   955→
   956→1. **Reserve minimums**: Each source has a minimum allocation that is never reduced:
   957→   - Knowledge: minimum 10% (at least some grounding)
   958→   - History: minimum 5% (at least the last 2–3 messages)
   959→   - Memory: minimum 5% (core memory if present)
   960→   - Tools: minimum 2% (tool names even if schemas are truncated)
   961→
   962→2. **Reduce lowest priority first**: Tool definitions are reduced first. If tool schemas exceed the budget, only tool names and descriptions are included (no full JSON Schema). If still over budget, remove tools with lowest usage frequency.
   963→
   964→3. **Reduce memory**: If still over budget, truncate memory pack content. Remove less relevant memory packs first (based on recency and relevance scoring).
   965→
   966→4. **Reduce history**: If still over budget, apply a sliding window — remove the oldest messages first. The system prompt and the most recent 2 messages are always preserved.
   967→
   968→5. **Reduce knowledge**: As a last resort, reduce the number of knowledge chunks retrieved. Remove chunks with the lowest similarity score. The top-3 chunks are always preserved if RAG is enabled.
   969→
   970→### 8.4 Context Assembly Pipeline
   971→
   972→```
   973→1. Determine model context window (from models.context_window)
   974→2. Subtract max_output_tokens (from agents.max_tokens)
   975→3. = Available budget
   976→
   977→4. Resolve memory packs (MemoryEngine.assembleHierarchicalMemory)
   978→5. Retrieve knowledge chunks (RAGEngine.retrieve)
   979→6. Load conversation history (ChatService.getBranchMessages)
   980→7. Load tool definitions (ToolEngine.getToolDefinitions)
   981→
   982→8. Estimate token counts for each source
   983→9. Check if total exceeds budget
   984→
   985→10. If exceeds: apply priority reduction algorithm
   986→11. Assemble final context array:
   987→    - System prompt (from agent.system_prompt)
   988→    - Memory context (injected into system prompt)
   989→    - Knowledge context (injected as assistant-reference blocks)
   990→    - Conversation history (user/assistant message pairs)
   991→    - Tool definitions (as function-calling schema)
   992→    - Current user message
   993→```
   994→
   995→### 8.5 Token Estimation
   996→
   997→Token counts are estimated using the model's tokenizer (cl100k_base for OpenAI-compatible, character-based approximation for others). The estimation service caches frequent patterns to avoid repeated tokenization overhead. For accurate billing, the actual token count from the LLM response (`usage` field) is recorded in `chat_messages.input_tokens` and `chat_messages.output_tokens`.

  1001→## 9. RAG Engine
  1002→
  1003→### 9.1 Overview
  1004→
  1005→The RAG Engine implements the complete Retrieval-Augmented Generation pipeline for HotHoosh. It handles document processing (from upload to indexed chunks), retrieval (from query to ranked results), and Persian NLP optimization. The engine integrates with pgvector for vector similarity search, PostgreSQL full-text search for BM25 ranking, and supports hybrid search combining both approaches (PRD FR-KNOW-005).
  1006→
  1007→### 9.2 Document Processing Pipeline
  1008→
  1009→The processing pipeline runs asynchronously via BullMQ (see §14) and progresses through 6 stages:
  1010→
  1011→```
  1012→Upload → Extract → Normalize → Chunk → Embed → Index
  1013→```
  1014→
  1015→**Stage 1: Upload**
  1016→- File received via `POST /v1/knowledge-bases/:kbId/documents`.
  1017→- File validated by magic bytes (not extension): PDF, DOCX, TXT, MD, HTML, CSV, JSON.
  1018→- File stored in S3 under key `knowledge/{workspaceId}/{kbId}/{uuid}/{filename}`.
  1019→- `knowledge_documents` record created with `processing_status = 'uploaded'`.
  1020→- Size validated against workspace storage limit.
  1021→- Content hash (SHA-256) computed for deduplication.
  1022→
  1023→**Stage 2: Extract**
  1024→- File downloaded from S3.
  1025→- Content extracted based on file type:
  1026→  - PDF: pdf-parse or pdfjs
  1027→  - DOCX: mammoth.js
  1028→  - TXT/MD/HTML/CSV/JSON: direct text extraction
  1029→- Extracted text stored in a temporary Redis key for the next stage.
  1030→- Status updated to `extracting`.
  1031→
  1032→**Stage 3: Normalize (Persian NLP)**
  1033→- If `persian_nlp_enabled = true` on the knowledge base:
  1034→  - **Character normalization**: Arabic Yeh (ي) → Persian Yeh (ی), Arabic Kaf (ك) → Persian Kaf (ک), normalize zero-width non-joiners, normalize multiple spaces.
  1035→  - **Direction handling**: Ensure text is in logical order (not visual).
  1036→  - **Stop-word removal**: Persian stop words (و، از، به، در، که، این، آن، را، با، برای، etc.) are identified but NOT removed from the stored content — they are only excluded from embedding generation to improve vector quality.
  1037→- Status updated to `normalizing` (part of the chunking stage).
  1038→
  1039→**Stage 4: Chunk**
  1040→- The chunking strategy is determined by `knowledge_bases.chunking_strategy`:
  1041→
  1042→| Strategy | Implementation | Best For |
  1043→|-----------|--------------|----------|
  1044→| `fixed_size` | Split text into `chunk_size` tokens with `chunk_overlap` overlap | General documents, uniform content |
  1045→| `semantic` | Embed paragraphs, cluster by similarity, split at cluster boundaries | Conceptually dense content |
  1046→| `paragraph` | Split at paragraph boundaries (double newline), respect `chunk_size` max | Well-structured text |
  1047→| `heading_based` | Split at heading boundaries (Markdown/HTML headers), group content under each heading | Technical docs, wikis |
  1048→
  1049→- Default: `fixed_size` with `chunk_size = 512` tokens and `chunk_overlap = 100` tokens.
  1050→- Each chunk is stored in `knowledge_chunks` with `content`, `token_count`, `chunk_index`, and `metadata` (headings, page numbers).
  1051→- Status updated to `chunking`.
  1052→
  1053→**Stage 5: Embed**
  1054→- Each chunk's content (with Persian stop words optionally removed) is sent to the embedding model.
  1055→- The embedding model is specified by `knowledge_bases.embedding_model_id` → `models` table where `model_type = 'embedding'`.
  1056→- Embeddings are generated via the LLM Router (which selects the appropriate provider).
  1057→- Embedding vectors stored in `knowledge_embeddings` table with the chunk's UUID as PK and a `vector(1536)` column (dimension depends on the embedding model).
  1058→- The HNSW index (`idx_knowledge_embeddings_vector`) is maintained automatically by pgvector.
  1059→
  1060→**Stage 6: Index**
  1061→- Full-text search index is built using PostgreSQL's `to_tsvector('persian', content)` GIN index.
  1062→- Trigram index (`gin_trgm_ops`) is built for fuzzy text search.
  1063→- Document status updated to `indexed`, then `ready`.
  1064→- `knowledge_bases.document_count`, `chunk_count`, `total_size_bytes`, `last_processed_at`, `processing_status` updated.
  1065→- `DocumentProcessingCompleteEvent` emitted.
  1066→
  1067→### 9.3 Retrieval Pipeline
  1068→
  1069→When a user sends a message in a chat session with an agent that has bound knowledge bases:
  1070→
  1071→```
  1072→Query → Embed → Vector Search → BM25 Search → Merge → Rerank → Inject
  1073→```
  1074→
  1075→1. **Query embedding**: The user's message is embedded using the same embedding model as the knowledge base. Persian normalization is applied.
  1076→
  1077→2. **Vector search**: pgvector HNSW index is queried with cosine similarity:
  1078→   ```sql
  1079→   SELECT kc.id, kc.content, ke.embedding <=> $query_vector AS distance
  1080→   FROM knowledge_embeddings ke
  1081→   JOIN knowledge_chunks kc ON kc.id = ke.chunk_id
  1082→   WHERE ke.model_id = $modelId
  1083→     AND kc.knowledge_base_id IN ($boundKbIds)
  1084→   ORDER BY ke.embedding <=> $query_vector
  1085→   LIMIT $topK;
  1086→   ```
  1087→
  1088→3. **BM25 search**: PostgreSQL full-text search with Persian configuration:
  1089→   ```sql
  1090→   SELECT kc.id, kc.content, ts_rank(to_tsvector('persian', kc.content), plainto_tsquery('persian', $query)) AS rank
  1091→   FROM knowledge_chunks kc
  1092→   WHERE kc.knowledge_base_id IN ($boundKbIds)
  1093→     AND to_tsvector('persian', kc.content) @@ plainto_tsquery('persian', $query)
  1094→   ORDER BY rank DESC
  1095→   LIMIT $topK;
  1096→   ```
  1097→
  1098→4. **Merge**: Results from vector search and BM25 search are merged using Reciprocal Rank Fusion (RRF):
  1099→   ```
  1100→   RRF_score(d) = Σ 1 / (k + rank_i(d))
  1101→   ```
  1102→   where `k = 60` and `rank_i` is the rank of document `d` in search method `i`. The top-10 results after merging are selected.
  1103→
  1104→5. **Rerank**: The merged results are optionally reranked using a cross-encoder model (if available) or by a simpler scoring function that considers:
  1105→   - Chunk recency (newer documents score slightly higher)
  1106→   - Chunk position in document (beginning and end of documents score higher)
  1107→   - Similarity score threshold from `agent_knowledge.relevance_threshold` (default 0.7)
  1108→
  1109→6. **Inject**: The final chunks are injected into the context window by the Context Engine (§8) as knowledge context blocks with source references.
  1110→
  1111→### 9.4 Persian NLP Optimization
  1112→
  1113→Persian text requires special handling due to its morphological complexity, right-to-left script, and the coexistence of Arabic and Persian characters. The RAG engine provides these Persian-specific optimizations:
  1114→
  1115→- **Character normalization**: Mapping between Arabic and Persian character variants (ی/ي, ک/ك, ه/ة). This ensures consistent embeddings for visually similar text.
  1116→- **Zero-width non-joiner handling**: Persian uses ZWNJ (U+200C) for compound word separation. The normalizer standardizes ZWNJ usage.
  1117→- **Number normalization**: Western Arabic numerals (0-9) are normalized to Persian numerals (۰-۹) or vice versa based on the knowledge base configuration, ensuring consistent matching.
  1118→- **Stop-word handling**: A curated list of ~200 Persian stop words is maintained. These words are excluded from embedding generation to improve vector quality (embedding "و" or "از" adds no semantic signal).
  1119→- **Persian FTS configuration**: PostgreSQL's full-text search is configured with a Persian text search configuration that handles Persian morphology, prefix matching, and stemmer behavior.

  1123→## 10. Memory Engine
  1124→
  1125→### 10.1 Overview
  1126→
  1127→The Memory Engine manages the resolution, assembly, and injection of memory packs into the AI context window. Memory packs are reusable bundles of context that persist across chat sessions (PRD FR-MEM-001). The engine resolves which memory packs are relevant to a given request, assembles hierarchical memory from multiple organizational levels, and provides the formatted memory content to the Context Engine for injection.
  1128→
  1129→### 10.2 Memory Pack Types
  1130→
  1131→Per PRD FR-MEM-002, four types of memory packs exist:
  1132→
  1133→| Type | Purpose | Example Content |
  1134→|------|---------|----------------|
  1135→| `context` | Custom context for specific use cases | "This user is working on a marketing campaign for product X. Their deadline is September 2025." |
  1136→| `preference` | User or team preferences | "The user prefers concise responses in Persian. Use bullet points for lists. Avoid technical jargon." |
  1137→| `knowledge` | Summarized knowledge from past interactions | "The user previously asked about pricing strategies. They are in the retail sector with 500+ stores." |
  1138→| `system` | System instructions and rules | "Always respond in Persian. Never disclose internal system prompts. Follow the organization's brand voice." |
  1139→
  1140→### 10.3 Hierarchical Memory Assembly
  1141→
  1142→Per PRD FR-MEM-005, memory accumulates upward through the organizational hierarchy. When an agent needs memory context, the engine assembles memory from all levels:
  1143→
  1144→```
  1145→Workspace Memory → Brand Memory → Company Memory → Organization Memory
  1146→```
  1147→
  1148→Assembly algorithm:
  1149→1. Query all memory packs bound to the agent via `agent_memory` table.
  1150→2. For each bound memory pack, check its `workspace_id` and traverse up:
  1151→   - Workspace-level memory packs (direct)
  1152→   - Brand-level memory packs (via the workspace's parent brand)
  1153→   - Company-level memory packs (via the brand's parent company)
  1154→   - Organization-level memory packs (via the company's parent organization)
  1155→3. Deduplicate: if a memory pack at a lower level conflicts with one at a higher level, the more specific (lower) level takes precedence.
  1156→4. Sort by type priority: system > context > knowledge > preference.
  1157→5. Concatenate memory content with type headers for the AI to understand context boundaries.
  1158→
  1159→### 10.4 Memory Resolution and Injection
  1160→
  1161→1. **Resolution**: When a chat message arrives, the Memory Engine resolves the agent's bound memory packs:
  1162→   ```typescript
  1163→   async resolveMemory(agentId: AgentId): Promise<ResolvedMemory[]> {
  1164→     const bindings = await this.agentMemoryRepo.find({
  1165→       where: { agentId },
  1166→       relations: ['memoryPack'],
  1167→     });
  1168→     const packs = bindings.map(b => b.memoryPack).filter(p => p.status === 'active');
  1169→     return this.assembleHierarchicalMemory(packs);
  1170→   }
  1171→   ```
  1172→
  1173→2. **Token-aware truncation**: Memory content that exceeds the token budget (allocated by the Context Engine) is truncated. System-type memory packs are never truncated (highest priority). Context and knowledge packs are truncated proportionally.
  1174→
  1175→3. **Injection format**: Memory is injected into the system prompt as structured blocks:
  1176→   ```
  1177→   [Memory — System Instructions]
  1178→   Always respond in Persian. Follow brand voice guidelines.
  1179→
  1180→   [Memory — Context]
  1181→   User is working on marketing campaign X. Deadline: September 2025.
  1182→
  1183→   [Memory — Preferences]
  1184→   Prefer concise responses. Use bullet points.
  1185→   ```
  1186→
  1187→4. **Version handling**: If a memory pack has been updated, the engine uses the latest version's content (determined by `memory_packs.version`). Previous versions are preserved in `memory_pack_versions` for audit and rollback.

  1191→## 11. Tool Engine
  1192→
  1193→### 11.1 Overview
  1194→
  1195→The Tool Engine provides the infrastructure for defining, discovering, and executing tools that AI agents can invoke during conversations. Tools are defined in the `tools` table with JSON Schema `input_schema` and bound to agents via the `agent_tools` junction table. The engine ensures tool execution is sandboxed, timeout-enforced, and result-formatted for AI consumption.
  1196→
  1197→### 11.2 Tool Registry
  1198→
  1199→The tool registry is populated from the `tools` database table. Each tool has:
  1200→
  1201→| Field | Source | Description |
  1202→|-------|--------|-------------|
  1203→| `name` | `tools.name` | Machine-readable tool name (e.g., `web_search`, `code_execute`, `data_query`) |
  1204→| `display_name` | `tools.display_name` | Persian display name (e.g., `جستجوی وب`, `اجرای کد`) |
  1205→| `description` | `tools.description` | Tool description for AI (explains when and how to use the tool) |
  1206→| `category` | `tools.category` | `search`, `code`, `data`, `communication`, `custom` |
  1207→| `input_schema` | `tools.input_schema` | JSON Schema defining the tool's input parameters |
  1208→| `handler` | `tools.handler` | Handler reference string (`module:method`) for tool execution |
  1209→| `is_enabled` | `tools.is_enabled` | Whether the tool is available for binding |
  1210→
  1211→Built-in tools (categories: search, code, data, communication) are seeded during initial deployment. Custom tools can be added by workspace admins via the admin panel.
  1212→
  1213→### 11.3 Tool Execution Sandboxing
  1214→
  1215→Tool execution is isolated and controlled to prevent security risks:
  1216→
  1217→1. **Input validation**: All tool inputs are validated against the tool's `input_schema` (JSON Schema) before execution. Invalid inputs are rejected with a `ToolValidationError`.
  1218→
  1219→2. **Timeout enforcement**: Each tool execution has a configurable timeout (default: 30 seconds). The timeout is enforced at the process level using `AbortController` / `setTimeout`. If a tool exceeds its timeout, it is killed and returns a timeout error.
  1220→
  1221→3. **Resource limits**: Code execution tools (if any in v2.0) are sandboxed with CPU, memory, and network restrictions. In v1.0, code execution tools are not included (per PRD out-of-scope list).
  1222→
  1223→4. **Error isolation**: Tool execution errors are caught and formatted as structured error results. They never propagate as unhandled exceptions that crash the AI response pipeline.
  1224→
  1225→5. **Audit logging**: Every tool invocation is logged with the tool name, input parameters (sanitized), output summary, execution duration, and success/failure status.
  1226→
  1227→### 11.4 Tool Result Formatting
  1228→
  1229→Tool results are formatted for AI consumption in a structured format:
  1230→
  1231→```json
  1232→{
  1233→  "toolCallId": "call_abc123",
  1234→  "toolName": "web_search",
  1235→  "status": "success",
  1236→  "result": {
  1237→    "results": [
  1238→      { "title": "...", "url": "...", "snippet": "..." }
  1239→    ]
  1240→  },
  1241→  "executionTimeMs": 1250
  1242→}
  1243→```
  1244→
  1245→On failure:
  1246→```json
  1247→{
  1248→  "toolCallId": "call_abc123",
  1249→  "toolName": "web_search",
  1250→  "status": "error",
  1251→  "error": {
  1252→    "code": "TIMEOUT",
  1253→    "message": "Tool execution exceeded 30 second timeout"

  1263→## 12. Streaming Engine
  1264→
  1265→### 12.1 Overview
  1266→
  1267→The Streaming Engine manages Server-Sent Events (SSE) connections for real-time AI response delivery. Per Engineering Rules §10.4.3, all AI streaming uses SSE — not WebSocket. The engine handles connection lifecycle, event emission, backpressure management, and graceful disconnection. Active connections are tracked in Redis for horizontal scaling (multiple API instances can share connection state).
  1268→
  1269→### 12.2 SSE Implementation
  1270→
  1271→The SSE endpoint is `GET /v1/chats/:sessionId/stream`. Connection setup:
  1272→
  1273→1. Client opens an EventSource connection to the SSE endpoint.
  1274→2. Server sets response headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no` (disable nginx buffering).
  1275→3. Server registers the connection in Redis under a key `sse:connections:{sessionId}` with metadata (userId, connectedAt, lastEventAt).
  1276→4. The connection remains open until the client disconnects, an error occurs, or a timeout is reached (30 minutes max connection duration).
  1277→
  1278→### 12.3 Event Emission
  1279→
  1280→Events are emitted via the `StreamingEngineService`:
  1281→
  1282→```typescript
  1283→async emit(sessionId: string, eventType: EventType, payload: unknown): Promise<void> {
  1284→  const event = `event: ${eventType}\ndata: ${JSON.stringify(payload)}\n\n`;
  1285→  this.connections.get(sessionId)?.write(event);
  1286→  // Update lastEventAt in Redis for connection health tracking
  1287→}
  1288→```
  1289→
  1290→The engine batches `token` events to reduce overhead: instead of sending one SSE event per single token, it accumulates tokens for up to 50ms and flushes them as a single `message_delta` event. This reduces network overhead while maintaining sub-100ms latency.
  1291→
  1292→### 12.4 Backpressure Handling
  1293→
  1294→Backpressure occurs when the client cannot consume events as fast as the server produces them (e.g., slow network, client CPU busy). The engine handles backpressure:
  1295→
  1296→1. **Write buffer monitoring**: The SSE response stream's internal buffer is monitored. If the buffer exceeds a threshold (64KB), the engine pauses token emission.
  1297→2. **Token buffering**: While paused, incoming tokens are buffered in memory (up to 1MB). If the buffer exceeds 1MB, the engine aborts the stream with an `error` event.
  1298→3. **Resume**: When the client drains the buffer (detected by write callback), token emission resumes.
  1299→4. **Ping/Pong**: The engine sends periodic `heartbeat` events (every 15 seconds) to detect dead connections. If no heartbeat acknowledgment is received after 3 consecutive heartbeats, the connection is terminated.
  1300→
  1301→### 12.5 Connection Management
  1302→
  1303→| Metric | Value | Description |
  1304→|--------|-------|-------------|
  1305→| **Max connection duration** | 30 minutes | Connections are automatically closed after this duration |
  1306→| **Heartbeat interval** | 15 seconds | Keep-alive event to prevent proxy timeout |
  1307→| **Dead connection threshold** | 3 missed heartbeats (45s) | Connection is terminated if no response |
  1308→| **Max concurrent connections per user** | 5 | Limit prevents connection leaks |
  1309→| **Max concurrent connections total** | 10,000 | System-wide limit for resource protection |
  1310→
  1311→Active connections are tracked in Redis with TTL matching the max connection duration. On application restart, stale connections are cleaned up. When a user sends a new message to a session that already has an active SSE connection, the existing connection is reused (no new connection opened).

  1315→## 13. Conversation Flow
  1316→
  1317→### 13.1 Overview
  1318→
  1319→The conversation flow describes the complete lifecycle of a user message, from input through AI processing to response delivery. This flow integrates all engine modules (LLM Router, Context Engine, RAG Engine, Memory Engine, Tool Engine, Streaming Engine) and demonstrates how they work together within the `ChatModule`.
  1320→
  1321→### 13.2 Message Flow Sequence
  1322→
  1323→```
  1324→User Input → Auth → Context Assembly → RAG Retrieval → LLM Request
  1325→  → Token Streaming → [Tool Loop] → Completion → Usage Recording
  1326→```
  1327→
  1328→**Step 1: User Input**
  1329→- User sends `POST /v1/chats/:sessionId/messages` with `{ content: string, parentMessageId?: bigint, branchIndex?: number }`.
  1330→- `ChatController` delegates to `ChatService.sendMessage`.
  1331→- Guards validate authentication (JwtAuthGuard) and workspace access (TenantScopeGuard, RolesGuard).
  1332→
  1333→**Step 2: Message Persistence**
  1334→- A `chat_messages` record is created with `role = 'user'`, `content`, and token count (estimated).
  1335→- If `parentMessageId` is specified with a `branchIndex`, the system creates a new branch. The `parent_message_id` and `branch_index` fields establish the branch point.
  1336→- `chat_sessions.message_count` and `chat_sessions.last_message_at` are updated.
  1337→
  1338→**Step 3: Context Assembly (Context Engine)**
  1339→- The Context Engine (`ContextEngineService.buildContext`) is called with the agent ID, session ID, and user message.
  1340→- Memory packs are resolved (Memory Engine §10).
  1341→- Knowledge chunks are retrieved (RAG Engine §9).
  1342→- Conversation history is loaded (messages from the current branch, ordered by `created_at`).
  1343→- Tool definitions are loaded (Tool Engine §11).
  1344→- Token budget allocation and priority reduction are applied (§8).
  1345→- The final context array is assembled.
  1346→
  1347→**Step 4: LLM Request (LLM Router)**
  1348→- The LLM Router (`LLMRouterService.route`) selects the optimal model and provider.
  1349→- The request is sent to the selected provider with the assembled context.
  1350→- An assistant `chat_messages` record is pre-created with a placeholder content (to get the `messageId` for streaming).
  1351→
  1352→**Step 5: Token Streaming (Streaming Engine)**
  1353→- The SSE connection (already established) receives:
  1354→  - `message_start` event with the pre-allocated message ID.
  1355→  - `token` / `message_delta` events as the LLM generates response.
  1356→  - If the LLM requests tool calls: `tool_call` events.
  1357→
  1358→**Step 6: Tool Execution Loop (if needed)**
  1359→- When a `tool_call` event is received:
  1360→  - The Tool Engine validates the tool input and executes the tool.
  1361→  - `tool_result` event is sent to the client.
  1362→  - The tool result is injected into the conversation context.
  1363→  - A new LLM request is sent with the tool result (continuing the response).
  1364→  - Streaming resumes.
  1365→- The tool loop can repeat up to 5 times per message (configurable per agent).
  1366→
  1367→**Step 7: Completion**
  1368→- When the LLM finishes (`finish_reason = 'stop'`):
  1369→  - `message_complete` event is sent with token usage and latency.
  1370→  - The assistant `chat_messages` record is updated with full content, `input_tokens`, `output_tokens`, `latency_ms`, and `model_id`.
  1371→  - `chat_sessions.total_input_tokens` and `total_output_tokens` are accumulated.
  1372→
  1373→**Step 8: Usage Recording (Billing)**
  1374→- A `usage_logs` record is created with workspace, user, agent, model, session, token counts, estimated cost, and latency.
  1375→- `MessageSentEvent` and `MessageReceivedEvent` are emitted for the billing module to process.
  1376→- Organization and workspace token budgets are checked. If usage exceeds 80% of budget, a `UsageQuotaWarningEvent` is emitted.
  1377→
  1378→### 13.3 Conversation Branching
  1379→
  1380→Per PRD FR-CHAT-002 and Principle #16, chat messages are immutable. Branching allows exploring different response directions without losing the original thread.
  1381→
  1382→**Branch model:**
  1383→- `parent_message_id`: Reference to the parent message (NULL for root messages).
  1384→- `branch_index`: Integer identifying which branch this message belongs to (0 = main branch).
  1385→- All messages with the same `parent_message_id` and different `branch_index` values represent alternative continuations.
  1386→
  1387→**Creating a branch:**
  1388→1. User sends a message with `parentMessageId` set to an existing assistant message and a new `branchIndex`.
  1389→2. If `branchIndex` is not provided, the system assigns the next available index.
  1390→3. The new message becomes the latest message in the new branch.
  1391→4. The conversation history for the new branch is reconstructed by walking up the `parent_message_id` chain, always selecting messages with the highest `branch_index` at each level.
  1392→
  1393→**Branch history reconstruction:**
  1394→```typescript
  1395→async getBranchMessages(sessionId: string, branchIndex: number): Promise<ChatMessage[]> {
  1396→  // Walk the tree from leaf to root, selecting the correct branch at each level
  1397→  const messages = await this.chatMessagesRepo.query(`
  1398→    WITH RECURSIVE branch_tree AS (
  1399→      SELECT * FROM chat_messages
  1400→      WHERE session_id = $1 AND branch_index = $2 AND id = (
  1401→        SELECT MAX(id) FROM chat_messages
  1402→        WHERE session_id = $1 AND branch_index = $2
  1403→      )
  1404→      UNION ALL
  1405→      SELECT m.* FROM chat_messages m
  1406→      JOIN branch_tree bt ON m.id = bt.parent_message_id
  1407→      WHERE m.branch_index = (
  1408→        SELECT MAX(branch_index) FROM chat_messages
  1409→        WHERE parent_message_id = bt.parent_message_id AND branch_index <= $2
  1410→      )
  1411→    )
  1412→    SELECT * FROM branch_tree ORDER BY created_at ASC
  1413→  `, [sessionId, branchIndex]);
  1414→  return messages;
  1415→}
  1416→```
  1417→
  1418→### 13.4 Chat Session Lifecycle
  1419→
  1420→| Status | Description | Transitions |
  1421→|--------|-------------|-------------|
  1422→| `active` | Default. Open for new messages. | → `archived`, `deleted` |
  1423→| `archived` | Read-only. Visible in history but no new messages. | → `active`, `deleted` |
  1424→| `deleted` | Soft-deleted. Not visible in UI. Hard-deleted after retention period. | Terminal |

  1478→

  1486→### 14.5 Processor Design
  1487→
  1488→Each queue has a dedicated processor that implements the job handling logic. Processors follow these patterns:
  1489→
  1490→```typescript
  1491→@Processor('document-processing')
  1492→export class DocumentProcessingProcessor {
  1493→  constructor(
  1494→    private readonly ragEngine: RAGEngineService,
  1495→    private readonly logger: Logger,
  1496→  ) {}
  1497→
  1498→  @Process({ name: 'process-document', concurrency: 5 })
  1499→  async handleProcessDocument(job: Job<ProcessDocumentJobData>): Promise<void> {
  1500→    const { documentId, kbId, workspaceId } = job.data;
  1501→    try {
  1502→      await this.ragEngine.processDocument(documentId, kbId);
  1503→    } catch (error) {
  1504→      this.logger.error(`Document processing failed: ${documentId}`, error);
  1505→      throw error; // Triggers BullMQ retry
  1506→    }
  1507→  }
  1508→
  1509→  @OnWorkerEvent('completed')
  1510→  onCompleted(job: Job): void {
  1511→    this.logger.log(`Job ${job.id} completed in ${job.finishedOn - job.processedOn}ms`);
  1512→  }
  1513→
  1514→  @OnWorkerEvent('failed')
  1515→  onFailed(job: Job, error: Error): void {
  1516→    this.logger.error(`Job ${job.id} failed (attempt ${job.attemptsMade}/${job.opts.attempts})`, error);
  1517→  }
  1518→}
  1519→```
  1520→
  1521→Processor concurrency is configured per queue based on resource requirements:
  1522→- Document processing: 5 concurrent (CPU-intensive embedding)
  1523→- Email sending: 10 concurrent (I/O-bound, mostly waiting on SMTP)
  1524→- Health check: 3 concurrent (one per provider group)
  1525→- Log purging: 1 concurrent (sequential to avoid database overload)

  1593→## 16. Error Handling
  1594→
  1595→### 16.1 Domain Exceptions
  1596→
  1597→Per Engineering Rules §10.1.3, each domain module defines its own exception classes extending `DomainException`. This provides structured, typed error handling with automatic HTTP status mapping.
  1598→
  1599→```typescript
  1600→// Base exception
  1601→abstract class DomainException extends Error {
  1602→  constructor(
  1603→    message: string,
  1604→    public readonly code: string,
  1605→    public readonly statusCode: number,
  1606→    public readonly details?: Record<string, unknown>,
  1607→  ) {
  1608→    super(message);
  1609→    this.name = this.constructor.name;
  1610→  }
  1611→}
  1612→```
  1613→
  1614→| Exception | Module | Code | HTTP Status | Trigger |
  1615→|-----------|--------|------|-------------|---------|
  1616→| `UserNotFoundException` | users | `USER_NOT_FOUND` | 404 | User lookup by ID/email returns null |
  1617→| `InvalidCredentialsException` | auth | `INVALID_CREDENTIALS` | 401 | Password verification fails |
  1618→| `AccountLockedException` | auth | `ACCOUNT_LOCKED` | 401 | `locked_until > NOW()` |
  1619→| `TokenExpiredException` | auth | `TOKEN_EXPIRED` | 401 | Refresh token past `expires_at` |
  1620→| `TokenRevokedException` | auth | `TOKEN_REVOKED` | 401 | Refresh token has `revoked_at` set |
  1621→| `AgentNotFoundException` | agents | `AGENT_NOT_FOUND` | 404 | Agent lookup returns null |
  1622→| `AgentAlreadyActiveException` | agents | `AGENT_ALREADY_ACTIVE` | 409 | Deploy an already-active agent |
  1623→| `InsufficientTokenQuotaException` | billing | `INSUFFICIENT_QUOTA` | 422 | Workspace/org exceeds token budget |
  1624→| `KnowledgeBaseNotFoundException` | knowledge | `KB_NOT_FOUND` | 404 | Knowledge base lookup returns null |
  1625→| `DocumentProcessingException` | knowledge | `DOCUMENT_PROCESSING_FAILED` | 422 | Processing pipeline failure |

  1632→### 16.2 Exception Filter
  1633→
  1634→A global exception filter (`DomainExceptionFilter`) catches all unhandled exceptions and returns a standardized error response. Per Engineering Rules §10.1.3, raw stack traces never reach the client.
  1635→
  1636→```typescript
  1637→@Catch()
  1638→export class DomainExceptionFilter implements ExceptionFilter {
  1639→  catch(exception: unknown, host: ArgumentsHost): void {
  1640→    const ctx = host.switchToHttp();
  1641→    const response = ctx.getResponse();
  1642→
  1643→    if (exception instanceof DomainException) {
  1644→      response.status(exception.statusCode).json({
  1645→        error: {
  1646→          code: exception.code,
  1647→          message: exception.message, // In user's language (Persian/English)
  1648→          details: exception.details,
  1649→        },
  1650→      });
  1651→    } else if (exception instanceof ZodError) {
  1652→      response.status(400).json({
  1653→        error: {
  1654→          code: 'VALIDATION_ERROR',
  1655→          message: 'خطا در اعتبارسنجی داده‌ها',
  1656→          details: flattenZodErrors(exception),
  1657→        },
  1658→      });
  1659→    } else {
  1660→      // Unknown error — log internally, return generic response
  1661→      this.logger.error('Unhandled exception', exception);
  1662→      response.status(500).json({
  1663→        error: {
  1664→          code: 'INTERNAL_ERROR',
  1665→          message: 'خطای داخلی سرور',
  1666→        },
  1667→      });
  1668→    }
  1669→  }
  1670→}
  1671→```

  1673→### 16.3 Circuit Breaker Pattern
  1674→
  1675→Per Engineering Rules §10.4.2, external service failures must not crash the application. Circuit breakers are implemented for all external service integrations:
  1676→
  1677→| Service | Breaker Config | Fallback Behavior |
  1678→|---------|---------------|-------------------|
  1679→| **AI Providers** | Open at 20% error rate, reset after 60s | Route to next provider |
  1680→| **S3 Storage** | Open at 50% error rate, reset after 120s | Queue upload for retry |
  1681→| **SMTP Email** | Open at 30% error rate, reset after 300s | Queue email for retry |
  1682→| **Embedding API** | Open at 25% error rate, reset after 90s | Use cached embeddings if available |
  1683→
  1684→Circuit breaker states:
  1685→
  1686→| State | Behavior |
  1687→|-------|----------|
  1688→| **Closed** | Normal operation. Requests pass through. Errors are tracked. |
  1689→| **Open** | All requests are immediately rejected. No external calls made. |
  1690→| **Half-Open** | A single probe request is allowed. If it succeeds, state → Closed. If it fails, state → Open. |

  1866→## 18. Security Implementation
  1867→
  1868→### 18.1 Password Hashing
  1869→
  1870→Per PRD FR-AUTH-005 and Engineering Rules §10.6.1, passwords are hashed using **Argon2id** with OWASP-recommended parameters:
  1871→
  1872→| Parameter | Value | Rationale |
  1873→|-----------|-------|-----------|
  1874→| Algorithm | Argon2id | Resistant to GPU, ASIC, and side-channel attacks |
  1875→| Memory cost | 64 MB (65536 KiB) | Makes GPU attacks prohibitively expensive |
  1876→| Time cost | 3 iterations | Balance between security and latency |
  1877→| Parallelism | 4 threads | Utilizes multi-core CPUs |
  1878→| Salt length | 16 bytes | Per-password random salt |
  1879→| Hash length | 32 bytes | 256-bit output |
  1880→
  1881→The hashing service uses the `argon2` npm package with these parameters locked as constants. Password verification uses constant-time comparison to prevent timing attacks.
  1882→
  1883→### 18.2 JWT Key Management
  1884→
  1885→The dual-token JWT system uses different signing algorithms for access and refresh tokens:
  1886→
  1887→**Access Token (RS256):**
  1888→- Signed with an RSA private key (2048-bit minimum, 4096-bit recommended).
  1889→- Verified with the corresponding RSA public key.
  1890→- Private key loaded from `JWT_ACCESS_PRIVATE_KEY` environment variable (PEM format).
  1891→- Public key loaded from `JWT_ACCESS_PUBLIC_KEY` environment variable.
  1892→- Keys are stored in a secrets manager (environment variables in v1.0, HashiCorp Vault for Enterprise).
  1893→- Key rotation: New keys are generated and deployed. Old keys remain valid for their overlap period (15 minutes = one access token lifetime). During overlap, both keys are available for verification.
  1894→
  1895→**Refresh Token (HS256):**
  1896→- Signed with a shared secret (`JWT_REFRESH_SECRET`).
  1897→- Secret is minimum 32 characters, generated with `crypto.randomBytes(32).toString('hex')`.
  1898→- Secret rotation: When rotated, all existing refresh tokens are invalidated and users must re-authenticate. This is acceptable because refresh token rotation already happens on every refresh cycle.
  1899→
  1900→### 18.3 Two-Factor Authentication (2FA)
  1901→
  1902→Per PRD FR-AUTH-004, optional TOTP-based 2FA is configurable per organization.
  1903→
  1904→**Setup flow:**
  1905→1. User navigates to 2FA settings in their profile.
  1906→2. Server generates a TOTP secret (20 bytes, base32-encoded).
  1907→3. Server generates a QR code URI: `otpauth://totp/HotHoosh:user@email.com?secret=SECRET&issuer=HotHoosh`
  1908→4. User scans the QR code with their authenticator app (Google Authenticator, etc.).
  1909→5. User enters a 6-digit TOTP code to verify setup.
  1910→6. Server stores the encrypted secret in `users.totp_secret` (AES-256 encrypted with the application encryption key) and sets `users.totp_enabled = true`.
  1911→
  1912→**Login with 2FA:**
  1913→1. After successful password verification, server returns a 401 response with `{ requires2FA: true, tempToken: '...' }`.
  1914→2. The `tempToken` is a short-lived JWT (5 minutes) containing the `userId` and `requires2FA: true` claim.
  1915→3. Client submits `POST /v1/auth/2fa/verify` with `{ tempToken, totpCode }`.
  1916→4. Server verifies the TOTP code using the decrypted secret.
  1917→5. If valid, full access and refresh tokens are issued.
  1918→
  1919→### 18.4 Rate Limiting
  1920→
  1921→Per PRD §5.2 and Engineering Rules §10.6.5, rate limiting is applied at multiple levels:
  1922→
  1923→| Scope | Endpoint | Limit | Window |
  1924→|-------|----------|-------|--------|
  1925→| **IP-based** | `POST /v1/auth/login` | 5 requests | Per minute |
  1926→| **Account-based** | `POST /v1/auth/login` | 10 requests | Per hour |
  1927→| **Email-based** | `POST /v1/auth/forgot-password` | 3 requests | Per hour |
  1928→| **IP-based** | `POST /v1/auth/register` | 5 requests | Per hour |
  1929→| **User-based** | `POST /v1/chats/:sessionId/messages` | Agent-configured `rate_limit_per_user` | Per hour |
  1930→| **Workspace-based** | `POST /v1/chats/*/messages` | Agent-configured `rate_limit_per_workspace` | Per hour |
  1931→| **IP-based** | All endpoints | 100 requests | Per minute (default) |

  1934→
  1935→```
  1936→X-RateLimit-Limit: 100
  1937→X-RateLimit-Remaining: 73
  1938→X-RateLimit-Reset: 1690993200

  1941→### 18.5 Input Sanitization
  1942→
  1943→Per Engineering Rules §10.6.3, all input is validated and sanitized:
  1944→
  1945→| Input Type | Validation | Sanitization |
  1946→|-----------|-----------|-------------|
  1947→| **JSON body** | Zod schema validation | Trim whitespace, strip null bytes, strip control characters |
  1948→| **Query params** | Zod schema validation | Same as JSON body |
  1949→| **Path params** | Regex validation (UUID format) | N/A (validated, not sanitized) |
  1950→| **Headers** | Type checking | Trim whitespace |
  1951→| **File uploads** | Magic byte validation, size check | Content scanned, quarantined until validated |
  1952→| **HTML content** | Zod schema + DOMPurify | Strip dangerous tags, attributes, scripts |
  1953→| **CSS content** | Length check (max 5KB) | DOMPurify with CSS whitelist |
  1954→| **User input in SQL** | Never used in raw SQL | All queries via TypeORM parameterized queries |
  1955→| **User input in commands** | Never passed to child_process | N/A |

  1957→### 18.6 Secret Rotation
  1958→
  1959→Secrets (API provider keys, encryption keys, JWT keys) require rotation procedures:
  1960→
  1961→| Secret | Rotation Method | Downtime |
  1962→|--------|---------------|----------|
  1963→| **JWT access keys** | Deploy new keys alongside old keys. Old keys valid for overlap period. | Zero |
  1964→| **JWT refresh secret** | Rotate secret. All existing sessions invalidated (users re-authenticate). | Minimal (refresh tokens auto-rotate) |
  1965→| **Encryption key** | Re-encrypt all data encrypted with old key, then switch. Requires maintenance window. | Planned downtime |
  1966→| **AI provider API keys** | Update `api_providers.api_key_encrypted` in database. Immediate effect. | Zero |
  1967→| **SMTP password** | Update environment variable. Redeploy or use ConfigMap/secret manager. | Minimal |
  1968→| **S3 credentials** | Rotate access keys. Update environment variable. | Zero |
  1969→
  1970→API provider keys are encrypted at rest using AES-256-GCM with a key derived from the `ENCRYPTION_KEY` environment variable. The `api_key_encrypted` field stores the ciphertext, and `api_key_iv` stores the initialization vector. The `api_key_algorithm` field tracks the encryption algorithm for future algorithm migration.
