     3→     3→## HotHoosh — Complete Schema Specification
     4→     4→
     5→     5→---
     6→     6→
     7→     7→## 1. Database Engine
     8→     8→
     9→     9→**PostgreSQL 16+** with the following extensions:
    10→    10→
    11→    11→| Extension | Version | Purpose |
    12→    12→|-----------|---------|--------|
    13→    13→| `uuid-ossp` | 1.1 | UUID v7 generation (via custom function) |
    14→    14→| `vector` (pgvector) | 0.7+ | Vector embeddings storage and HNSW indexing |
    15→    15→| `pg_trgm` | 1.6 | Trigram similarity for fuzzy text search |
    16→    16→| `btree_gin` | 1.3 | GIN indexes on JSONB columns |
    17→    17→
    18→    18→### 1.1 UUID v7 Strategy
    19→    19→
    20→    20→HotHoosh uses **UUID v7** (time-sortable) as the default primary key for all entities. UUID v7 combines a Unix timestamp (millisecond precision) with random bytes, producing IDs that are:
    21→    21→
    22→    22→- **Globally unique** (no coordination needed)
    23→    23→- **Time-sortable** (recent entities have higher IDs, benefiting B-tree indexes)
    24→    24→- **K-sortable** within the same millisecond
    25→    25→
    26→    26→For **high-throughput append-only tables** (audit_logs, usage_logs, chat_messages, system_logs), **BIGINT** auto-increment is used instead to avoid UUID storage overhead and maintain maximum insert throughput.
    27→    27→
    28→    28→### 1.2 Migration Strategy
    29→    29→
    30→    30→Migrations are managed via a dedicated migration tool integrated with NestJS. Each migration file is timestamped and contains `UP` and `DOWN` functions. Migrations are:
    31→    31→
    32→    32→- **Sequential**: Each migration builds on the previous one.
    33→    33→- **Irreversible by default**: `DOWN` functions must be explicitly written for rollback support.
    34→    34→- **Tested**: Every migration is tested against a copy of production data before deployment.
    35→    35→- **Reviewed**: Schema changes require PR review with at least 2 approvals.
    36→    36→

    39→    39→## 2. Schema Overview
    40→    40→
    41→    41→The HotHoosh data model is organized into the following domains:
    42→    42→
    43→    43→```
    44→    44→┌─────────────────────────────────────────────────────────┐
    45→    45→│                    TENANT HIERARCHY                      │
    46→    46→│  organizations → companies → brands → workspaces       │
    47→    47→│       ↓            ↓          ↓          ↓              │
    48→    48→│  org_settings  company_settings  brand_settings  workspace_settings │
    49→    49→└─────────────────────────────────────────────────────────┘
    50→    50→
    51→    51→┌─────────────────────────────────────────────────────────┐
    52→    52→│                      IDENTITY                             │
    53→    53→│  users → user_roles → roles → permissions                │
    54→    54→│  workspace_users (junction: users × workspaces)          │
    55→    55→│  refresh_tokens                                           │
    56→    56→│  user_invitations                                         │
    57→    57→└─────────────────────────────────────────────────────────┘
    58→    58→
    59→    59→┌─────────────────────────────────────────────────────────┐
    60→    60→│                        AI                                 │
    61→    61→│  api_providers → models → model_routing_rules            │
    62→    62→│  agents → agent_tools → agent_knowledge → agent_memory   │
    63→    63→│  tools → tool_parameters                                  │
    64→    64→└─────────────────────────────────────────────────────────┘
    65→    65→
    66→    66→┌─────────────────────────────────────────────────────────┐
    67→    67→│                     CONVERSATION                          │
    68→    68→│  chat_sessions → chat_messages (immutable)               │
    69→    69→│  chat_branches                                            │
    70→    70→└─────────────────────────────────────────────────────────┘
    71→    71→
    72→    72→┌─────────────────────────────────────────────────────────┐
    73→    73→│                     KNOWLEDGE                             │
    74→    74→│  knowledge_bases → knowledge_documents → knowledge_chunks│
    75→    75→│  knowledge_embeddings (vector)                            │
    76→    76→└─────────────────────────────────────────────────────────┘
    77→    77→
    78→    78→┌─────────────────────────────────────────────────────────┐
    79→    79→│                      MEMORY                               │
    80→    80→│  memory_packs → memory_pack_versions                     │
    81→    81→│  memory_pack_bindings (agents × memory_packs)            │
    82→    82→└─────────────────────────────────────────────────────────┘
    83→    83→
    84→    84→┌─────────────────────────────────────────────────────────┐
    85→    85→│                    OPERATIONS                             │
    86→    86→│  audit_logs (BIGINT PK)                                  │
    87→    87→│  usage_logs (BIGINT PK, partitioned)                     │
    88→    88→│  system_logs (BIGINT PK)                                  │
    89→    89→│  background_jobs (BullMQ)                                 │
    90→    90→│  invoices → invoice_line_items → transactions            │
    91→    91→│  plans → subscriptions                                    │
    92→    92→│  settings (key-value)                                     │
    93→    93→│  webhooks                                                 │
    94→    94→│  email_templates                                          │
    95→    95→│  notifications                                           │
    96→    96→└─────────────────────────────────────────────────────────┘
    97→    97→```

   102→   102→
   103→   103→### 3.1 organizations
   104→   104→
   105→   105→| Column | Type | Constraints | Description |
   106→   106→|--------|------|-------------|-------------|
   107→   107→| id | UUID | PK, DEFAULT uuid_generate_v7() | Organization identifier |
   108→   108→| name | VARCHAR(100) | NOT NULL, CHECK(length > 2) | Organization display name (Persian) |
   109→   109→| slug | VARCHAR(50) | NOT NULL, UNIQUE, CHECK(slug ~ '^[a-z0-9-]+$') | URL-safe identifier |
   110→   110→| logo_url | VARCHAR(500) | NULL | S3 URL for organization logo |
   111→   111→| description | TEXT | NULL | Organization description |
   112→   112→| owner_id | UUID | NOT NULL, FK(users.id) | Organization owner |
   113→   113→| plan_id | UUID | NOT NULL, FK(plans.id) | Current subscription plan |
   114→   114→| status | VARCHAR(20) | NOT NULL, DEFAULT 'active', CHECK(status IN ('active','inactive','suspended')) | Organization status |

   116→   116→| max_users | INTEGER | NOT NULL, DEFAULT 50 | Plan-defined limit |
   117→   117→| token_budget_monthly | BIGINT | NOT NULL, DEFAULT 5000000 | Monthly token budget (5M default) |
   118→   118→| storage_limit_mb | BIGINT | NOT NULL, DEFAULT 51200 | Storage limit in MB (50GB default) |
   119→   119→| settings | JSONB | NOT NULL, DEFAULT '{}' | Organization-level settings (JSON) |
   120→   120→| created_at | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | Creation timestamp |
   121→   121→| updated_at | TIMESTAMPTZ | NOT NULL, DEFAULT NOW() | Last update timestamp |
   122→   122→| deleted_at | TIMESTAMPTZ | NULL | Soft delete timestamp |
   123→   123→
   124→   124→**Indexes:**
   125→   125→- `uniq_orgs_slug` UNIQUE (slug) WHERE deleted_at IS NULL
   126→   126→- `idx_orgs_owner_id` B-tree (owner_id)
   127→   127→- `idx_orgs_plan_id` B-tree (plan_id)
   128→   128→- `idx_orgs_status` B-tree (status) WHERE deleted_at IS NULL
   129→   129→- `idx_orgs_created_at` B-tree (created_at DESC)
   130→   130→
   131→   131→**RLS Policy:**
   132→   132→- Super admins: full access
   133→   133→- Org admins: access to own org + no access to others
   134→   134→- Others: no direct access (access via company/brand/workspace membership)

  1110→  1110→- **All status columns**: B-tree indexes with partial index for active status
  1111→  1111→- **All timestamp columns used in queries**: B-tree DESC for chronological queries
  1112→  1112→- **Full-text search**: GIN index with `to_tsvector('persian', column)` for Persian content

  1115→  1115→- **JSONB columns**: GIN indexes for columns queried with `@>`, `?`, `??` operators

  1117→  1117→### 11.3 Future Extensibility
  1118→  1118→
  1119→  1119→- **Dedicated vector database**: When pgvector HNSW exceeds ~10M vectors, migrate to Qdrant or Milvus. The `knowledge_embeddings` table abstraction supports this.
  1120→  1120→- **Read replicas**: All read-heavy queries (dashboard, analytics) are directed to read replicas via query hints.
  1121→  1121→- **Sharding**: Tenant-level sharding is possible by adding a `shard_key` column to tenant tables. Not needed until single-node capacity is exceeded.
  1122→  1122→- **Event sourcing**: Audit logs provide a foundation for future event sourcing if needed.
  1123→  1123→- **Workspace databases (EAV)**: The `settings` JSONB columns on tenant entities support the EAV pattern for workspace-specific dynamic data. If structured workspace databases are needed in the future, a dedicated `workspace_data` table with EAV pattern can be added.
