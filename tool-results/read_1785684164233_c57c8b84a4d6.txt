   116→   315→### 3.2 State Management Boundaries
   117→   316→
   118→   317→HotHoosh enforces a strict separation of state management concerns. Overlapping these boundaries is a violation of Engineering Rules §10.4.1.
   119→   318→
   120→   319→| State Type | Tool | Scope | Examples |
   121→   320→|-----------|------|-------|----------|
   122→   321→| **Server state** | TanStack Query | API data: users, agents, knowledge bases, usage stats | `useQuery`, `useMutation`, `useInfiniteQuery` |
   123→   322→| **Client state** | Zustand | UI-only: theme, sidebar open/closed, command palette, selection | `useThemeStore`, `useSidebarStore` |
   124→   323→| **Form state** | React Hook Form + Zod | Form inputs: login form, create agent, upload document | `useForm` with `zodResolver` |
   125→   324→| **URL state** | Next.js `useSearchParams` | Filters, pagination, active tab | `?page=2&status=active&sort=created_at` |
   126→   325→
   127→   326→**Key rules:**
   128→   327→- Zustand stores never hold server data. If it came from the API, it belongs in TanStack Query.
   129→   328→- Zustand store actions are synchronous. Async work (API calls) lives in TanStack Query mutations, which call Zustand actions on success.
   130→   329→- Components read Zustand via selectors (`useThemeStore(s => s.theme)`) to prevent unnecessary re-renders.
   131→   330→- TanStack Query keys use a factory pattern: `chatKeys.messages(sessionId)`, `adminKeys.agents.list(filters)`.

   238→   437→### 3.6 RTL-First Design
   239→   438→
   240→   439→Per PRD Principles #1 and #2, the entire interface is built **RTL-first** using CSS logical properties. LTR is supported as a secondary direction. The root `<html>` element has `dir="rtl"` by default for Persian users.
   241→   440→
   242→   441→**CSS rules enforced by the engineering rules:**
   243→   442→- Use `ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `inline-*`, `block-*` exclusively.
   244→   443→- Never use physical properties: `left`, `right`, `ml-*`, `mr-*`, `pl-*`, `pr-*`.
   245→   444→- Tailwind utility classes follow logical property mapping: `ms-4` (margin-inline-start), `me-4` (margin-inline-end).
   246→   445→- Dark mode is implemented by switching CSS variable values on `:root` and `[data-theme="dark"]`. Tailwind's `dark:` variant is not used.

   261→   460→## 4. Backend Architecture
   262→   461→
   263→   462→### 4.1 Architectural Philosophy
   264→   463→
   265→   464→HotHoosh's backend is a **NestJS modular monolith** with hexagonal module boundaries (PRD Principle #15, Engineering Rules §10.4.2). The entire backend runs as a single deployable unit, but internal module boundaries are strictly enforced as if each module were a separate microservice. Modules communicate exclusively through well-defined public APIs (injected services and domain events), never through shared mutable state or direct internal imports across module boundaries.
   266→   465→
   267→   466→The modular monolith preserves the ability to extract modules into separate services in the future (v2.0+) because hexagonal boundaries ensure low coupling and high cohesion within each domain module.
   268→   467→
   269→   468→### 4.2 Technology Stack
   270→   469→
   271→   470→| Layer | Technology | Rationale |
   272→   471→|-------|-----------|----------|
   273→   472→| Runtime | Node.js 20+ LTS | Non-blocking I/O for SSE streaming and concurrent AI requests |
   274→   473→| Framework | NestJS 10+ | DI container, module system, guard/filter/interceptor pipeline |
   275→   474→| ORM | TypeORM | PostgreSQL-native, custom repository support, migration tooling |
   276→   475→| Database | PostgreSQL 16+ | pgvector, RLS, JSONB, partitioned tables, full-text search |
   277→   476→| Cache/Queue | Redis 7+ | BullMQ job queues, session store, rate limiting, caching |
   278→   477→| Validation | Zod | Shared schemas between frontend and backend (§10.1.3) |
   279→   478→| File Storage | S3-compatible (MinIO) | Document storage for knowledge bases |
   280→   479→| Email | Nodemailer (SMTP) | Transactional emails for invitations, password resets |
   281→   480→| Streaming | Server-Sent Events (SSE) | One-directional real-time AI response streaming |

   301→   500→
   302→   501→### 4.4 6 Engine Modules
   303→   502→
   304→   503→Engine modules provide AI/ML infrastructure consumed by domain modules. They are stateless computational units (no owned database tables, except for caching/state).
   305→   504→
   306→   505→| Engine | Responsibility | Consumed By | Key Design |
   307→   506→|--------|---------------|-------------|------------|
   308→   507→| **llm-router** | Route AI requests to optimal provider/model, health monitoring, failover | `ChatModule`, `RAGEngine` | 5-step routing pipeline, circuit breakers, Redis health cache |
   309→   508→| **context-engine** | Token budget allocation, context window management, priority reduction | `ChatModule` | Priority: Knowledge (40%) → History (30%) → Memory (20%) → Tools (10%) |
   310→   509→| **rag-engine** | Document processing pipeline, hybrid retrieval, Persian NLP | `ChatModule`, `KnowledgeModule` | HNSW + BM25 with RRF, 4 chunking strategies, Persian normalizer |
   311→   510→| **memory-engine** | Memory pack resolution, hierarchical assembly, injection | `ChatModule`, `ContextEngine` | Workspace → Brand → Company → Org (accumulates upward) |
   312→   511→| **tool-engine** | Tool registry, validation, sandboxed execution, result formatting | `ChatModule` | JSON Schema input validation, timeout enforcement, audit logging |
   313→   512→| **streaming-engine** | SSE connection management, event emission, backpressure | `ChatModule`, `KnowledgeModule` | 8 event types, Redis connection tracking, 50ms batch window |
   314→   513→
   315→   514→### 4.5 Domain Event System
   316→   515→
   317→   516→Modules never import each other's services directly for cross-domain operations. Instead, they emit **domain events** through an in-memory event bus backed by Redis for reliability. A **transactional outbox** pattern ensures no events are lost: events are written to the database within the same transaction as the state change, then dispatched asynchronously by a BullMQ worker.
   318→   517→
   319→   518→```
   320→   519→Service performs write operation
   321→   520→  → Opens DB transaction
   322→   521→  → Writes domain state change
   323→   522→  → Inserts outbox_events record (same transaction)
   324→   523→  → Commits atomically
   325→   524→  → BullMQ worker polls outbox
   326→   525→  → Dispatches to event bus
   327→   526→  → Handlers react asynchronously
   328→   527→```
   329→   528→
   330→   529→### 4.6 Authentication: Dual-Token JWT
   331→   530→
   332→   531→| Token | Algorithm | Expiry | Storage | Purpose |
   333→   532→|-------|-----------|-------|---------|---------|
   334→   533→| **Access** | RS256 (asymmetric) | 15 minutes | In-memory only | API authentication. Validated via public key — no DB lookup. |
   335→   534→| **Refresh** | HS256 (symmetric) | 7 days | `HttpOnly`, `Secure`, `SameSite=Strict` cookie | Session persistence. Validated via DB lookup (revocation check). |
   336→   535→
   337→   536→**Token rotation on refresh:** Every refresh invalidates the old token and issues a new one with the same `family_id`. If a previously-revoked token is presented (theft detection), all tokens in that family are revoked.
   338→   537→
   339→   538→**Password hashing:** Argon2id (memory=64MB, time=3, parallelism=4). Account lockout after 10 failed attempts within 1 hour (30-minute lockout).
   340→   539→
   341→   540→### 4.7 Authorization: Three-Layer RBAC + RLS
   342→   541→
   343→   542→| Layer | Source | Scope | Example Roles |
   344→   543→|-------|--------|-------|--------------|
   345→   544→| **Organization Role** | `roles` table (`level = 'org'`) | Organization-wide | `super_admin`, `org_admin`, `org_member` |
   346→   545→| **Workspace Role** | `workspace_users.role_id` | Workspace-specific | `workspace_admin`, `workspace_member`, `workspace_viewer` |
   347→   546→| **Resource Permissions** | `roles.permissions` JSONB | Individual resource | `agents:create`, `knowledge:delete`, `billing:read` |
   348→   547→
   349→   548→Effective permissions are the **union** of all permissions from all roles the user holds. Authorization is enforced via NestJS guards (`JwtAuthGuard → TenantScopeGuard → RolesGuard → ImpersonationGuard`).
   350→   549→
   351→   550→**PostgreSQL RLS** provides database-level tenant isolation — even if application code has a bug, RLS prevents cross-tenant data access. Session variables (`app.current_user_id`, `app.current_org_id`) are set at connection checkout.
   352→   551→
   353→   552→### 4.8 API Design
   354→   553→
   355→   554→All endpoints follow REST conventions with URL-based versioning (`/v1/`), consistent response envelopes, and pagination on all list endpoints.
   356→   555→
   357→   556→**Response envelope (success):**
   358→   557→```json
   359→   558→{ "data": { ... }, "meta": { "page": 1, "limit": 20, "total": 142, "hasMore": true } }
   360→   559→```
   361→   560→
   362→   561→**Response envelope (error):**
   363→   562→```json
   364→   563→{ "error": { "code": "AGENT_NOT_FOUND", "message": "عامل هوش مصنوعی یافت نشد", "details": {} } }
   365→   564→```
   366→   565→
   367→   566→**SSE streaming** is used for all AI responses. The endpoint `GET /v1/chats/:sessionId/stream` emits 8 event types: `token`, `message_start`, `message_delta`, `message_complete`, `tool_call`, `tool_result`, `error`, `heartbeat`.
   368→   567→
   369→   568→### 4.9 Error Handling
   370→   569→
   371→   570→Each domain module defines typed exceptions extending `DomainException`. A global `DomainExceptionFilter` catches all unhandled exceptions and returns the standardized error envelope. Raw stack traces never reach the client. Circuit breakers protect against external service failures (AI providers, S3, SMTP, embedding APIs).

   665→   864→    │                         │  5. Verify HS256          │                    │
   666→   865→    │                         │     signature             │                    │
   667→   866→    │                         │  6. Extract userId,       │                    │
   668→   867→    │                         │     familyId              │                    │
   669→   868→    │                         │                            │                    │

   675→   874→    │                         │     expires_at > NOW()?   │                    │

   677→   876→    │                         │                            │                    │
   678→   877→    │                         │  9. [THEFT CHECK]         │                    │
   679→   878→    │                         │     Is token already      │                    │

   688→   887→    │                         │                            │                    │
   689→   888→    │                         │  11. Generate new HS256   │                    │

   691→   890→    │                         │  12. Store new token      │                    │
   692→   891→    │                         │      hash in DB           │                    │

   822→  1021→## 8. Key Design Decisions
   823→  1022→
   824→  1023→### DD-01: Modular Monolith, Not Microservices
   825→  1024→
   826→  1025→**Decision:** Build the backend as a single NestJS application with strict hexagonal module boundaries, not as a set of independent microservices.
   827→  1026→
   828→  1027→**Rationale:**
   829→  1028→
   830→  1029→| Factor | Modular Monolith | Microservices |
   831→  1030→|--------|-----------------|---------------|
   832→  1031→| Development velocity | Single codebase, single build, single deploy | Multiple codebases, independent builds |
   833→  1032→| Data consistency | Single PostgreSQL transaction spans all modules | Distributed transactions (Saga) or eventual consistency |
   834→  1033→| Team size fit | 3–8 developers (current phase) | Requires 10+ for independent service ownership |
   835→  1034→| Latency | In-process communication (nanoseconds) | Network communication (milliseconds) |
   836→  1035→| Operational cost | Single process to monitor and debug | Service mesh, load balancing, distributed tracing |
   837→  1036→
   838→  1037→Hexagonal boundaries ensure that any module can be extracted into a separate service in v2.0+ with minimal refactoring. The modular monolith gives us microservice-level discipline without microservice-level operational tax.
   839→  1038→
   840→  1039→### DD-02: PostgreSQL, Not MongoDB
   841→  1040→
   842→  1041→**Decision:** Use PostgreSQL 16+ as the sole data store.
   843→  1042→
   844→  1043→**Rationale:** HotHoosh requires ACID transactions (billing, token accounting), relational data (Org → Company → Brand → Workspace hierarchy), full-text search (BM25 for RAG), vector search (pgvector for embeddings), and row-level security (tenant isolation). PostgreSQL provides all of these in a single database, eliminating the operational complexity of maintaining MongoDB + a vector DB + a relational DB. JSONB columns provide schema flexibility where needed (settings, permissions, tool schemas).
   845→  1044→
   846→  1045→### DD-03: pgvector, Not Dedicated Vector DB (Initially)
   847→  1046→
   848→  1047→**Decision:** Use pgvector for vector storage and HNSW indexing. Do not introduce Pinecone, Qdrant, or Weaviate in v1.0.
   849→  1048→
   850→  1049→**Rationale:** pgvector with HNSW indexes achieves < 150ms P95 latency for 10M+ vectors, which meets our requirements. Adding a dedicated vector DB introduces operational complexity, data synchronization challenges, and cost. The PRD explicitly defers dedicated vector DB to v2.0 if scale demands it. PostgreSQL's advantage is that vector queries can join with relational data (e.g., filter by `knowledge_base_id` and `workspace_id` within the same query).
   851→  1050→
   852→  1051→### DD-04: Dual-Token JWT, Not Single Token or Session
   853→  1052→
   854→  1053→**Decision:** Use two separate JWTs: RS256 access token (15min, in-memory) + HS256 refresh token (7d, HttpOnly cookie).
   855→  1054→
   856→  1055→**Rationale:**
   857→  1056→
   858→  1057→| Approach | Security | Performance | Complexity |
   859→  1058→|----------|----------|-------------|------------|
   860→  1059→| Single long-lived JWT | Low — compromised token valid for days | High — no refresh needed | Low |
   861→  1060→| Server-side sessions | High — instant revocation | Low — DB lookup on every request | Medium |
   862→  1061→| **Dual-token JWT** | **High** — short-lived access, rotation detects theft | **High** — access token validated without DB | **Medium** |
   863→  1062→
   864→  1063→RS256 for access tokens means validation requires only the public key (no DB lookup). HS256 for refresh tokens means revocation requires the shared secret + DB check. The rotation mechanism provides theft detection: if a previously-revoked token is presented, all sessions are terminated.
   865→  1064→
   866→  1065→### DD-05: UUID v7, Not UUID v4
   867→  1066→
   868→  1067→**Decision:** Use UUID v7 (time-sortable) as the default primary key for all entities.
   869→  1068→
   870→  1069→**Rationale:** UUID v7 combines a Unix timestamp (millisecond precision) with random bytes. This produces IDs that are globally unique (no coordination) and time-sortable (recent entities have higher IDs), which benefits B-tree index performance on append-heavy tables. UUID v4 is random, causing index fragmentation on time-ordered data. For high-throughput append-only tables (audit_logs, chat_messages, usage_logs), BIGINT auto-increment is used instead to avoid UUID storage overhead.
   871→  1070→
   872→  1071→### DD-06: Immutable Chat Messages
   873→  1072→
   874→  1073→**Decision:** Chat messages are never updated in place. Edits create new messages. Branching uses `parent_message_id` + `branch_index`.
   875→  1074→
   876→  1075→**Rationale:** Immutability eliminates an entire class of bugs (concurrent edits, lost updates, audit trail corruption). Branching enables exploring different AI response directions without losing the original thread. The `parent_message_id` + `branch_index` model reconstructs conversation history by walking up the tree. This design also simplifies billing (each message has a definitive token count that never changes) and audit logging (a complete, tamper-proof record of every interaction).
   877→  1076→
   878→  1077→### DD-07: Zod, Not class-validator
   879→  1078→
   880→  1079→**Decision:** Use Zod schemas for all input validation on both frontend and backend.
   881→  1080→
   882→  1081→**Rationale:** Zod schemas can be shared between frontend and backend via `packages/shared`, guaranteeing that the same validation rules apply on both sides. `class-validator` uses decorators and classes, which cannot be shared with a React frontend. Zod also provides superior TypeScript inference (`z.infer<typeof schema>`) and composable schema building (`.pick()`, `.omit()`, `.partial()`, `.merge()`).
   883→  1082→
   884→  1083→### DD-08: NestJS, Not Express or Fastify
   885→  1084→
   886→  1085→**Decision:** Build the backend API with NestJS.
   887→  1086→
   888→  1087→**Rationale:** NestJS provides a built-in DI container, module system, and guard/filter/interceptor pipeline that directly map to our hexagonal architecture requirements. Express requires manual assembly of middleware chains and has no DI or module system. Fastify is performant but lacks NestJS's structured module system. NestJS's decorators (`@Controller`, `@Get`, `@UseGuards`) provide declarative API definitions that align with our engineering rules (thin controllers, guard-based authorization).
   889→  1088→
   890→  1089→### DD-09: App Router, Not Pages Router
   891→  1090→
   892→  1091→**Decision:** Use Next.js App Router (`app/` directory) exclusively.
   893→  1092→
   894→  1093→**Rationale:** The App Router supports React Server Components, which allow page-level data fetching via `async/await` without client-side JavaScript. This reduces the client-side JavaScript bundle and improves Core Web Vitals (especially LCP and FID). Server Components are the default; the `'use client'` directive is added only where needed. The Pages Router does not support Server Components and is considered legacy by Next.js.
   895→  1094→
   896→  1095→### DD-10: Zustand, Not Redux
   897→  1096→
   898→  1097→**Decision:** Use Zustand for client-side state management.
   899→  1098→
   900→  1099→**Rationale:**
   901→  1100→
   902→  1101→| Factor | Zustand | Redux Toolkit |
   903→  1102→|--------|---------|---------------|
   904→  1103→| Boilerplate | Minimal — no actions, reducers, providers | Significant — slice, asyncThunk, configureStore |
   905→  1104→| Bundle size | ~1 KB | ~11 KB |
   906→  1105→| Learning curve | Low — hooks-based API | Medium — requires understanding thunks, selectors |
   907→  1106→| TypeScript | First-class, simple | Good but verbose |
   908→  1107→
   909→  1108→Zustand's minimal API reduces boilerplate while providing the same capabilities (selectors, middleware for persistence, devtools integration). Since TanStack Query handles all server state, Zustand only manages simple UI state (theme, sidebar, selection), where its simplicity is a perfect fit.
   910→  1109→
   911→  1110→### DD-11: Feature-Based Folders, Not Type-Based
   912→  1111→
   913→  1112→**Decision:** Organize frontend code by feature (`features/chat/`), not by type (`components/`, `hooks/`, `stores/`).
   914→  1113→
   915→  1114→**Rationale:** Feature-based organization ensures that all code related to a domain concept lives in one place. A feature is self-contained and deletable — removing the `features/chat/` directory removes chat without affecting agents or knowledge. Type-based organization scatters related code across multiple directories, making it harder to understand, modify, and delete features. The engineering rules enforce this with the principle: "A feature must be deletable without affecting other features."
   916→  1115→
   917→  1116→### DD-12: CSS Logical Properties, Not Physical Properties
   918→  1117→
   919→  1118→**Decision:** Use `ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*` exclusively. Never use `left`, `right`, `ml-*`, `mr-*`.
   920→  1119→
   921→  1120→**Rationale:** HotHoosh is Persian-first and RTL-native. CSS logical properties automatically adapt to the document's `dir` attribute. When `dir="rtl"`, `margin-inline-start` maps to `margin-right`; when `dir="ltr"`, it maps to `margin-left`. Physical properties (`margin-left`) require manual RTL/LTR conditionals in every component. Logical properties make bidirectional support automatic and eliminates an entire class of RTL bugs.
   922→  1121→
   923→  1122→### DD-13: Solar Hijri Calendar
   924→  1123→
   925→  1124→**Decision:** Use Solar Hijri (شمسی) as the default calendar. Gregorian available as secondary.
   926→  1125→
   927→  1126→**Rationale:** HotHoosh targets Iranian enterprises. The Solar Hijri calendar is the official calendar of Iran, used for business operations, financial reporting, and legal documents. Displaying Gregorian dates as the default would be a localization failure. Day.js with the `jalaali-js` plugin provides Solar Hijri support with the same API as standard date handling.
   928→  1127→
   929→  1128→### DD-14: SSE, Not WebSocket for AI Streaming
   930→  1129→
   931→  1130→**Decision:** Use Server-Sent Events (`text/event-stream`) for all AI response streaming.
   932→  1131→
   933→  1132→**Rationale:**
   934→  1133→
   935→  1134→| Factor | SSE | WebSocket |
   936→  1135→|--------|-----|-----------|
   937→  1136→| Direction | Server → Client (unidirectional) | Bidirectional |
   938→  1137→| Complexity | Simple — built on HTTP | Complex — handshake, framing, ping/pong |
   939→  1138→| Proxy compatibility | Works through all proxies, CDNs, load balancers | Requires special proxy configuration (Upgrade header) |
   940→  1139→| Reconnection | Browser auto-reconnects | Manual reconnection logic |
   941→  1140→| HotHoosh need | Server pushes AI tokens to client | Client only sends messages via POST |
   942→  1141→
   943→  1142→AI response streaming is inherently unidirectional: the server generates tokens and the client displays them. The client sends messages via standard `POST` requests. There is no need for bidirectional communication. SSE is simpler, more robust, and works through all network infrastructure without special configuration.
   944→  1143→
   945→  1144→### DD-15: TypeORM, Not Prisma
   946→  1145→
   947→  1146→**Decision:** Use TypeORM as the ORM for NestJS.
   948→  1147→
   949→  1148→**Rationale:** TypeORM provides native PostgreSQL support including custom repository classes (essential for the repository pattern mandated by Engineering Rules §10.4.2), direct access to migration tooling, and fine-grained query control needed for complex operations (recursive CTEs for branch traversal, JSONB queries, pgvector operations). While Prisma offers a cleaner query API, TypeORM's custom repository support better aligns with our hexagonal architecture where repositories are the data access boundary.
   950→  1149→
   951→  1150→### DD-16: Invitation-Only Registration
   952→  1151→
   953→  1152→**Decision:** Users cannot self-register. All access is via organization invitation.
   954→  1153→
   955→  1154→**Rationale:** HotHoosh is an enterprise product, not a consumer SaaS. Open registration creates security risks (unauthorized access, spam accounts) and administrative burden. Invitation-only registration ensures that every user is explicitly authorized by an organization admin, tied to a specific role and organizational scope. This aligns with enterprise security requirements and Iranian enterprise governance practices.
   956→  1155→
   957→  1156→### DD-17: Hybrid Search (Vector + BM25), Not Vector Only
   958→  1157→
   959→  1158→**Decision:** Combine pgvector HNSW cosine similarity with PostgreSQL BM25 full-text search using Reciprocal Rank Fusion.
   960→  1159→
   961→  1160→**Rationale:** Vector search excels at semantic similarity but misses exact keyword matches. BM25 excels at keyword matching but misses semantic relationships. Hybrid search with RRF (k=60) combines the strengths of both. For Persian text specifically, exact keyword matching is critical because Persian morphology (prefixes, suffixes, zero-width non-joiners) can cause vector embeddings to miss matches that a full-text search catches easily.
   962→  1161→
   963→  1162→### DD-18: Bigint Auto-Increment for High-Throughput Tables
   964→  1163→
   965→  1164→**Decision:** Use BIGINT auto-increment (not UUID v7) for `audit_logs`, `usage_logs`, `chat_messages`, and `system_logs`.
   966→  1165→
   967→  1166→**Rationale:** UUID v7 is 128 bits (16 bytes) vs BIGINT which is 64 bits (8 bytes). On append-only tables that receive millions of inserts per month, halving the primary key size significantly reduces storage and index size. BIGINT auto-increment also provides optimal B-tree insert performance (sequential, no page splits). UUID v7 is used for all other tables where the benefits of global uniqueness and time-sortability outweigh the storage cost.
