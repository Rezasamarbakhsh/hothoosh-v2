     3→     3→## HotHoosh — Non-Violable Engineering Standards
     4→     4→
     5→     5→---
     6→     6→
     7→     7→> **These rules are mandatory.** Every line of code, every commit, every pull request, and every deployment must comply. There are no exceptions. If a rule feels wrong, propose an amendment through the RFC process — do not violate it.

    11→    11→## 10.1 Code Style
    12→    12→
    13→    13→### 10.1.1 TypeScript
    14→    14→
    15→    15→**Strict Mode is non-negotiable.** The following `tsconfig.json` settings are required across all packages:
    16→    16→
    17→    17→```json
    18→    18→{
    19→    19→  "compilerOptions": {
    20→    20→    "strict": true,
    21→    21→    "noUncheckedIndexedAccess": true,
    22→    22→    "noImplicitOverride": true,
    23→    23→    "noPropertyAccessFromIndexSignature": true,
    24→    24→    "exactOptionalPropertyTypes": true,
    25→    25→    "noFallthroughCasesInSwitch": true,
    26→    26→    "forceConsistentCasingInFileNames": true,
    27→    27→    "noUnusedLocals": true,
    28→    28→    "noUnusedParameters": true,
    29→    29→    "noImplicitReturns": true,
    30→    30→    "noEmit": false
    31→    31→  }
    32→    32→}
    33→    33→```
    34→    34→
    35→    35→**Type rules:**
    36→    36→
    37→    37→| Rule | Description |
    38→    38→|------|-------------|
    39→    39→| No `any` | Use `unknown` and narrow with type guards. `any` is only permitted in generic constraint positions (`<T extends any>`). |
    40→    40→| No `as` casts | Prefer type guards, `satisfies`, and `zod` parsing. `as` is only permitted when converting between branded types or when a type guard is infeasible and the cast is documented with a `// SAFETY:` comment. |
    41→    41→| No non-null assertion | Never use `!` postfix. Use optional chaining, nullish coalescing, or early returns. |
    42→    42→| Prefer `interface` for objects | Use `interface` for object shapes and API contracts. Use `type` for unions, intersections, and utility types. |
    43→    43→| Branded types for IDs | All entity IDs use branded types: `type UserId = string & { readonly __brand: 'UserId' }`. This prevents accidental ID misuse. |
    44→    44→| Discriminated unions for state | All state machines, API responses with multiple shapes, and entity statuses must use discriminated unions, not optional fields. |
    45→    45→| Explicit return types on exports | Every exported function, method, and hook must have an explicit return type annotation. Internal functions may rely on inference. |
    46→    46→| No default exports | Every module uses named exports only. This improves refactoring tooling and tree-shaking. |
    47→    47→| Enum ban | Do not use TypeScript `enum`. Use `as const` objects with `type ValueType = typeof Object[keyof typeof Object]` instead. Enums emit runtime code and have subtle type-safety holes. |
    48→    48→
    49→    49→**Formatting (enforced by Prettier, not debated):**
    50→    50→
    51→    51→```json
    52→    52→{
    53→    53→  "semi": true,
    54→    54→  "singleQuote": false,
    55→    55→  "trailingComma": "all",
    56→    56→   "printWidth": 100,
    57→    57→  "tabWidth": 2,
    58→    58→  "bracketSpacing": true,
    59→    59→  "arrowParens": "always",
    60→    60→  "endOfLine": "lf"
    61→    61→}
    62→    62→```

    64→    64→### 10.1.2 Frontend (React / Next.js)
    65→    65→
    66→    66→**Component rules:**
    67→    67→
    68→    68→| Rule | Description |
    69→    69→|------|-------------|
    70→    70→| Functional components only | No class components. Ever. No exceptions. No legacy wrappers. |
    71→    71→| No default props | Use JavaScript default parameters instead of `Component.defaultProps`. |
    72→    72→| No `propTypes` | TypeScript types replace runtime prop validation entirely. |
    73→    73→| Destructure props at signature | Always destructure props in the function signature, not inside the body. |
    74→    74→| No forwarding refs manually | Use `React.forwardRef` only when wrapping a native element. For component-to-component ref forwarding, use the `ref` prop as a regular prop. |
    75→    75→| Component file structure | Order within a component file: (1) imports, (2) types, (3) constants, (4) helper functions, (5) hooks, (6) component, (7) sub-components, (8) export. |
    76→    76→| Max component length | A single component function body must not exceed 120 lines. If it does, extract sub-components or custom hooks. |
    77→    77→| Max hook file length | A single custom hook file must not exceed 150 lines. If it does, decompose into smaller hooks. |
    78→    78→| No `useEffect` for data fetching | All server data fetching uses TanStack Query. `useEffect` is only for subscriptions, event listeners, and DOM side effects. |
    79→    79→| No `useState` for derived state | If a value can be computed from existing state or props, compute it inline or with `useMemo`. Do not store it in a separate `useState`. |
    80→    80→| Colocate related files | A component, its styles, its types, and its tests live in the same directory. The component file is `index.tsx`. Tests are `*.test.tsx`. Types are `types.ts`. |
    81→    81→
    82→    82→**JSX rules:**
    83→    83→
    84→    84→| Rule | Description |
    85→    85→|------|-------------|
    86→    86→| Boolean props shorthand | Use `<Modal open />` not `<Modal open={true} />`. |
    87→    87→| String props shorthand | Use `<Input placeholder="..." />` with double quotes for string props. |
    88→    88→| No complex expressions in JSX | If a JSX expression spans more than 2 lines, extract it to a variable or a `render*` function. |
    89→    89→| No inline arrow functions for event handlers in JSX | Define event handlers as named functions inside the component, not inline. Exception: trivial one-liners like `onClick={() => setOpen(false)}`. |
    90→    90→| Fragment shorthand | Use `<>...</>` not `<Fragment>...</Fragment>` unless you need a `key` prop. |
    91→    91→| No array index as key | Never use array index as the `key` prop. Use stable, unique identifiers. |
    92→    92→| Conditional rendering | For large conditional blocks, extract to separate components. For small conditions, use ternary or `&&`. Never nest ternaries. |
    93→    93→| Image components | Always use `next/image` for images. Provide `width`, `height`, and `alt` (in Persian) for all images. |
    94→    94→| Link components | Always use `next/link` for internal navigation. Use `<a>` only for external links with `target="_blank" rel="noopener noreferrer"`. |
    95→    95→
    96→    96→**Hook rules:**
    97→    97→
    98→    98→| Rule | Description |
    99→    99→|------|-------------|
   100→   100→| Custom hook naming | All custom hooks start with `use` and are named in camelCase: `useUser`, `useAdminFilters`, `useKnowledgeSearch`. |
   101→   101→| No conditional hooks | Hooks must not be called inside conditions, loops, or nested functions. This is a React rule, not a style preference. |
   102→   102→| Extract complex logic to hooks | If a component has more than 3 `useState` calls or more than 2 `useEffect` calls, extract the related logic into a custom hook. |
   103→   103→| Hook return type | Custom hooks that return multiple values must return a named tuple or an object with explicit types. Never return unnamed arrays. |
   104→   104→| No hooks in utility files | Utility functions live in `utils/`. Hooks live in `hooks/`. Never mix them. |
   105→   105→
   106→   106→### 10.1.3 Backend (NestJS)
   107→   107→
   108→   108→**Module rules:**
   109→   109→
   110→   110→| Rule | Description |
   111→   111→|------|-------------|
   112→   112→| Single responsibility modules | Each NestJS module encapsulates exactly one domain concept. A module that manages both users and organizations violates this rule. |
   113→   113→| Module boundary enforcement | Modules communicate through public APIs (injected services), never through shared mutable state. Module-private implementations are never exported. |
   114→   114→| No circular dependencies | If Module A needs Module B and Module B needs Module A, extract the shared concern into a third Module C. Circular dependencies are a design smell, not an inconvenience. |
   115→   115→| Controller thinness | Controllers handle HTTP concerns only: request parsing, response shaping, status codes. All business logic lives in services. A controller method must not exceed 15 lines. |
   116→   116→| Service isolation | Services are injected via DI. A service must never import another module's internal files. It depends only on the injected service's public interface. |
   117→   117→| Guard composition | Authentication and authorization are enforced via NestJS guards, not manual checks in controllers or services. |
   118→   118→
   119→   119→**DTO rules:**
   120→   120→
   121→   121→| Rule | Description |
   122→   122→|------|-------------|
   123→   123→| Zod for all DTOs | All DTOs use Zod schemas for validation. NestJS `class-validator` is not used. Zod schemas are defined alongside or inside the DTO file and used with a `ZodValidationPipe`. |
   124→   124→| Separate DTOs per operation | One DTO for create, one for update, one for response. Never reuse the same DTO for different operations. Response DTOs never contain password hashes, internal IDs, or other sensitive fields. |
   125→   125→| DTO naming | Create DTOs: `CreateUserDto`, `CreateAgentDto`. Update DTOs: `UpdateUserDto`, `UpdateAgentDto`. Response DTOs: `UserResponseDto`, `AgentResponseDto`. List response DTOs: `UserListResponseDto` (contains pagination metadata). |
   126→   126→| Pick/Omit for variations | When update DTOs differ from create DTOs only by making fields optional, use `z.infer<typeof CreateDto>.partial()` and add additional constraints. |
   127→   127→
   128→   128→**Error handling rules:**
   129→   129→
   130→   130→| Rule | Description |
   131→   131→|------|-------------|
   132→   132→| Domain exceptions | Each domain defines its own exception class extending `DomainException`. Examples: `UserNotFoundException`, `InsufficientTokenQuotaException`, `AgentAlreadyActiveException`. |
   133→   133→| Exception filters | A global exception filter catches all unhandled exceptions and returns a standardized error response. Never let raw stack traces reach the client. |
   134→   134→| HTTP status mapping | Domain exceptions map to specific HTTP status codes via the exception class definition, not in the controller. |
   135→   135→| Error response format | All error responses follow the same JSON structure: `{ error: { code: string, message: string, details?: Record<string, unknown> } }`. The `message` field is in the user's language (Persian for Persian users, English for English users). |
   136→   136→| Never swallow errors | Empty catch blocks are forbidden. If an error is intentionally handled, add a comment explaining why it's safe to ignore. |
   137→   137→| Never throw non-Error | Always throw instances of `Error` or its subclasses. Never throw strings, numbers, or objects. |
   138→   138→
   139→   139→### 10.1.4 CSS / Tailwind
   140→   140→
   141→   141→| Rule | Description |
   142→   142→|------|-------------|
   143→   143→| RTL logical properties only | Use `ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `inline-*`, `block-*`. Never use `left`, `right`, `ml-*`, `mr-*`, `pl-*`, `pr-*`. |
   144→   144→| Tailwind for layout, design tokens for theme | Layout (flex, grid, spacing, sizing) uses Tailwind utility classes. Colors, shadows, and effects use design token CSS variables via `var(--color-accent)`. |
   145→   145→| No `!important` | If Tailwind's `!` prefix doesn't suffice, restructure the specificity. `!important` in custom CSS is forbidden. |
   146→   146→| No inline styles | Inline `style={{}}` is forbidden except for dynamically computed values (e.g., chart colors from API data). All static styling uses Tailwind or CSS modules. |
   147→   147→| BEM for complex components | When a component's styling complexity exceeds what Tailwind utilities reasonably express, use a single CSS module file with BEM naming: `.chat-input`, `.chat-input__send-btn`, `.chat-input--focused`. |
   148→   148→| No hardcoded colors | Never hardcode hex, rgb, or hsl values. Use design tokens. The only exception is `transparent` and `currentColor`. |
   149→   149→| No hardcoded font sizes | All font sizes use the type scale defined in the design system (caption-sm, body-sm, body-md, heading-lg, etc.). |
   150→   150→| No hardcoded spacing | Use the spacing scale (4px increments) via Tailwind (p-4, gap-2, etc.) or CSS variables for semantic spacing. |
   151→   151→| Animation performance | Only animate `transform` and `opacity`. Never animate `width`, `height`, `top`, `left`, `margin`, or `padding`. Use `will-change` sparingly and only for elements that actually animate. |
   152→   152→| Dark mode via CSS variables | Dark mode is implemented by switching CSS variable values on `:root` and `[data-theme="dark"]`. Tailwind's `dark:` variant is not used. |
   153→   153→
   154→   154→### 10.1.5 General Code Hygiene
   155→   155→
   156→   156→| Rule | Description |
   157→   157→|------|-------------|
   158→   158→| No `console.log` | All logging uses a structured logger. On the frontend, use the `logger` utility. On the backend, use NestJS `Logger` service. `console.log`, `console.warn`, and `console.error` are forbidden in committed code. |
   159→   159→| No TODO without a ticket | `// TODO` comments must include a ticket reference: `// TODO(HOT-1234): implement retry logic`. Plain `// TODO` is forbidden. |
   160→   160→| No commented-out code | Delete dead code. Git preserves history. Commented-out code creates noise and confusion. |
   161→   161→| No magic numbers | Extract all non-obvious numbers to named constants: `const MAX_RETRY_ATTEMPTS = 3`. Zero, one, and negative one as initial values are exempt. |
   162→   162→| No deep nesting | Maximum indentation level is 4. If you exceed this, use early returns, extract functions, or use `async/await` to flatten promise chains. |
   163→   163→| Function length | Functions must not exceed 30 lines. If they do, decompose. |
   164→   164→| Parameter count | Functions must not accept more than 4 parameters. If more are needed, use an options object. |
   165→   165→| File length | Files must not exceed 300 lines. If they do, split into smaller modules. |
   166→   166→| Import order | Imports are organized in this exact order with blank line separators: (1) React/Next.js, (2) third-party libraries, (3) internal packages (`@hotHoosh/*`), (4) relative imports (`./`, `../`). Within each group, imports are alphabetized. |
   167→   167→| No barrel exports in hot paths | `index.ts` barrel files are permitted for leaf modules (components, utils). They are forbidden for service modules, API clients, and any module that would cause unnecessary re-evaluation. |

   482→   482→### 10.2.5 Folder Structure Rules
   483→   483→
   484→   484→| Rule | Description |
   485→   485→|------|-------------|
   486→   486→| Feature-based, not type-based | Frontend code is organized by feature (`features/chat/`), not by type (`components/`, `hooks/`). Type-based directories exist only for shared/app-level code. |
   487→   487→| Feature self-containment | Each feature directory contains everything it needs: components, hooks, stores, services, types, and tests. A feature must be deletable without affecting other features. |
   488→   488→| Colocate tests | Test files live alongside the files they test. Unit tests: `foo.ts` → `foo.spec.ts`. Component tests: `button.tsx` → `button.test.tsx`. E2E tests for a module: `__tests__/` directory inside the module. |
   489→   489→| Colocate DTOs with their module | DTOs live in the module's `dto/` directory, not in a shared DTO folder. Shared validation schemas (used across modules) live in `packages/shared/src/validators/`. |
   490→   490→| No `utils/` dumping ground | The `utils/` directory is for pure functions with no domain coupling. Domain logic goes into services. UI logic goes into hooks or components. |
   491→   491→| No `helpers/` directory | Use `utils/` for pure utilities and `lib/` for configuration/initialization. `helpers/` is a forbidden directory name. |
   492→   492→| Deep nesting limit | Maximum directory depth from package root is 7 levels. If you exceed this, flatten the structure. |
   493→   493→| Index files for public API | Each feature/module has an `index.ts` that exports only the public API. Internal files are not exported. |

   589→   589→## 10.4 Architecture
   590→   590→
   591→   591→### 10.4.1 Frontend Architecture Rules
   592→   592→
   593→   593→| Rule | Description |
   594→   594→|------|-------------|
   595→   595→| App Router only | All routing uses Next.js App Router (`app/` directory). The `pages/` directory does not exist. |
   596→   596→| Server Components by default | All components are React Server Components unless they explicitly need interactivity. Add `'use client'` only when the component uses hooks, event handlers, or browser APIs. |
   597→   597→| Client boundary at feature level | The `'use client'` directive is placed at the feature component level (e.g., the chat input), not on every small interactive element. Child components of a client component are automatically client components. |
   598→   598→| Data fetching on server | Page-level data fetching uses Server Components with `async/await` and direct database or service calls (via Next.js server actions or API routes). Client-side data fetching uses TanStack Query. |
   599→   599→| No client-side `fetch` in components | Components never call `fetch()` directly. All API communication goes through TanStack Query hooks or server actions. |
   600→   600→| State management boundaries | **Server state** (API data) → TanStack Query. **Client state** (UI state) → Zustand. **Form state** → React Hook Form + Zod. **URL state** → Next.js `useSearchParams`. Never overlap these boundaries. |
   601→   601→| No global CSS side effects | Styles are scoped. Global styles are limited to `globals.css` for design tokens, font faces, and Tailwind base/reset. Component styles never leak. |
   602→   602→| Error boundaries | Every route segment has an `error.tsx` boundary. Every feature with async operations has a React error boundary wrapper. |
   603→   603→| Loading states | Every route segment with async data has a `loading.tsx` that renders a skeleton matching the page layout. |
   604→   604→| No direct DOM manipulation | Use React refs only for focus management, scroll positioning, and integrating non-React libraries. Never use `document.querySelector`, `innerHTML`, or `addEventListener` outside of custom hooks. |
   605→   605→| Feature isolation | Features communicate through shared types and the event system (if needed), not through direct imports of each other's internal files. A feature may import from `packages/ui`, `packages/shared`, and its own internal files only. |
   606→   606→
   607→   607→### 10.4.2 Backend Architecture Rules
   608→   608→
   609→   609→| Rule | Description |
   610→   610→|------|-------------|
   611→   611→| Hexagonal modules | Each domain module has a clear boundary. Controllers define the API, services contain business logic, and repositories (via TypeORM/Prisma) handle data access. The module's internal implementation is not exported. |
   612→   612→| Dependency injection | All dependencies are injected via NestJS DI container. No manual `new` instantiation of services. No import of service files directly — always inject via constructor. |
   613→   613→| Repository pattern | Data access goes through repository classes (TypeORM custom repositories or Prisma service wrappers). Controllers and services never use `createQueryBuilder` directly — that's the repository's responsibility. |
   614→   614→| Domain events | Modules communicate through a domain event system. When `UserService` creates a user, it emits `UserCreatedEvent`. `AuditService` and `BillingService` listen for this event. Modules never import each other's services directly for cross-domain operations. |
   615→   615→| No anemic domain models | Entities contain behavior, not just data. A `User` entity has methods like `canAccessWorkspace()`, `hasRole()`, `isActive()`, not just properties. |
   616→   616→| CQRS for complex operations | Read-heavy and write-heavy operations are separated when they have significantly different requirements. Query services handle reads (optimized for speed). Command services handle writes (optimized for consistency). Simple CRUD does not require CQRS. |
   617→   617→| Interface segregation | Services define narrow interfaces for what they need from other services. A service that only needs to check if a user exists should depend on a `UserExistsChecker` interface, not the full `UserService`. |
   618→   618→| Configuration over hardcoding | All configurable values (timeouts, limits, feature flags) are defined in the configuration module and injected via `ConfigService`. No magic strings or hardcoded values in business logic. |
   619→   619→| Graceful degradation | External service failures (AI provider down, storage unavailable) must not crash the application. Implement circuit breakers, fallbacks, and retry logic. Return degraded responses, not 500 errors. |
   620→   620→| Transaction boundaries | Database transactions are managed at the service method level, not the controller level. Use NestJS `TransactionManager` or the unit of work pattern. |
   621→   621→
   622→   622→### 10.4.3 API Design Rules
   623→   623→
   624→   624→| Rule | Description |
   625→   625→|------|-------------|
   626→   626→| RESTful resource naming | Resources are plural nouns: `/users`, `/agents`, `/knowledge-bases`, `/memory-packs`. No verbs in URLs. |
   627→   627→| Consistent URL structure | `/{api-version}/{resource}/{id}/{sub-resource}/{sub-id}`. Example: `/v1/organizations/org_123/companies` |
   628→   628→| HTTP methods correctly used | `GET` = read (never modify state), `POST` = create, `PUT` = full replace, `PATCH` = partial update, `DELETE` = delete. |
   629→   629→| Pagination on all list endpoints | Every `GET` endpoint that returns a list supports pagination: `?page=1&limit=20` (offset-based) or `?cursor=xxx&limit=20` (cursor-based). |
   630→   630→| Filtering on list endpoints | Every list endpoint supports filtering via query parameters. Filter parameter names match the response field names: `?status=active&role=admin`. |
   631→   631→| Sorting on list endpoints | Every list endpoint supports sorting: `?sort=created_at&order=desc`. Multi-sort: `?sort=status,created_at&order=asc,desc`. |
   632→   632→| Consistent response envelope | All responses use: `{ data: T, meta?: { page, limit, total, hasMore } }`. Error responses use: `{ error: { code, message, details } }`. |
   633→   633→| API versioning | URL-based versioning: `/v1/`, `/v2/`. No header-based or query-based versioning. |
   634→   634→| Idempotency | `PUT` and `DELETE` are always idempotent. `POST` is idempotent when an `Idempotency-Key` header is provided. |
   635→   635→| Rate limiting | All API endpoints are rate-limited. Limits are configurable per route, per user tier, and per IP. Rate limit headers (`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`) are included in responses. |
   636→   636→| HATEOAS-lite | List responses include `_links` for pagination: `{ _links: { self, next, prev } }`. Detail responses include `_links` for related resources. |
   637→   637→| No nested resource depth > 2 | Maximum URL depth: `/{resource}/{id}/{sub-resource}`. Deeper nesting is forbidden. Use query parameters or separate endpoints instead. |
   638→   638→| Streaming via SSE | All AI streaming responses use Server-Sent Events (`text/event-stream`). No WebSocket for request-response streaming. |
   639→   639→
   640→   640→### 10.4.4 State Management Architecture
   641→   641→
   642→   642→**Zustand store rules:**
   643→   643→
   644→   644→| Rule | Description |
   645→   645→|------|-------------|
   646→   646→| One store per concern | Each store manages one domain of client state. Do not create god stores. |
   647→   647→| Store as state machine | When state has distinct modes (idle → loading → success → error), model it explicitly, not as a collection of independent booleans. Use a `status` field with a discriminated union type. |
   648→   648→| No derived state in stores | If a value can be computed from store state, compute it in the component using a selector. Do not store it. |
   649→   649→| Persist only when needed | Use `zustand/middleware` persist only for user preferences (theme, sidebar state). Never persist server state (that's TanStack Query's job). |
   650→   650→| Store actions are pure | Store actions modify state synchronously. Async operations (API calls) live in TanStack Query mutations, which call store actions on success. |
   651→   651→| Selectors for performance | Components read store state via selectors, not by subscribing to the entire store. `useThemeStore(s => s.theme)`, not `useThemeStore()`. |
   652→   652→
   653→   653→**TanStack Query rules:**
   654→   654→
   655→   655→| Rule | Description |
   656→   656→|------|-------------|
   657→   657→| Query keys are structured | Use a key factory function: `adminKeys.agents.detail(agentId)`. Never use raw strings. |
   658→   658→| Stale time configured | Every query has an explicit `staleTime` and `gcTime`. Server data that changes infrequently has longer stale times. Real-time data has shorter stale times or uses polling. |
   659→   659→| Optimistic updates for mutations | Create, update, and delete mutations optimistically update the cache. Roll back on error. |
   660→   660→| Error boundaries per query | Query errors are caught by React error boundaries, not by `try/catch` in components. |
   661→   661→| No `useQuery` in event handlers | Queries are declared at the component level. Event handlers trigger mutations, not queries. To refetch, use `queryClient.invalidateQueries()`. |
   662→   662→| Prefetch on hover | Navigation links prefetch their target page's data on hover using `queryClient.prefetchQuery()`. |
   663→   663→| Infinite queries for large lists | Audit logs, system logs, and any list that exceeds 10,000 records use `useInfiniteQuery`. |

   667→   667→## 10.5 Testing
   668→   668→
   669→   669→### 10.5.1 Testing Principles
   670→   670→
   671→   671→| Principle | Description |
   672→   672→|-----------|-------------|
   673→   673→| Tests are code | Tests are held to the same quality standards as production code. They must be readable, well-named, and maintainable. |
   674→   674→| Test behavior, not implementation | Tests verify what the system does (outputs, side effects), not how it does it (internal function calls, variable assignments). |
   675→   675→| No test interdependency | Each test must run in isolation. No test depends on another test's execution order, side effects, or database state. |
   676→   676→| Deterministic | Tests must produce the same result every time. No reliance on wall-clock time, random values, or external service availability. Mock time, randomness, and external calls. |
   677→   677→| Fast | Unit tests run in milliseconds. Integration tests run in seconds. The full test suite completes in under 5 minutes. If a test is slow, profile and fix it. |
   678→   678→
   679→   679→### 10.5.2 Test Structure
   680→   680→
   681→   681→Every test file follows the **AAA pattern** (Arrange, Act, Assert):
   682→   682→
   683→   683→```typescript
   684→   684→describe('UserService', () => {
   685→   685→  describe('createUser', () => {
   686→   686→    it('should create a user with valid data and emit UserCreatedEvent', async () => {
   687→   687→      // Arrange
   688→   688→      const dto = createValidUserDto();
   689→   689→      const hashedPassword = 'hashed_password';
   690→   690→      passwordService.hash.mockResolvedValue(hashedPassword);
   691→   691→
   692→   692→      // Act
   693→   693→      const result = await userService.createUser(dto);
   694→   694→
   695→   695→      // Assert
   696→   696→      expect(result).toEqual(expect.objectContaining({
   697→   697→        email: dto.email,
   698→   698→        displayName: dto.displayName,
   699→   699→      }));
   700→   700→      expect(eventBus.emit).toHaveBeenCalledWith(
   701→   701→        expect.any(UserCreatedEvent),
   702→   702→      );
   703→   703→    });
   704→   704→  });
   705→   705→});
   706→   706→```
   707→   707→
   708→   708→### 10.5.3 Naming Conventions
   709→   709→
   710→   710→| Context | Convention | Example |
   711→   711→|---------|-----------|--------|
   712→   712→| `describe` block | The unit under test | `describe('UserService')`, `describe('useChatMessages')` |
   713→   713→| Nested `describe` | The method or scenario | `describe('createUser')`, `describe('when user is suspended')` |
   714→   714→| `it` / `test` block | Expected behavior, starting with 'should' | `it('should throw UserNotFoundException when user does not exist')` |
   715→   715→| Test file | Same name as source + `.spec.ts` or `.test.tsx` | `users.service.spec.ts`, `button.test.tsx` |
   716→   716→| Test directory | `__tests__/` inside the module | `modules/users/__tests__/` |
   717→   717→| E2E test file | `*.e2e-spec.ts` | `auth.e2e-spec.ts` |
   718→   718→| Mock files | `*.mock.ts` | `users.service.mock.ts`, `llm-provider.mock.ts` |
   719→   719→| Fixture files | `*.fixture.ts` | `users.fixture.ts`, `chat-messages.fixture.ts` |
   720→   720→
   721→   721→### 10.5.4 Unit Testing Rules
   722→   722→
   723→   723→| Rule | Description |
   724→   724→|------|-------------|
   725→   725→| Cover business logic | Every service method, utility function, and custom hook with non-trivial logic must have unit tests. |
   726→   726→| No testing framework globals | Import `describe`, `it`, `expect` from the test framework. Do not rely on globals. |
   727→   727→| Mock at boundaries | Mock external dependencies (database, HTTP, file system, AI providers). Do not mock the unit under test. |
   728→   728→| Use test factories | Create factory functions for generating test data: `createUserDto(overrides?)`, `createAgentEntity(overrides?)`. Do not hardcode test data inline. |
   729→   729→| Test edge cases | For every function, test: happy path, empty input, null/undefined input, boundary values, error cases. |
   730→   730→| Test error paths | Verify that functions throw the correct exception type and message when given invalid input. |
   731→   731→| No implementation details | Do not test private methods, internal variable assignments, or function call counts unless verifying side effects. |
   732→   732→| Minimum 90% coverage on services | Service layer must maintain 90%+ branch coverage. Other layers: 80%+. |
   733→   733→
   734→   734→### 10.5.5 Integration Testing Rules
   735→   735→
   736→   736→| Rule | Description |
   737→   737→|------|-------------|
   738→   738→| Test API contracts | Every API endpoint has an integration test that verifies the request/response contract. |
   739→   739→| Use test database | Integration tests use a dedicated test database (PostgreSQL). Tests are responsible for setup and teardown. |
   740→   740→| Test with real dependencies | Integration tests use real database queries (TypeORM/Prisma), real Zod validation, and real NestJS DI. Only external services (AI providers, S3) are mocked. |
   741→   741→| Test authentication and authorization | Verify that protected endpoints reject unauthenticated requests and that role-based access control works correctly. |
   742→   742→| Test file uploads | Verify that file upload endpoints accept valid files and reject invalid types/sizes. |
   743→   743→| Test pagination, filtering, sorting | List endpoints must have tests verifying pagination behavior, filter combinations, and sort directions. |
   744→   744→
   745→   745→### 10.5.6 E2E Testing Rules
   746→   746→
   747→   747→| Rule | Description |
   748→   748→|------|-------------|
   749→   749→| Critical user journeys only | E2E tests cover the 10-15 most critical user journeys: registration, login, create chat, send message, create agent, upload knowledge base, admin CRUD operations. |
   750→   750→| No E2E for edge cases | Edge cases are covered by unit and integration tests. E2E tests verify that the system works end-to-end for normal flows. |
   751→   751→| Independent test database | E2E tests run against a dedicated, isolated database that is reset between test suites. |
   752→   752→| Page Object Model | E2E tests use the Page Object pattern. Page objects encapsulate selectors and interactions. Tests use page objects, not raw CSS selectors. |
   753→   753→| Visual regression | Key pages have visual regression snapshots. Tests fail if the UI changes unexpectedly. |
   754→   754→| Run in CI only | E2E tests are too slow for local development. They run in CI pipelines. |
   755→   755→
   756→   756→### 10.5.7 Component Testing Rules
   757→   757→
   758→   758→| Rule | Description |
   759→   759→|------|-------------|
   760→   760→| Render, act, assert | Use `@testing-library/react`: render the component, perform user actions with `fireEvent` or `userEvent`, assert on the rendered output. |
   761→   761→| Query by role, not by class | Use `screen.getByRole()`, `screen.getByLabelText()`, `screen.getByText()`. Never use `container.querySelector` or `getByTestId` except as a last resort. |
   762→   762→| Test user-visible behavior | Test what the user sees and does. Do not test internal state variables or whether a specific function was called (unless verifying a side effect like navigation or API call). |
   763→   763→| Test accessibility | Verify that interactive elements are accessible: buttons have accessible names, forms have labels, modals trap focus. |
   764→   764→| Test loading, error, and empty states | Every component that fetches data has tests for its loading skeleton, error state, and empty state. |

   768→   768→## 10.6 Security
   769→   769→
   770→   770→### 10.6.1 Authentication Rules
   771→   771→
   772→   772→| Rule | Description |
   773→   773→|------|-------------|
   774→   774→| Dual-token JWT | Access token: RS256, 15-minute expiry, in `Authorization: Bearer` header. Refresh token: HS256, 7-day expiry, in `HttpOnly`, `Secure`, `SameSite=Strict` cookie. |
   775→   775→| No JWT in localStorage | Access tokens are stored in memory only. On page refresh, a silent refresh is triggered using the refresh token cookie. |
   776→   776→| Token rotation on refresh | Every refresh token usage generates a new refresh token and invalidates the old one (rotation). If a previously-used refresh token is presented again, all sessions for that user are revoked (theft detection). |
   777→   777→| Password hashing | Argon2id with OWASP-recommended parameters. Never use MD5, SHA-1, SHA-256, or bcrypt (Argon2id is resistant to GPU attacks). |
   778→   778→| Password policy enforcement | Minimum 8 characters, at least one uppercase, one lowercase, one number, one special character. Checked on both client and server. |
   779→   779→| Rate limiting on auth endpoints | Login: 5 attempts per minute per IP, 10 per hour per account. Password reset: 3 per hour per email. Registration: 5 per hour per IP. |
   780→   780→| Account lockout | After 10 failed login attempts within 1 hour, the account is locked for 30 minutes. The user is notified via email. |
   781→   781→
   782→   782→### 10.6.2 Authorization Rules
   783→   783→
   784→   784→| Rule | Description |
   785→   785→|------|-------------|
   786→   786→| 3-layer RBAC | Organization role → Workspace role → Resource-level permissions. All three layers are checked for every authenticated request. |
   787→   787→| Permission checks on server | Authorization is enforced server-side via NestJS guards. Client-side permission checks (hiding UI elements) are UX only — never security. |
   788→   788→| PostgreSQL RLS | Row-Level Security policies enforce tenant isolation at the database level. Even if application code has a bug, RLS prevents cross-tenant data access. |
   789→   789→| Principle of least privilege | Users and services have the minimum permissions necessary. A service that reads user profiles does not need write access. |
   790→   790→| Admin impersonation audit | When a super admin impersonates a user, an audit log entry is created with both the admin's and the target user's IDs. The impersonated session is clearly marked. |
   791→   791→
   792→   792→### 10.6.3 Input Validation Rules
   793→   793→
   794→   794→| Rule | Description |
   795→   795→|------|-------------|
   796→   796→| Validate everything | Every input from the client (body, query params, path params, headers) is validated with Zod schemas. No exceptions. |
   797→   797→| Server-side validation is authoritative | Client-side validation is UX only. Server-side validation is the source of truth and must be complete. |
   798→   798→| Sanitize all strings | All string inputs are sanitized: trimmed, stripped of null bytes and control characters. HTML content is sanitized with a library like DOMPurify. |
   799→   799→| No user input in file paths | User-provided strings are never used directly in file system paths. Use UUIDs for file naming. |
   800→   800→| No user input in SQL | All database queries use parameterized queries via TypeORM/Prisma. Raw SQL is forbidden except in migrations. |
   801→   801→| No user input in commands | User input is never passed to `child_process`, `eval()`, or `Function()`. |
   802→   802→| File upload validation | Validate file type (by magic bytes, not extension), file size, and file content. Quarantine uploaded files until validation is complete. |
   803→   803→
   804→   804→### 10.6.4 Data Protection Rules
   805→   805→
   806→   806→| Rule | Description |
   807→   807→|------|-------------|
   808→   808→| Encrypt at rest | All sensitive data (passwords, API keys, tokens) is encrypted at rest using AES-256. Database-level encryption for PII fields. |
   809→   809→| Encrypt in transit | TLS 1.3 for all connections. HSTS header enabled. No plain HTTP, not even internally. |
   810→   810→| No PII in logs | Passwords, tokens, API keys, and personal identifying information are never logged. Log only non-sensitive identifiers (user ID, not email or phone). |
   811→   811→| No PII in URLs | Personal data does not appear in query parameters or path segments. Use POST body or server-side lookups instead. |
   812→   812→| Data masking in responses | Sensitive fields (passwords, API keys, internal IDs) are never included in API responses. Use DTOs to control exactly which fields are returned. |
   813→   813→| Right to erasure | User data deletion is supported. When a user is deleted, all their personal data is purged within 30 days (with a grace period for accidental deletion recovery). |
   814→   814→
   815→   815→### 10.6.5 API Security Rules
   816→   816→
   817→   817→| Rule | Description |
   818→   818→|------|-------------|
   819→   819→| CORS configuration | Explicit allowlist of origins. No `*` wildcard. Credentials allowed only for known origins. |
   820→   820→| CSRF protection | All state-changing requests require the `Authorization` header (which prevents CSRF since custom headers trigger preflight). Cookie-based refresh token endpoints use CSRF tokens additionally. |
   821→   821→| Security headers | `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` are set on all responses. |
   822→   822→| Rate limiting headers | `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` on every response. |
   823→   823→| No sensitive data in query params | API keys, tokens, and secrets are never passed in URL query parameters. |
   824→   824→| Request size limits | Body size is limited: 1MB for JSON, 50MB for file uploads. |
   825→   825→| Dependency auditing | `npm audit` runs in CI. Critical and high vulnerabilities block the build. Dependabot or Renovate is enabled for automatic PRs. |

   916→   916→| Rule | Description |
   917→   917→|------|-------------|
   918→   918→| Main branch is always deployable | The `main` branch must always be in a state where it can be deployed to production at any time. No broken tests, no incomplete features, no debug code. |
   919→   919→| Feature branches from main | All feature branches are created from `main` and merged back into `main` via pull request. |
   920→   920→| Branch naming | `{type}/{ticket}-{short-description}`. Example: `feat/HOT-1234-user-search-filter`, `fix/HOT-5678-login-redirect-loop`. |
   921→   921→| Branch types | `feat/` (new feature), `fix/` (bug fix), `chore/` (maintenance, dependencies), `docs/` (documentation), `refactor/` (code restructuring without behavior change), `perf/` (performance improvement), `test/` (adding or fixing tests), `security/` (security fix). |
   922→   922→| No long-lived branches | Feature branches must be merged or closed within 5 business days. If a branch needs more time, it should be broken into smaller incremental PRs. |
   923→   923→| Rebase before merge | Feature branches must be rebased onto the latest `main` before merging (not merged with a merge commit, unless resolving complex conflicts). Squash merge is the default strategy. |
   924→   924→| No direct commits to main | All changes to `main` go through pull requests. Direct commits are blocked by branch protection rules. |
   925→   925→| Release branches | Release branches (`release/v1.2.0`) are created from `main` for production releases. Hotfix branches (`hotfix/v1.2.1`) are created from release branches or `main`. |
   926→   926→
   927→   927→### 10.9.2 Branch Protection
   928→   928→
   929→   929→The `main` branch has the following protections:
   930→   930→
   931→   931→- No direct push (require PR)
   932→   932→- Require 1 approval (2 for database schema changes)
   933→   933→- Require passing CI checks (lint, type-check, test)
   934→   934→- Require up-to-date branch (rebase before merge)
   935→   935→- Require signed commits (GPG or SSH)
   936→   936→- No force push
   937→   937→- Linear history (squash merge only)
   938→   938→
   939→   939→### 10.9.3 Git Hygiene
   940→   940→
   941→   941→| Rule | Description |
   942→   942→|------|-------------|
   943→   943→| No committed secrets | `.env` files, API keys, tokens, and credentials are in `.gitignore`. A pre-commit hook (git-secrets or gitleaks) scans for accidentally committed secrets. |
   944→   944→| No committed build artifacts | `node_modules/`, `dist/`, `.next/`, `build/`, and other build outputs are in `.gitignore`. |
   945→   945→| No large files | Files larger than 10MB are tracked via Git LFS. This includes videos, large datasets, and model files. |
   946→   946→| No merge conflicts in committed code | PRs with merge conflicts are not mergable. Resolve all conflicts before merging. |
   947→   947→| `.gitignore` is comprehensive | The project `.gitignore` covers all common ignores: node_modules, dist, build, .env, .DS_Store, *.log, coverage, .turbo. |

   951→   951→## 10.10 Pull Request Rules
   952→   952→
   953→   953→### 10.10.1 PR Requirements
   954→   954→
   955→   955→| Rule | Description |
   956→   956→|------|-------------|
   957→   957→| PR title follows Conventional Commits | `feat(users): add search and filter to user list` — type(scope): description. Persian descriptions are acceptable. |
   958→   958→| PR description is complete | Every PR includes: (1) What changed and why, (2) How to test, (3) Screenshots for UI changes, (4) Breaking changes (if any), (5) Links to related tickets. |
   959→   959→| PR size limit | PRs must not exceed 400 lines of changed code (excluding tests and generated files). If a change is larger, split it into multiple incremental PRs. |
   960→   960→| PR links to a ticket | Every PR references at least one ticket number in the description: `Closes HOT-1234` or `Related to HOT-1234`. |
   961→   961→| All CI checks pass | Lint, type-check, unit tests, and integration tests must pass before a PR is reviewed. |
   962→   962→| No draft PRs in review | Mark PRs as "Ready for Review" only when they are ready. Draft PRs are not reviewed. |
   963→   963→
   964→   964→### 10.10.2 Review Rules
   965→   965→
   966→   966→| Rule | Description |
   967→   967→|------|-------------|
   968→   968→| At least 1 approval required | Every PR requires at least 1 approving review from a team member. PRs touching security, authentication, or billing require 2 approvals. |
   969→   969→| Review within 24 hours | PRs must receive a first review within 24 hours of being marked "Ready for Review". If no review is available, the PR author may self-merge trivial changes (typos, config) after 48 hours. |
   970→   970→| Reviews are constructive | Review comments must be specific, actionable, and respectful. "This is wrong" is not a review comment. "This query lacks an index on `user_id`, which will cause a seq scan. See: [EXPLAIN output]" is. |
   971→   971→| Address all comments | All review comments must be addressed (fixed, discussed, or explicitly deferred with a reason). Push a new commit to address comments — do not amend the existing commit. |
   972→   972→| No rubber-stamping | Reviewers must actually read and understand the code. A review that only checks the "Approve" button without comments is not a review. |
   973→   973→| Self-review first | PR authors must self-review their own diff before requesting review. Use GitHub's "Review changes" feature. |

  1006→  1006→## 10.11 Commit Rules
  1007→  1007→
  1008→  1008→### 10.11.1 Conventional Commits
  1009→  1009→
  1010→  1010→All commits follow the [Conventional Commits](https://www.conventionalcommits.org/) specification:
  1011→  1011→
  1012→  1012→```
  1013→  1013→<type>(<scope>): <subject>
  1014→  1014→
  1015→  1015→<body>
  1016→  1016→
  1017→  1017→<footer>
  1018→  1018→```
  1019→  1019→
  1020→  1020→**Types:**
  1021→  1021→
  1022→  1022→| Type | Description | Example |
  1023→  1023→|------|-------------|--------|
  1024→  1024→| `feat` | New feature | `feat(chat): add message branching UI` |
  1025→  1025→| `fix` | Bug fix | `fix(auth): resolve token refresh loop on expired JWT` |
  1026→  1026→| `docs` | Documentation only | `docs(api): update authentication endpoint spec` |
  1027→  1027→| `style` | Code style (formatting, semicolons) | `style(lint): fix trailing comma issues` |
  1028→  1028→| `refactor` | Code restructuring, no behavior change | `refactor(agents): extract tool-binding logic to separate service` |
  1029→  1029→| `perf` | Performance improvement | `perf(rag): add query caching for vector search results` |
  1030→  1030→| `test` | Adding or updating tests | `test(users): add integration tests for bulk user creation` |
  1031→  1031→| `chore` | Maintenance, dependencies, config | `chore(deps): update Next.js to 15.1.0` |
  1032→  1032→| `ci` | CI/CD changes | `ci(github): add E2E test job to pipeline` |
  1033→  1033→| `build` | Build system or dependencies | `build(turbo): configure remote caching` |
  1034→  1034→| `revert` | Revert a previous commit | `revert: feat(chat): add message branching UI` |
  1035→  1035→
  1036→  1036→**Scope** (optional but recommended):
  1037→  1037→
  1038→  1038→The scope is the module or feature area affected. Use the module/directory name: `auth`, `users`, `agents`, `chat`, `knowledge`, `rag`, `billing`, `admin`, `ui`, `shared`, `config`.
  1039→  1039→
  1040→  1040→**Subject rules:**
  1041→  1041→
  1042→  1042→| Rule | Description |
  1043→  1043→|------|-------------|
  1044→  1044→| Imperative mood | Use "add", not "added" or "adds". |
  1045→  1045→| Lowercase | Do not capitalize the first letter. |
  1046→  1046→| No period | Do not end with a period. |
  1047→  1047→| Maximum 72 characters | Keep the subject line concise. |
  1048→  1048→| Persian acceptable | The subject may be in Persian if the change is user-facing or team convention. |
  1049→  1049→
  1050→  1050→**Body rules:**
  1051→  1051→
  1052→  1052→- Explain **what** and **why**, not **how** (the code shows how).
  1053→  1053→- Separate from subject with a blank line.
  1054→  1054→- Wrap at 72 characters.
  1055→  1055→- Use bullet points for multiple changes.
  1056→  1056→
  1057→  1057→**Footer rules:**
  1058→  1058→
  1059→  1059→- Reference tickets: `Closes HOT-1234` or `Related to HOT-1234`.
  1060→  1060→- Breaking changes: `BREAKING CHANGE: description of what broke and migration steps.`
  1061→  1061→
  1062→  1062→### 10.11.2 Commit Discipline
  1063→  1063→
  1064→  1064→| Rule | Description |
  1065→  1065→|------|-------------|
  1066→  1066→| One logical change per commit | A commit contains one logical change. A feature with 3 unrelated files gets 3 commits. A bug fix and a refactor are separate commits. |
  1067→  1067→| Atomic commits | Each commit is atomic: it either applies completely or not at all. No partially complete commits. |
  1068→  1068→| No whitespace-only commits | Whitespace changes are bundled with the logical change they accompany. |
  1069→  1069→| No "fix lint" follow-up commits | Lint and format issues are fixed before committing. Pre-commit hooks (lint-staged + husky) enforce this. |
  1070→  1070→| No WIP commits | Work-in-progress commits are not pushed. Use `git stash` locally. Push only when the change is ready for review. |
  1071→  1071→| Signed commits | All commits are signed (GPG or SSH key). Unsigned commits are rejected by branch protection. |
  1072→  1072→| Meaningful commit messages | `fix stuff`, `update`, `wip`, `asdf` are forbidden. Every commit message must clearly describe the change. |
  1073→  1073→
  1074→  1074→### 10.11.3 Pre-Commit Hooks
  1075→  1075→
  1076→  1076→| Hook | Tool | Purpose |
  1077→  1077→|------|------|---------|
  1078→  1078→| `pre-commit` | lint-staged | Runs ESLint and Prettier on staged files only. Fixes auto-fixable issues. Rejects the commit if unfixable issues exist. |
  1079→  1079→| `pre-commit` | tsc (type-check) | Runs TypeScript type-checking on the entire project. Rejects the commit if type errors exist. |
  1080→  1080→| `pre-commit` | git-secrets | Scans staged files for secrets, API keys, tokens, and credentials. Rejects the commit if found. |
  1081→  1081→| `commit-msg` | commitlint | Validates commit message against Conventional Commits format. Rejects the commit if the format is wrong. |

  1085→  1085→## 10.12 Documentation Rules
  1086→  1086→
  1087→  1087→### 10.12.1 Code Documentation
  1088→  1088→
  1089→  1089→| Rule | Description |
  1090→  1090→|------|-------------|
  1091→  1091→| JSDoc on public APIs | All exported functions, classes, interfaces, and types have JSDoc comments describing their purpose, parameters, and return value. |
  1092→  1092→| JSDoc language | JSDoc descriptions are in English (developer-facing). UI-facing text (labels, messages) is in Persian. |
  1093→  1093→| No obvious JSDoc | `/** Returns the user's display name */` on `getDisplayName()` adds no value. Only document non-obvious behavior, edge cases, and constraints. |
  1094→  1094→| Complex logic comments | Non-obvious algorithms, business rules, and workarounds have inline comments explaining **why**, not **what**. |
  1095→  1095→| `// SAFETY:` for unsafe operations | Any `as` cast, `!` assertion, or type coercion must be preceded by a `// SAFETY:` comment explaining why it's safe. |
  1096→  1096→| `// TODO(ticket):` for deferred work | All TODOs reference a ticket number. Plain TODOs are forbidden. |
  1097→  1097→| No commented-out code | Dead code is deleted, not commented. Git preserves history. |
  1098→  1098→| No file-level headers | No `// @file`, `// @author`, `// @date` headers. This information is in git metadata. |

  1102→  1102→| Rule | Description |
