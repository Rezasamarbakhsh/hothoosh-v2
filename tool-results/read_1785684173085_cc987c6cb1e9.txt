    20→   315→### 3.2 State Management Boundaries
    21→   316→
    22→   317→HotHoosh enforces a strict separation of state management concerns. Overlapping these boundaries is a violation of Engineering Rules §10.4.1.
    23→   318→
    24→   319→| State Type | Tool | Scope | Examples |
    25→   320→|-----------|------|-------|----------|
    26→   321→| **Server state** | TanStack Query | API data: users, agents, knowledge bases, usage stats | `useQuery`, `useMutation`, `useInfiniteQuery` |
    27→   322→| **Client state** | Zustand | UI-only: theme, sidebar open/closed, command palette, selection | `useThemeStore`, `useSidebarStore` |
    28→   323→| **Form state** | React Hook Form + Zod | Form inputs: login form, create agent, upload document | `useForm` with `zodResolver` |
    29→   324→| **URL state** | Next.js `useSearchParams` | Filters, pagination, active tab | `?page=2&status=active&sort=created_at` |
    30→   325→
    31→   326→**Key rules:**
    32→   327→- Zustand stores never hold server data. If it came from the API, it belongs in TanStack Query.
    33→   328→- Zustand store actions are synchronous. Async work (API calls) lives in TanStack Query mutations, which call Zustand actions on success.
    34→   329→- Components read Zustand via selectors (`useThemeStore(s => s.theme)`) to prevent unnecessary re-renders.
    35→   330→- TanStack Query keys use a factory pattern: `chatKeys.messages(sessionId)`, `adminKeys.agents.list(filters)`.

   126→   421→### 3.5 Server Components and Client Boundaries
   127→   422→
   128→   423→Per Engineering Rules §10.4.1, all components are **React Server Components** by default. The `'use client'` directive is added only when a component uses hooks, event handlers, or browser APIs. The client boundary is placed at the feature component level — child components of a client component are automatically client components.
   129→   424→
   130→   425→| Boundary | `'use client'`? | Rationale |
   131→   426→|----------|-----------------|-----------|
   132→   427→| Root layout | No | Pure HTML shell, fonts, providers |
   133→   428→| Workspace shell | No | Layout structure, navigation |
   134→   429→| Page components | Usually No | Data fetching via `async/await` in Server Components |
   135→   430→| Chat input | **Yes** | Uses `useState`, `onSubmit`, keyboard events |
   136→   431→| Message list | **Yes** | Uses `useChatStreaming` (EventSource), scroll management |
   137→   432→| Agent gallery card | No | Static rendering, link via `next/link` |
   138→   433→| Data table (admin) | **Yes** | Sorting, filtering, pagination interactions |
   139→   434→| Dashboard stat card | No | Receives data as props from Server Component parent |
   140→   435→| Chart component | **Yes** | Canvas/SVG rendering, interactivity |

   142→   437→### 3.6 RTL-First Design
   143→   438→
   144→   439→Per PRD Principles #1 and #2, the entire interface is built **RTL-first** using CSS logical properties. LTR is supported as a secondary direction. The root `<html>` element has `dir="rtl"` by default for Persian users.
   145→   440→
   146→   441→**CSS rules enforced by the engineering rules:**
   147→   442→- Use `ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `inline-*`, `block-*` exclusively.
   148→   443→- Never use physical properties: `left`, `right`, `ml-*`, `mr-*`, `pl-*`, `pr-*`.
   149→   444→- Tailwind utility classes follow logical property mapping: `ms-4` (margin-inline-start), `me-4` (margin-inline-end).
   150→   445→- Dark mode is implemented by switching CSS variable values on `:root` and `[data-theme="dark"]`. Tailwind's `dark:` variant is not used.

   165→   460→## 4. Backend Architecture
   166→   461→
   167→   462→### 4.1 Architectural Philosophy
   168→   463→
   169→   464→HotHoosh's backend is a **NestJS modular monolith** with hexagonal module boundaries (PRD Principle #15, Engineering Rules §10.4.2). The entire backend runs as a single deployable unit, but internal module boundaries are strictly enforced as if each module were a separate microservice. Modules communicate exclusively through well-defined public APIs (injected services and domain events), never through shared mutable state or direct internal imports across module boundaries.
   170→   465→
   171→   466→The modular monolith preserves the ability to extract modules into separate services in the future (v2.0+) because hexagonal boundaries ensure low coupling and high cohesion within each domain module.
   172→   467→
   173→   468→### 4.2 Technology Stack
   174→   469→
   175→   470→| Layer | Technology | Rationale |
   176→   471→|-------|-----------|----------|
   177→   472→| Runtime | Node.js 20+ LTS | Non-blocking I/O for SSE streaming and concurrent AI requests |
   178→   473→| Framework | NestJS 10+ | DI container, module system, guard/filter/interceptor pipeline |
   179→   474→| ORM | TypeORM | PostgreSQL-native, custom repository support, migration tooling |
   180→   475→| Database | PostgreSQL 16+ | pgvector, RLS, JSONB, partitioned tables, full-text search |
   181→   476→| Cache/Queue | Redis 7+ | BullMQ job queues, session store, rate limiting, caching |
   182→   477→| Validation | Zod | Shared schemas between frontend and backend (§10.1.3) |
   183→   478→| File Storage | S3-compatible (MinIO) | Document storage for knowledge bases |
   184→   479→| Email | Nodemailer (SMTP) | Transactional emails for invitations, password resets |
   185→   480→| Streaming | Server-Sent Events (SSE) | One-directional real-time AI response streaming |
   186→   481→

   206→   501→### 4.4 6 Engine Modules
   207→   502→
   208→   503→Engine modules provide AI/ML infrastructure consumed by domain modules. They are stateless computational units (no owned database tables, except for caching/state).
   209→   504→
   210→   505→| Engine | Responsibility | Consumed By | Key Design |
   211→   506→|--------|---------------|-------------|------------|
   212→   507→| **llm-router** | Route AI requests to optimal provider/model, health monitoring, failover | `ChatModule`, `RAGEngine` | 5-step routing pipeline, circuit breakers, Redis health cache |
   213→   508→| **context-engine** | Token budget allocation, context window management, priority reduction | `ChatModule` | Priority: Knowledge (40%) → History (30%) → Memory (20%) → Tools (10%) |
   214→   509→| **rag-engine** | Document processing pipeline, hybrid retrieval, Persian NLP | `ChatModule`, `KnowledgeModule` | HNSW + BM25 with RRF, 4 chunking strategies, Persian normalizer |
   215→   510→| **memory-engine** | Memory pack resolution, hierarchical assembly, injection | `ChatModule`, `ContextEngine` | Workspace → Brand → Company → Org (accumulates upward) |
   216→   511→| **tool-engine** | Tool registry, validation, sandboxed execution, result formatting | `ChatModule` | JSON Schema input validation, timeout enforcement, audit logging |
   217→   512→| **streaming-engine** | SSE connection management, event emission, backpressure | `ChatModule`, `KnowledgeModule` | 8 event types, Redis connection tracking, 50ms batch window |
   218→   513→
   219→   514→### 4.5 Domain Event System
   220→   515→
   221→   516→Modules never import each other's services directly for cross-domain operations. Instead, they emit **domain events** through an in-memory event bus backed by Redis for reliability. A **transactional outbox** pattern ensures no events are lost: events are written to the database within the same transaction as the state change, then dispatched asynchronously by a BullMQ worker.
   222→   517→
   223→   518→```
   224→   519→Service performs write operation
   225→   520→  → Opens DB transaction
   226→   521→  → Writes domain state change
   227→   522→  → Inserts outbox_events record (same transaction)
   228→   523→  → Commits atomically
   229→   524→  → BullMQ worker polls outbox
   230→   525→  → Dispatches to event bus
   231→   526→  → Handlers react asynchronously
   232→   527→```
   233→   528→
   234→   529→### 4.6 Authentication: Dual-Token JWT
   235→   530→
   236→   531→| Token | Algorithm | Expiry | Storage | Purpose |
   237→   532→|-------|-----------|-------|---------|---------|
   238→   533→| **Access** | RS256 (asymmetric) | 15 minutes | In-memory only | API authentication. Validated via public key — no DB lookup. |
   239→   534→| **Refresh** | HS256 (symmetric) | 7 days | `HttpOnly`, `Secure`, `SameSite=Strict` cookie | Session persistence. Validated via DB lookup (revocation check). |
   240→   535→
   241→   536→**Token rotation on refresh:** Every refresh invalidates the old token and issues a new one with the same `family_id`. If a previously-revoked token is presented (theft detection), all tokens in that family are revoked.
   242→   537→
   243→   538→**Password hashing:** Argon2id (memory=64MB, time=3, parallelism=4). Account lockout after 10 failed attempts within 1 hour (30-minute lockout).
   244→   539→
   245→   540→### 4.7 Authorization: Three-Layer RBAC + RLS
   246→   541→
   247→   542→| Layer | Source | Scope | Example Roles |
   248→   543→|-------|--------|-------|--------------|
   249→   544→| **Organization Role** | `roles` table (`level = 'org'`) | Organization-wide | `super_admin`, `org_admin`, `org_member` |
   250→   545→| **Workspace Role** | `workspace_users.role_id` | Workspace-specific | `workspace_admin`, `workspace_member`, `workspace_viewer` |
   251→   546→| **Resource Permissions** | `roles.permissions` JSONB | Individual resource | `agents:create`, `knowledge:delete`, `billing:read` |
   252→   547→
   253→   548→Effective permissions are the **union** of all permissions from all roles the user holds. Authorization is enforced via NestJS guards (`JwtAuthGuard → TenantScopeGuard → RolesGuard → ImpersonationGuard`).
   254→   549→
   255→   550→**PostgreSQL RLS** provides database-level tenant isolation — even if application code has a bug, RLS prevents cross-tenant data access. Session variables (`app.current_user_id`, `app.current_org_id`) are set at connection checkout.
   256→   551→
   257→   552→### 4.8 API Design
   258→   553→
   259→   554→All endpoints follow REST conventions with URL-based versioning (`/v1/`), consistent response envelopes, and pagination on all list endpoints.
   260→   555→
   261→   556→**Response envelope (success):**
   262→   557→```json
   263→   558→{ "data": { ... }, "meta": { "page": 1, "limit": 20, "total": 142, "hasMore": true } }
   264→   559→```
   265→   560→
   266→   561→**Response envelope (error):**
   267→   562→```json
   268→   563→{ "error": { "code": "AGENT_NOT_FOUND", "message": "عامل هوش مصنوعی یافت نشد", "details": {} } }
   269→   564→```
   270→   565→
   271→   566→**SSE streaming** is used for all AI responses. The endpoint `GET /v1/chats/:sessionId/stream` emits 8 event types: `token`, `message_start`, `message_delta`, `message_complete`, `tool_call`, `tool_result`, `error`, `heartbeat`.
   272→   567→
   273→   568→### 4.9 Error Handling
   274→   569→
   275→   570→Each domain module defines typed exceptions extending `DomainException`. A global `DomainExceptionFilter` catches all unhandled exceptions and returns the standardized error envelope. Raw stack traces never reach the client. Circuit breakers protect against external service failures (AI providers, S3, SMTP, embedding APIs).

   618→   913→## 7. Infrastructure
   619→   914→
   620→   915→### 7.1 PostgreSQL 16+
   621→   916→
   622→   917→PostgreSQL is the sole data store, chosen for its rich feature set that eliminates the need for multiple specialized databases.
   623→   918→
   624→   919→| Feature | Implementation | Purpose |
   625→   920→|---------|---------------|---------|
   626→   921→| **pgvector** (0.7+) | HNSW index with cosine similarity | Vector embeddings for RAG — 10M+ vectors |
   627→   922→| **Row-Level Security** | Session variable-based policies | Tenant isolation at DB level |
   628→   923→| **JSONB** | GIN indexes via `btree_gin` | Flexible settings, permissions, tool schemas |
   629→   924→| **Full-Text Search** | `to_tsvector('persian', ...)` with GIN | BM25 retrieval for hybrid RAG search |
   630→   925→| **pg_trgm** | Trigram GIN indexes | Fuzzy text search |
   631→   926→| **Partitioning** | Monthly range on `usage_logs`, `audit_logs`, `chat_messages` | Query performance on high-volume tables |
   632→   927→| **UUID v7** | Custom `uuid_generate_v7()` function | Time-sortable globally unique PKs |
   633→   928→| **BIGINT PKs** | Auto-increment on append-only tables | Maximum insert throughput for logs/messages |
   634→   929→
   635→   930→**Connection pooling:** PgBouncer in transaction mode for high-concurrency scenarios. Pool size configurable (default: 20 connections). Connection initialization callback sets RLS session variables.
   636→   931→
   637→   932→### 7.2 Redis 7+
   638→   933→
   639→   934→Redis serves six distinct roles in the HotHoosh architecture:
   640→   935→
   641→   936→| Role | Data Type | TTL | Key Pattern Example |
   642→   937→|------|-----------|-----|-------------------|
   643→   938→| **BullMQ backing store** | Lists, hashes, sets | Job-dependent | `bull:document-processing:*` |
   644→   939→| **SSE connection tracking** | Hash | 30 min | `sse:connections:{sessionId}` |
   645→   940→| **Rate limiting** | String (sliding window) | Window-dependent | `ratelimit:{userId}:{endpoint}` |
   646→   941→| **Session lockout** | String (counter) | 1 hour | `lockout:{userId}:attempts` |
   647→   942→| **Event outbox pointer** | String | Persistent | `outbox:lastProcessedId` |
   648→   943→| **Provider health cache** | Hash | 30 seconds | `health:{providerId}` |
   649→   944→| **Config cache** | Hash | 5 minutes | `cache:config:{scope}:{key}` |
   650→   945→| **Token family tracking** | String (set) | 7 days | `family:{familyId}:tokens` |
   651→   946→| **Password reset tokens** | String | 1 hour | `reset:{email}` |
   652→   947→| **Idempotency keys** | String | 24 hours | `idempotency:{key}` |
   653→   948→
   654→   949→Configured with `maxmemory-policy: allkeys-lru`. Connection pooling enabled (max 20 connections).
   655→   950→
   656→   951→### 7.3 S3-Compatible Storage
   657→   952→
   658→   953→Used for all file storage. MinIO for self-hosted deployments; AWS S3 for cloud deployments. All uploads use server-side encryption (AES-256). Pre-signed URLs for client-side downloads (15-minute expiry).
   659→   954→
   660→   955→| Operation | Key Pattern | Max Size | Validation |
   661→   956→|-----------|-------------|----------|------------|
   662→   957→| Document upload | `knowledge/{wsId}/{kbId}/{uuid}/{filename}` | 50 MB | Magic bytes, content scan |
   663→   958→| Avatar upload | `avatars/{userId}/{uuid}.{ext}` | 5 MB | Image magic bytes |
   664→   959→| Logo upload | `logos/{entityType}/{entityId}/{uuid}.{ext}` | 5 MB | Image magic bytes |
   665→   960→| Exports/Backups | `backups/{type}/{date}/{filename}` | Variable | N/A |
   666→   961→
   667→   962→### 7.4 BullMQ Queue System
   668→   963→
   669→   964→11 queues handle all asynchronous processing. No long-running operations run in request handlers.
   670→   965→
   671→   966→| # | Queue | Purpose | Priority | Concurrency |
   672→   967→|---|-------|---------|----------|-------------|
   673→   968→| 1 | `document-processing` | Knowledge document pipeline (extract → chunk → embed → index) | Low | 5 |
   674→   969→| 2 | `embedding-generation` | Batch embedding for chunks | Low | 3 |
   675→   970→| 3 | `vector-indexing` | Bulk vector index updates | Low | 2 |
   676→   971→| 4 | `health-check` | AI provider health monitoring (every 30s) | Critical | 3 |
   677→   972→| 5 | `email-sending` | Transactional emails | Medium | 10 |
   678→   973→| 6 | `usage-aggregation` | Hourly usage metric aggregation | Medium | 2 |
   679→   974→| 7 | `audit-log-purge` | Daily expired audit log cleanup | Low | 1 |
   680→   975→| 8 | `token-cleanup` | Daily expired refresh token purge | Low | 1 |
   681→   976→| 9 | `system-log-purge` | Daily old system log partition drop | Low | 1 |
   682→   977→| 10 | `invoice-generation` | Monthly automated invoice generation | High | 2 |
   683→   978→| 11 | `notification-delivery` | In-app notification creation/delivery | Medium | 5 |
   684→   979→
   685→   980→**Retry policy:** 3 attempts with exponential backoff (2s → 4s → 8s). Keeps last 1000 completed and 5000 failed jobs.
   686→   981→

   726→  1021→## 8. Key Design Decisions
   727→  1022→
   728→  1023→### DD-01: Modular Monolith, Not Microservices
   729→  1024→
   730→  1025→**Decision:** Build the backend as a single NestJS application with strict hexagonal module boundaries, not as a set of independent microservices.
   731→  1026→
   732→  1027→**Rationale:**
   733→  1028→
   734→  1029→| Factor | Modular Monolith | Microservices |
   735→  1030→|--------|-----------------|---------------|
   736→  1031→| Development velocity | Single codebase, single build, single deploy | Multiple codebases, independent builds |
   737→  1032→| Data consistency | Single PostgreSQL transaction spans all modules | Distributed transactions (Saga) or eventual consistency |
   738→  1033→| Team size fit | 3–8 developers (current phase) | Requires 10+ for independent service ownership |
   739→  1034→| Latency | In-process communication (nanoseconds) | Network communication (milliseconds) |
   740→  1035→| Operational cost | Single process to monitor and debug | Service mesh, load balancing, distributed tracing |
   741→  1036→
   742→  1037→Hexagonal boundaries ensure that any module can be extracted into a separate service in v2.0+ with minimal refactoring. The modular monolith gives us microservice-level discipline without microservice-level operational tax.
   743→  1038→
   744→  1039→### DD-02: PostgreSQL, Not MongoDB
   745→  1040→
   746→  1041→**Decision:** Use PostgreSQL 16+ as the sole data store.
   747→  1042→
   748→  1043→**Rationale:** HotHoosh requires ACID transactions (billing, token accounting), relational data (Org → Company → Brand → Workspace hierarchy), full-text search (BM25 for RAG), vector search (pgvector for embeddings), and row-level security (tenant isolation). PostgreSQL provides all of these in a single database, eliminating the operational complexity of maintaining MongoDB + a vector DB + a relational DB. JSONB columns provide schema flexibility where needed (settings, permissions, tool schemas).
   749→  1044→
   750→  1045→### DD-03: pgvector, Not Dedicated Vector DB (Initially)
   751→  1046→
   752→  1047→**Decision:** Use pgvector for vector storage and HNSW indexing. Do not introduce Pinecone, Qdrant, or Weaviate in v1.0.
   753→  1048→
   754→  1049→**Rationale:** pgvector with HNSW indexes achieves < 150ms P95 latency for 10M+ vectors, which meets our requirements. Adding a dedicated vector DB introduces operational complexity, data synchronization challenges, and cost. The PRD explicitly defers dedicated vector DB to v2.0 if scale demands it. PostgreSQL's advantage is that vector queries can join with relational data (e.g., filter by `knowledge_base_id` and `workspace_id` within the same query).
   755→  1050→
   756→  1051→### DD-04: Dual-Token JWT, Not Single Token or Session
   757→  1052→
   758→  1053→**Decision:** Use two separate JWTs: RS256 access token (15min, in-memory) + HS256 refresh token (7d, HttpOnly cookie).
   759→  1054→
   760→  1055→**Rationale:**
   761→  1056→
   762→  1057→| Approach | Security | Performance | Complexity |
   763→  1058→|----------|----------|-------------|------------|
   764→  1059→| Single long-lived JWT | Low — compromised token valid for days | High — no refresh needed | Low |
   765→  1060→| Server-side sessions | High — instant revocation | Low — DB lookup on every request | Medium |
   766→  1061→| **Dual-token JWT** | **High** — short-lived access, rotation detects theft | **High** — access token validated without DB | **Medium** |
   767→  1062→
   768→  1063→RS256 for access tokens means validation requires only the public key (no DB lookup). HS256 for refresh tokens means revocation requires the shared secret + DB check. The rotation mechanism provides theft detection: if a previously-revoked token is presented, all sessions are terminated.
   769→  1064→
   770→  1065→### DD-05: UUID v7, Not UUID v4
   771→  1066→
   772→  1067→**Decision:** Use UUID v7 (time-sortable) as the default primary key for all entities.
   773→  1068→
   774→  1069→**Rationale:** UUID v7 combines a Unix timestamp (millisecond precision) with random bytes. This produces IDs that are globally unique (no coordination) and time-sortable (recent entities have higher IDs), which benefits B-tree index performance on append-heavy tables. UUID v4 is random, causing index fragmentation on time-ordered data. For high-throughput append-only tables (audit_logs, chat_messages, usage_logs), BIGINT auto-increment is used instead to avoid UUID storage overhead.
   775→  1070→
   776→  1071→### DD-06: Immutable Chat Messages
   777→  1072→
   778→  1073→**Decision:** Chat messages are never updated in place. Edits create new messages. Branching uses `parent_message_id` + `branch_index`.
   779→  1074→
   780→  1075→**Rationale:** Immutability eliminates an entire class of bugs (concurrent edits, lost updates, audit trail corruption). Branching enables exploring different AI response directions without losing the original thread. The `parent_message_id` + `branch_index` model reconstructs conversation history by walking up the tree. This design also simplifies billing (each message has a definitive token count that never changes) and audit logging (a complete, tamper-proof record of every interaction).
   781→  1076→
   782→  1077→### DD-07: Zod, Not class-validator
   783→  1078→
   784→  1079→**Decision:** Use Zod schemas for all input validation on both frontend and backend.
   785→  1080→
   786→  1081→**Rationale:** Zod schemas can be shared between frontend and backend via `packages/shared`, guaranteeing that the same validation rules apply on both sides. `class-validator` uses decorators and classes, which cannot be shared with a React frontend. Zod also provides superior TypeScript inference (`z.infer<typeof schema>`) and composable schema building (`.pick()`, `.omit()`, `.partial()`, `.merge()`).
   787→  1082→
   788→  1083→### DD-08: NestJS, Not Express or Fastify
   789→  1084→
   790→  1085→**Decision:** Build the backend API with NestJS.
   791→  1086→
   792→  1087→**Rationale:** NestJS provides a built-in DI container, module system, and guard/filter/interceptor pipeline that directly map to our hexagonal architecture requirements. Express requires manual assembly of middleware chains and has no DI or module system. Fastify is performant but lacks NestJS's structured module system. NestJS's decorators (`@Controller`, `@Get`, `@UseGuards`) provide declarative API definitions that align with our engineering rules (thin controllers, guard-based authorization).
   793→  1088→
   794→  1089→### DD-09: App Router, Not Pages Router
   795→  1090→
   796→  1091→**Decision:** Use Next.js App Router (`app/` directory) exclusively.
   797→  1092→
   798→  1093→**Rationale:** The App Router supports React Server Components, which allow page-level data fetching via `async/await` without client-side JavaScript. This reduces the client-side JavaScript bundle and improves Core Web Vitals (especially LCP and FID). Server Components are the default; the `'use client'` directive is added only where needed. The Pages Router does not support Server Components and is considered legacy by Next.js.
   799→  1094→
   800→  1095→### DD-10: Zustand, Not Redux
   801→  1096→
   802→  1097→**Decision:** Use Zustand for client-side state management.
   803→  1098→
   804→  1099→**Rationale:**
   805→  1100→
   806→  1101→| Factor | Zustand | Redux Toolkit |
   807→  1102→|--------|---------|---------------|
   808→  1103→| Boilerplate | Minimal — no actions, reducers, providers | Significant — slice, asyncThunk, configureStore |
   809→  1104→| Bundle size | ~1 KB | ~11 KB |
   810→  1105→| Learning curve | Low — hooks-based API | Medium — requires understanding thunks, selectors |
   811→  1106→| TypeScript | First-class, simple | Good but verbose |
   812→  1107→
   813→  1108→Zustand's minimal API reduces boilerplate while providing the same capabilities (selectors, middleware for persistence, devtools integration). Since TanStack Query handles all server state, Zustand only manages simple UI state (theme, sidebar, selection), where its simplicity is a perfect fit.
   814→  1109→
   815→  1110→### DD-11: Feature-Based Folders, Not Type-Based
   816→  1111→
   817→  1112→**Decision:** Organize frontend code by feature (`features/chat/`), not by type (`components/`, `hooks/`, `stores/`).
   818→  1113→
   819→  1114→**Rationale:** Feature-based organization ensures that all code related to a domain concept lives in one place. A feature is self-contained and deletable — removing the `features/chat/` directory removes chat without affecting agents or knowledge. Type-based organization scatters related code across multiple directories, making it harder to understand, modify, and delete features. The engineering rules enforce this with the principle: "A feature must be deletable without affecting other features."
   820→  1115→
   821→  1116→### DD-12: CSS Logical Properties, Not Physical Properties
   822→  1117→
   823→  1118→**Decision:** Use `ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*` exclusively. Never use `left`, `right`, `ml-*`, `mr-*`.
   824→  1119→
   825→  1120→**Rationale:** HotHoosh is Persian-first and RTL-native. CSS logical properties automatically adapt to the document's `dir` attribute. When `dir="rtl"`, `margin-inline-start` maps to `margin-right`; when `dir="ltr"`, it maps to `margin-left`. Physical properties (`margin-left`) require manual RTL/LTR conditionals in every component. Logical properties make bidirectional support automatic and eliminates an entire class of RTL bugs.
   826→  1121→
   827→  1122→### DD-13: Solar Hijri Calendar
   828→  1123→
   829→  1124→**Decision:** Use Solar Hijri (شمسی) as the default calendar. Gregorian available as secondary.
   830→  1125→
   831→  1126→**Rationale:** HotHoosh targets Iranian enterprises. The Solar Hijri calendar is the official calendar of Iran, used for business operations, financial reporting, and legal documents. Displaying Gregorian dates as the default would be a localization failure. Day.js with the `jalaali-js` plugin provides Solar Hijri support with the same API as standard date handling.
   832→  1127→
   833→  1128→### DD-14: SSE, Not WebSocket for AI Streaming
   834→  1129→
   835→  1130→**Decision:** Use Server-Sent Events (`text/event-stream`) for all AI response streaming.
   836→  1131→
   837→  1132→**Rationale:**
   838→  1133→
   839→  1134→| Factor | SSE | WebSocket |
   840→  1135→|--------|-----|-----------|
   841→  1136→| Direction | Server → Client (unidirectional) | Bidirectional |
   842→  1137→| Complexity | Simple — built on HTTP | Complex — handshake, framing, ping/pong |
   843→  1138→| Proxy compatibility | Works through all proxies, CDNs, load balancers | Requires special proxy configuration (Upgrade header) |
   844→  1139→| Reconnection | Browser auto-reconnects | Manual reconnection logic |
   845→  1140→| HotHoosh need | Server pushes AI tokens to client | Client only sends messages via POST |
   846→  1141→
   847→  1142→AI response streaming is inherently unidirectional: the server generates tokens and the client displays them. The client sends messages via standard `POST` requests. There is no need for bidirectional communication. SSE is simpler, more robust, and works through all network infrastructure without special configuration.
   848→  1143→
   849→  1144→### DD-15: TypeORM, Not Prisma
   850→  1145→
   851→  1146→**Decision:** Use TypeORM as the ORM for NestJS.
   852→  1147→
   853→  1148→**Rationale:** TypeORM provides native PostgreSQL support including custom repository classes (essential for the repository pattern mandated by Engineering Rules §10.4.2), direct access to migration tooling, and fine-grained query control needed for complex operations (recursive CTEs for branch traversal, JSONB queries, pgvector operations). While Prisma offers a cleaner query API, TypeORM's custom repository support better aligns with our hexagonal architecture where repositories are the data access boundary.
   854→  1149→
   855→  1150→### DD-16: Invitation-Only Registration
   856→  1151→
   857→  1152→**Decision:** Users cannot self-register. All access is via organization invitation.
   858→  1153→
   859→  1154→**Rationale:** HotHoosh is an enterprise product, not a consumer SaaS. Open registration creates security risks (unauthorized access, spam accounts) and administrative burden. Invitation-only registration ensures that every user is explicitly authorized by an organization admin, tied to a specific role and organizational scope. This aligns with enterprise security requirements and Iranian enterprise governance practices.
   860→  1155→
   861→  1156→### DD-17: Hybrid Search (Vector + BM25), Not Vector Only
   862→  1157→
   863→  1158→**Decision:** Combine pgvector HNSW cosine similarity with PostgreSQL BM25 full-text search using Reciprocal Rank Fusion.
   864→  1159→
   865→  1160→**Rationale:** Vector search excels at semantic similarity but misses exact keyword matches. BM25 excels at keyword matching but misses semantic relationships. Hybrid search with RRF (k=60) combines the strengths of both. For Persian text specifically, exact keyword matching is critical because Persian morphology (prefixes, suffixes, zero-width non-joiners) can cause vector embeddings to miss matches that a full-text search catches easily.
   866→  1161→
   867→  1162→### DD-18: Bigint Auto-Increment for High-Throughput Tables
   868→  1163→
   869→  1164→**Decision:** Use BIGINT auto-increment (not UUID v7) for `audit_logs`, `usage_logs`, `chat_messages`, and `system_logs`.
   870→  1165→
   871→  1166→**Rationale:** UUID v7 is 128 bits (16 bytes) vs BIGINT which is 64 bits (8 bytes). On append-only tables that receive millions of inserts per month, halving the primary key size significantly reduces storage and index size. BIGINT auto-increment also provides optimal B-tree insert performance (sequential, no page splits). UUID v7 is used for all other tables where the benefits of global uniqueness and time-sortability outweigh the storage cost.
